Beginner — Chapter 1

What is DevOps?

Before we write a single line of code or touch a cloud console, we need to understand why DevOps exists — because it will shape every decision we make throughout this tutorial.

The Problem DevOps Solves

Imagine a traditional software company in 2010. The development team writes features for three months, then hands a zip file to the operations team and says "deploy this." The ops team has never seen the code before. They don't know what dependencies it needs, what environment variables it requires, or why it behaves differently on the production server than on the developer's laptop. The release takes two days of frantic debugging. Something breaks in production. Everyone points fingers. The developer says "it worked on my machine." The ops team says "you gave us a broken build."

This was the norm — and it was genuinely painful. Releases happened monthly or quarterly because they were so risky. Teams were siloed, incentives were misaligned (developers rewarded for shipping features, ops rewarded for stability), and the feedback loop from "code written" to "code running in production" was weeks or months long.

DevOps emerged to fix this. The word combines Development and Operations, but the idea is simpler than the jargon: the people who build software should also take responsibility for running it. When you know your code will page you at 3am if it breaks, you write it differently.

What Changes in a DevOps Culture

🤝
Shared Ownership
Developers own their service end-to-end — from writing the code to monitoring it in production. "You build it, you run it" is the mantra at Amazon.
⚡
Fast Feedback Loops
Code gets tested and deployed within minutes of being written. Problems surface immediately, before they compound. The goal is same-day feedback, not quarterly releases.
🤖
Automation Over Heroics
Manual steps are codified and automated. The hero who can deploy by hand at 2am is replaced by a pipeline that anyone can trigger with confidence.
📉
Small, Safe Changes
Deploy small changes frequently rather than big risky batches. If something breaks, you know exactly which small change caused it and rollback is trivial.
📚
Blameless Post-Mortems
When things break (and they will), the question is "what in our system allowed this to happen?" not "whose fault is this?" Fear of blame makes people hide problems.
📐
Measure Everything
You can't improve what you don't measure. Deployment frequency, lead time, incident rate, and recovery time are tracked and improved continuously.

DevOps vs Platform Engineering vs SRE

You'll hear these terms used interchangeably, but they're distinct:

  • DevOps — a cultural philosophy and set of practices. Anyone can practice DevOps. It's not a team or a role, it's a way of working.
  • SRE (Site Reliability Engineering) — Google's concrete implementation of DevOps principles, with specific tools like SLOs, error budgets, and toil reduction. SRE is DevOps with a rulebook.
  • Platform Engineering — building the internal tools and "golden paths" that let other development teams practice DevOps without becoming infrastructure experts. Platform engineers build the platform that makes DevOps easy for everyone else.

File Permissions — Why They Matter

Permissions control who can do what to a file. This bites DevOps engineers constantly — a script that "worked fine" on the developer's machine fails in production because it's not executable, or a config file is readable by the wrong user.

bashunderstanding and fixing permissions
# Look at permissions
ls -la src/app.js
# -rw-r--r-- 1 ubuntu ubuntu 1234 Jan 1 12:00 src/app.js
#  ↑↑↑       owner permissions (read+write, no execute)
#     ↑↑↑    group permissions (read only)
#        ↑↑↑ others permissions (read only)
# r=read(4), w=write(2), x=execute(1)

# Make a script executable (you'll do this constantly)

chmod 755 scripts/deploy.sh   # same thing: rwxr-xr-x

# Protect your SSH key (AWS requires this — will refuse to connect otherwise)
chmod 400 ~/.ssh/taskflow-key.pem

# Make a config file private
chmod 600 .env                # only owner can read/write, nobody else

# Check who owns a file
ls -la .env                   # shows owner and group
whoami                        # who you're logged in as

Version Control — Git

Git is the backbone of all modern DevOps. Every CI/CD pipeline, deployment, and code review you'll build in this tutorial starts with a git push. Let's set it up properly and create the TaskFlow repository.

Why Git is Non-Negotiable

Git does two things that make DevOps possible. First, it gives every change a permanent, addressable identity (a commit hash). This means you can always answer "exactly what code is running in production?" and "what changed between the version that worked and the version that's broken?" Second, Git enables collaboration without collision — multiple engineers can work on the same codebase simultaneously, and Git merges their changes intelligently.

In our pipeline, a git push to main will be the trigger for everything else: tests run, a Docker image is built, and the app gets deployed. Nothing happens without Git.

javascriptsrc/app.js — TaskFlow v1
const express = require('express');
const app = express();
app.use(express.json());

// In-memory store — we'll replace this with a real DB later
let tasks = [];
let nextId = 1;

// GET /tasks — list all tasks
app.get('/tasks', (req, res) => {
  res.json({ tasks, count: tasks.length });
});

// POST /tasks — create a task
// Expected body: { "title": "Buy milk" }
// Returns 400 if title is missing, 201 with the new task if successful
app.post('/tasks', (req, res) => {
  const { title } = req.body;
  if (!title || title.trim() === '') {
    return res.status(400).json({ error: 'title is required and cannot be empty' });
  }
  const task = { id: nextId++, title: title.trim(), done: false, createdAt: new Date().toISOString() };
  tasks.push(task);
  res.status(201).json(task);
});

// PATCH /tasks/:id — mark a task done or not done
app.patch('/tasks/:id', (req, res) => {
  const task = tasks.find(t => t.id === parseInt(req.params.id));
  if (!task) return res.status(404).json({ error: 'task not found' });
  task.done = req.body.done !== undefined ? req.body.done : task.done;
  res.json(task);
});

// DELETE /tasks/:id
app.delete('/tasks/:id', (req, res) => {
  const before = tasks.length;
  tasks = tasks.filter(t => t.id !== parseInt(req.params.id));
  if (tasks.length === before) return res.status(404).json({ error: 'task not found' });
  res.status(204).send();
});

// GET /health — used by load balancers and Kubernetes to check if app is alive
app.get('/health', (req, res) => {
  res.json({ status: 'ok', uptime: process.uptime(), timestamp: new Date().toISOString() });
});

const PORT = process.env.PORT || 3000;
const server = app.listen(PORT, () => {
  console.log(`TaskFlow API running on port ${PORT}`);
  console.log(`Try: curl http://localhost:${PORT}/health`);
});

// Export for testing
module.exports = { app, server };

Commit Message Convention

Vague commit messages like "fix stuff" are useless. Use Conventional Commits — a standard format that makes your git history readable and powers automated changelogs:

textconventional commit format
# Format: type(scope): description
# type is mandatory, (scope) is optional

feat: add PATCH /tasks/:id endpoint
feat(auth): add JWT token validation
fix: handle missing title in POST /tasks correctly
fix(db): close connection pool on shutdown
docs: add API usage examples to README
test: add integration tests for delete endpoint
chore: update express to v4.18.3
refactor: extract task validation to middleware
ci: add docker build step to GitHub Actions pipeline

# Why this matters:
# - "feat:" triggers a minor version bump (1.0.0 → 1.1.0)
# - "fix:" triggers a patch bump (1.0.0 → 1.0.1)
# - "feat!:" or "BREAKING CHANGE" triggers a major bump (1.0.0 → 2.0.0)

Networking Basics

When your app doesn't respond, 80% of the time it's a networking issue — wrong port, blocked firewall, incorrect DNS, or a missing security group rule. This chapter gives you the vocabulary and tools to diagnose those problems fast.

How a Request Reaches Your App

When a user types https://taskflow.app/tasks in their browser, here's exactly what happens before your Node.js code runs:

1

DNS Resolution

The browser asks a DNS resolver: "What IP address is taskflow.app?" The resolver checks its cache, then queries authoritative name servers, and returns something like 54.12.0.1. This lookup typically takes 10–100ms on first load.

2

TCP Connection

The browser opens a TCP connection to 54.12.0.1 on port 443 (HTTPS). This is a 3-way handshake — SYN, SYN-ACK, ACK. Takes one round-trip time (RTT).

3

TLS Handshake

Browser and server negotiate encryption, exchange certificates, and agree on a cipher suite. Your TLS certificate proves you're the real owner of taskflow.app.

4

HTTP Request

The browser sends GET /tasks HTTP/1.1 with headers like Host: taskflow.app, Accept: application/json.

5

Load Balancer

The request hits your AWS Application Load Balancer, which picks one of your running TaskFlow instances based on a round-robin or least-connections algorithm.

6

Security Group Check

AWS checks: is this traffic allowed by the Security Group attached to the EC2 instance or ECS task? If port 3000 isn't open, the request is silently dropped here.

7

Your Node.js Code

Express receives the request, routes it to the GET /tasks handler, queries the in-memory store, and sends back a JSON response.

Key Concepts You'll Use Every Day

🏠
IP Addresses
Private: 10.x.x.x, 172.16-31.x.x, 192.168.x.x — only reachable within your network. Public: Everything else — routable on the internet. Your EC2 instance gets both.
🚪
Ports
Every process that listens on the network uses a port. HTTP=80, HTTPS=443, SSH=22, Postgres=5432, our app=3000. Ports 1-1024 require root privileges.
🗺️
DNS
A Records map a domain to an IP. CNAME records alias one domain to another. TTL controls how long DNS results are cached. Low TTL = faster failover, more DNS queries.
🔒
HTTPS/TLS
TLS certificates prove identity and encrypt traffic. AWS Certificate Manager gives you free TLS certificates that auto-renew. Never run APIs over plain HTTP.
⚖️
Load Balancer
Sits in front of multiple app instances. Distributes traffic, performs health checks (removes unhealthy instances), and terminates TLS so your app only handles HTTP internally.
🧱
Security Groups
AWS stateful firewall. You define inbound and outbound rules by port, protocol, and source IP/CIDR. Think: "only allow port 3000 from the load balancer's IP".

Understanding HTTP Status Codes

Your API returns HTTP status codes. Knowing them makes you much faster at debugging — both your own API and external ones you depend on:

texthttp status codes cheat sheet
2xx — Success
  200 OK            GET /tasks returned tasks successfully
  201 Created       POST /tasks created a new task
  204 No Content    DELETE /tasks/1 — deleted, nothing to return

4xx — Client Error (the request is wrong)
  400 Bad Request   POST /tasks with no title — caller's fault
  401 Unauthorized  Missing or invalid auth token
  403 Forbidden     Valid token, but no permission for this action
  404 Not Found     PATCH /tasks/999 — task ID doesn't exist
  429 Too Many Req  Rate limit exceeded

5xx — Server Error (something broke in your code)
  500 Internal      Unhandled exception — always a bug to fix
  502 Bad Gateway   Load balancer can't reach your app
  503 Unavailable   App is overloaded or restarting
  504 Gateway TO    Your app is taking too long to respond
⚠️

The #1 AWS networking mistake: Forgetting to open the right port in your Security Group. CI/CD Pipelines

Right now, deploying TaskFlow means SSH-ing into a server and running commands by hand. That's fine once. It's not fine when you're shipping multiple times a day and a typo in a manual step takes down production. CI/CD eliminates that risk entirely.

What CI/CD Actually Means in Practice

Continuous Integration (CI) means every time anyone pushes code, an automated system immediately runs the full test suite against that code. If tests pass, the code is eligible for deployment. If they fail, the push is rejected and the developer is notified before the broken code can reach anyone else. The "continuous" part means this happens on every single commit, not just at release time.

Continuous Delivery (CD) means the deployment to production (or staging) is also automated. Once tests pass, the system builds a Docker image, pushes it to ECR, and updates the running containers — all without a human clicking buttons. The result: "code merged to main" and "code running in production" are the same event, separated by perhaps 5 minutes of pipeline runtime.

  push:
    branches: [main]
  pull_request:

  ECR_REPOSITORY: taskflow
  NODE_VERSION: '20'

  test:
    name: Test
    runs-on: ubuntu-latest   # GitHub provides this Linux runner for free

      - name: Checkout code
        uses: actions/checkout@v4
        # This action clones your repo into the runner

      - name: Set up Node.js
        uses: actions/setup-node@v4
        with:

        run: npm ci   # ci is stricter than install: uses package-lock.json exactly

          name: coverage-report

Understanding What the Pipeline Does

Let's trace through what happens the moment you type git push:

1

GitHub receives your push

GitHub's event system fires. It finds your ci.yml workflow matches the push: branches: [main] trigger.

2

A runner is provisioned

GitHub spins up a fresh Ubuntu virtual machine (the "runner"). This is a clean environment — nothing from previous runs persists. This is why you need npm ci to install dependencies every time.

3

Your code is checked out

The actions/checkout@v4 action clones your repo at the exact commit that triggered the workflow.

4

Tests run

npm ci, then npm test. If any test fails, the job fails, the build and deploy jobs never start, and GitHub marks the commit with a red ✗. GitHub can also block PR merges until the check passes.

5

Docker image is built and pushed

The build job authenticates to AWS (using the secrets you added), builds a Docker image tagged with the git commit SHA, and pushes it to ECR. The SHA tag means you can always trace exactly which code is in which image.

6

Deployment happens

We'll complete this step in Chapter 8 when we have Kubernetes set up. For now the deploy job just echoes the image name.

Docker — Containerising TaskFlow

Docker solves a problem that plagued software teams for decades: "it works on my machine." A container packages your application together with every library, runtime, and system dependency it needs — making the environment reproducible everywhere from a developer laptop to a production server.

Containers vs Virtual Machines

Both containers and VMs isolate workloads, but they do it at different levels. A VM emulates entire hardware and runs a full OS — heavy, slow to start, gigabytes in size. A container shares the host OS kernel and only packages the application and its dependencies — lightweight, starts in milliseconds, megabytes in size.

The practical difference: on your MacBook, you can run 3-4 VMs before it slows down. You can run hundreds of containers. And because containers are so lightweight, it's feasible to create a fresh one for every CI pipeline run — meaning every test runs in a perfectly clean, identical environment.

Core Docker Concepts

📄
Dockerfile
A text file with instructions to build an image. Describes the base OS, runtime, file copies, and start command. Think of it as a recipe.
🖼️
Image
A built, immutable snapshot of your app + environment. Can be pushed to a registry and pulled anywhere. Tagged with versions like taskflow:1.0.0 or taskflow:abc123.
📦
Container
A running instance of an image. Isolated filesystem, network, and process space. Can be started, stopped, and deleted while the image persists.
📚
Layer Cache
Each instruction in a Dockerfile creates a layer. Layers are cached — if package.json hasn't changed, Docker reuses the cached npm install layer. Order matters enormously for build speed.

Kubernetes — Orchestrating TaskFlow at Scale

Docker runs one container on one machine. Kubernetes runs hundreds of containers across dozens of machines, automatically healing failures, scaling with load, and rolling out updates with zero downtime. This is where DevOps gets serious.

Why Kubernetes Exists

Once you containerise an app, you face a new set of problems: What happens when the container crashes at 3am? Who restarts it? What if traffic spikes and one instance can't keep up — how do you add more? How do you deploy a new version without taking the app offline? How do containers find each other on the network when their IPs change constantly?

Kubernetes (K8s) was built at Google to solve exactly these problems. It treats your fleet of servers as a single pool of resources, then schedules containers onto servers based on available CPU and memory. It continuously reconciles actual state (what's running) against desired state (what you declared in YAML). If a container dies, Kubernetes notices immediately and starts a replacement — usually within seconds.

The Core Kubernetes Objects

🫘
Pod
The smallest deployable unit — one or more containers that share a network namespace and storage. Pods are ephemeral: they die and get replaced, never repaired in-place.
🔄
Deployment
Declares "I want 3 replicas of this pod running at all times, using this image." Kubernetes continuously ensures that's true. Handles rolling updates and rollbacks.
🔗
Service
A stable network endpoint in front of a set of pods. As pods come and go, the Service's IP stays constant. Type LoadBalancer creates an AWS ELB automatically.
🗂️
ConfigMap
Non-sensitive configuration injected as env vars or files. Change a ConfigMap and pods pick up the new config on next restart — no image rebuild needed.
🔑
Secret
Like ConfigMap but base64-encoded and access-controlled. Stores passwords, tokens, and keys. In production, back these with AWS Secrets Manager.
🚪
Ingress
HTTP routing rules — "traffic to /tasks goes to taskflow-service, traffic to /auth goes to auth-service." One load balancer handles all your services.

  namespace: taskflow

  selector:
    matchLabels:
      app: taskflow

    type: RollingUpdate

Monitoring & Observability

Deploying your app is only half the job. The other half is knowing what it's doing at all times — catching problems before your users do, and having enough data to diagnose failures quickly when they happen.

The Three Pillars of Observability

Monitoring tells you that something is wrong. Observability tells you why. A truly observable system gives you three types of data working together:

📝
Logs
Timestamped text records of events. "POST /tasks 201 — created task 42 in 23ms". Detailed but high-volume. Best for debugging specific incidents.
📈
Metrics
Numerical measurements over time. Request rate, error rate, latency percentiles, CPU, memory. Low-volume, fast to query. Best for dashboards and alerts.
🔍
Traces
A single request traced through every service it touched, with timing for each hop. Essential for microservices. Answers: "which service is slow and why?"

DevSecOps — Security Built Into the Pipeline

"Shift left" means moving security checks earlier in the development process — catching vulnerabilities when a developer writes a line of code, not after a breach in production. Security isn't a final gate; it's woven into every step.

The Cost of Finding Security Issues Late

A vulnerability caught by a developer during code review costs almost nothing to fix — change a line of code, submit a commit. The same vulnerability found in a production breach costs millions: legal fees, regulatory fines, customer notification, forensic investigation, reputation damage, and often the jobs of everyone involved. The earlier you catch it, the cheaper it is. DevSecOps is about making the cheap path also the default path.

Secret #1 Rule: Never Commit Secrets to Git

The most common, most damaging security mistake in DevOps: accidentally committing an AWS key, database password, or API token to a Git repository. Even if you immediately delete the file, the secret lives forever in git history — and GitHub has bots that scan every public push for credentials within seconds of the commit.

🚨

If you accidentally commit a secret to GitHub: (1) Immediately revoke the credential in AWS/GitHub/whatever issued it. (2) Remove it from code. (3) Rotate it — get a new one. Deleting the file is NOT enough. The secret is now in git history and must be considered compromised.

GitOps with ArgoCD

We've built a CI/CD pipeline that pushes code changes directly to Kubernetes. That works — but it has hidden problems. GitOps fixes them by making Git the single source of truth for everything that runs in production, including the infrastructure itself.

The Problem With Push-Based Deployment

Our current GitHub Actions pipeline has a step that runs kubectl set image to update the cluster. This means the pipeline needs credentials to access Kubernetes — and those credentials live as GitHub Secrets. If they're ever leaked, an attacker can modify your production cluster directly.

There's a subtler problem too: drift. Someone SSH-es into the cluster at 2am during an incident and runs a quick kubectl patch to fix something. The problem is resolved, but now the cluster's actual state no longer matches what's in Git. The next deployment will overwrite the fix — or worse, the fix was hiding a bigger problem that now resurfaces unexpectedly.

GitOps solves both: no external system ever needs cluster credentials, and any deviation from the Git-declared state is automatically detected and corrected.

⬆️
Push-Based (What We Have)
CI pipeline calls kubectl/AWS APIs directly. Pipeline needs cluster credentials. No drift detection — manual changes persist silently.
⬇️
Pull-Based GitOps (What We Want)
An agent inside the cluster watches Git. Credentials never leave the cluster. Any drift from Git is detected within seconds and auto-corrected.

How ArgoCD Works

ArgoCD runs as a set of pods inside your Kubernetes cluster. It continuously compares two things: the desired state (YAML files in your Git repository) and the live state (what's actually running in the cluster). When it detects a difference — whether from a new Git commit or a manual kubectl change — it reconciles them by applying the Git state.

The continuous reconciliation loop is what makes GitOps powerful. It's not just "deploy when someone pushes code." It's "at all times, ensure the cluster looks exactly like what's in Git." This is a fundamentally different and more reliable model.

Service Mesh — Istio

TaskFlow is one service. But real production systems have dozens — an auth service, a notification service, a billing service, all calling each other over the network. A service mesh gives you visibility, security, and traffic control across all of them without changing a single line of application code.

What Problem Does a Service Mesh Solve?

Imagine TaskFlow grows to three services: the API, an auth service, and a notification service. The auth service calls a third-party email provider. Every one of these network calls can fail. How do you ensure an email provider outage doesn't cascade into TaskFlow being completely unavailable? How do you gradually roll out a new version of the auth service to 10% of requests while keeping 90% on the stable version? How do you know which service is the bottleneck when a request is slow?

You could add retry logic, circuit breakers, and distributed tracing libraries to every service individually. But that means every team must implement it correctly, in every language, in every service. A service mesh moves all of this into the infrastructure layer via a sidecar proxy — a small proxy container injected automatically alongside every pod that intercepts all network traffic and handles it transparently.

🔒
mTLS — Zero Trust
Every service-to-service call is mutually authenticated and encrypted. Even if an attacker gets inside your cluster, they can't impersonate a service they don't have certificates for.
🚦
Traffic Management
Canary releases, A/B testing, blue/green deployments, retries with backoff, timeouts, and fault injection — all declaratively configured in YAML, no code changes.
📊
Automatic Observability
Latency, error rate, and request rate between every service pair — automatically collected. Service topology graph shows the full call chain with health indicators.
⚡
Circuit Breaking
When a downstream service starts failing, the mesh automatically stops sending it traffic — preventing cascade failures from propagating through your system.

Site Reliability Engineering

SRE is Google's answer to a question every engineering team eventually faces: how do you balance moving fast with staying reliable? The answer is surprisingly mathematical — and it fundamentally changes how teams make decisions about risk.

The Core Tension SRE Resolves

Every engineering organisation has two groups with opposing incentives. The development team wants to ship features fast — their success is measured by new capabilities delivered. The operations team wants stability — their success is measured by uptime. These goals are genuinely in conflict: every deployment is a potential source of outage.

Traditional organisations resolve this tension politically: ops teams slow down releases, devs push back, people argue about "are we stable enough to deploy?" SRE resolves it mathematically with error budgets: a quantitative answer to "how much risk can we afford right now?" that both teams agreed to in advance.

The SLI / SLO / SLA Framework

📏
SLI — Service Level Indicator
A carefully defined measurement of service behaviour. Must be quantitative, measurable, and directly tied to user experience. Example: the fraction of TaskFlow API requests completing successfully in under 500ms.
🎯
SLO — Service Level Objective
An internal target for your SLI over a time window. Example: 99.9% of requests succeed in under 500ms, measured as a rolling 30-day window. This is your promise to yourself.
📜
SLA — Service Level Agreement
A contractual promise to customers with financial penalties for breach. Always set your SLA looser than your SLO — the SLO is your early warning system before you violate the SLA.
💳
Error Budget
100% minus your SLO target. At 99.9% SLO, your monthly error budget is 0.1% of requests × 30 days = 43.8 minutes of total downtime, or equivalent request failures. This budget is spent on deployments, experiments, and incidents.
💡

How error budgets change decisions: If you have 80% of your budget remaining this month, deploying a risky feature is a reasonable bet. If you've already burned 95% of your budget, you should stop new deployments and focus entirely on stability until the window resets. The budget makes "should we deploy?" a data-driven question, not a political one.

Defining SLIs and SLOs for TaskFlow

Bad SLIs: things that are easy to measure but don't correlate with user experience. ("CPU utilisation" — the server could be at 0% CPU and users still can't create tasks.) Good SLIs: things that are only good when the user is having a good experience.

texttaskflow sli and slo definitions
── Availability SLI ────────────────────────────────────────────────────────
Definition: (successful requests) / (total requests)
Successful:  HTTP 2xx or 3xx responses
Failed:      HTTP 4xx (5xx only — 4xx are client errors, not our fault)
Measurement: Calculated over every 5-minute window using Prometheus

SLO: 99.9% availability over 30-day rolling window
Error budget: 0.1% × 43,200 minutes = 43.2 minutes of downtime/month

── Latency SLI ──────────────────────────────────────────────────────────────
Definition: proportion of requests completing in under 500ms
Measurement: p99 latency from Prometheus histogram

SLO: 95% of requests complete in under 500ms
Error budget: 5% of requests per month may exceed 500ms

── Why these two? ───────────────────────────────────────────────────────────
Availability tells you: "can users reach the service?"
Latency tells you: "is the service responding acceptably?"
Together they cover the two most common user complaints.

Implementing SLO Tracking with Prometheus Rules

yamlk8s/prometheus-slo-rules.yml — apply to your cluster
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: taskflow-slo
  namespace: monitoring
  labels:
    prometheus: kube-prometheus
    role: alert-rules
spec:
  groups:
    - name: taskflow.slo.availability
      rules:
        # Recording rule: calculate availability SLI every 5 minutes
        - record: taskflow:sli:availability5m
          expr: |
            sum(rate(taskflow_http_request_duration_seconds_count{status_code!~"5.."}[5m]))
            /
            sum(rate(taskflow_http_request_duration_seconds_count[5m]))

        # Burn rate: how fast are we consuming the error budget?
        # 1.0 = exactly at the SLO rate (sustainable)
        # >1.0 = burning faster than allowed (will exhaust budget before month end)
        - record: taskflow:slo:burn_rate1h
          expr: |
            (1 - taskflow:sli:availability5m) / (1 - 0.999)

        # Error budget remaining (as a fraction)
        - record: taskflow:slo:budget_remaining30d
          expr: |
            1 - (
              sum_over_time((1 - taskflow:sli:availability5m)[30d:5m])
              / (30 * 24 * 12)  # total 5m windows in 30 days
            ) / (1 - 0.999)

        # Alert: fast burn — losing >5% of monthly budget in 1 hour
        - alert: TaskflowFastBudgetBurn
          expr: taskflow:slo:burn_rate1h > 14.4
          for: 2m
          labels:
            severity: critical
            team: platform
          annotations:
            summary: "TaskFlow burning error budget too fast"
            description: "Burn rate {{ $value }}x — at this rate, monthly budget exhausted in {{ printf \"%.1f\" (720 / $value) }} hours. Check for elevated error rate."
            runbook_url: "https://wiki.taskflow.app/runbooks/high-error-rate"

        # Alert: slow burn — on track to exhaust budget by month end
        - alert: TaskflowSlowBudgetBurn
          expr: taskflow:slo:burn_rate1h > 1 and taskflow:slo:budget_remaining30d < 0.25
          for: 60m
          labels:
            severity: warning
          annotations:
            summary: "TaskFlow error budget below 25%"

Chaos Engineering

We've built a system that is theoretically resilient — multiple replicas, health checks, circuit breakers, rollback capabilities. But theory and practice are different things. Chaos engineering deliberately breaks your system to find out where the theory is wrong before your users discover it at the worst possible time.

Why Deliberate Failure is the Safer Choice

In 2011, Netflix's Chaos Monkey randomly terminated production EC2 instances during business hours. The reasoning was counterintuitive: because failures were frequent and predictable, engineers were forced to build systems resilient enough to handle them. A failure that happens on a Tuesday afternoon when the whole team is watching is infinitely better than a surprise 3am outage that nobody was prepared for.

The alternative — avoiding failures — doesn't eliminate them. It just means when they happen, they're unexpected, the team is unprepared, and the blast radius is unknown. Regular, controlled experiments make failure boring, which is exactly what you want.

The Chaos Engineering Workflow

1

Define Steady State

Before breaking anything, define what "working" looks like quantitatively. For TaskFlow: error rate <0.1%, p99 latency <500ms, all 3 pods Running. This is your baseline — the experiment succeeds if steady state is maintained.

2

Form a Hypothesis

Write it down before running the experiment. Example: "If we terminate one of three TaskFlow pods, the remaining two pods will absorb the traffic within 5 seconds and the error rate will stay below 0.1% throughout." Being explicit forces you to think about what you actually expect.

3

Add a Safety Mechanism

Define a stop condition that automatically halts the experiment if things go worse than expected. For AWS FIS: a CloudWatch alarm on error rate >5%. If the alarm fires, the experiment stops immediately and traffic normalises. Never run chaos without an automatic abort.

4

Run in Staging First

Always run a new experiment in staging before production. The goal isn't to be brave — it's to learn. Learn what breaks in staging, fix it, then graduate to production with confidence.

5

Observe, Learn, Fix

If the system handled it perfectly: great, document it, automate it to run weekly, move on to a harder experiment. If it didn't: you just found a real weakness before it became an incident. Fix the root cause, not just the symptom.

FinOps — Cloud Cost Control

Cloud infrastructure can silently accumulate thousands of dollars of waste every month. FinOps is the practice of bringing financial accountability to cloud spending so every dollar is traceable, justified, and optimised. It starts the day you create an AWS account — not after you get your first shocking bill.

How Cloud Bills Grow Without Anyone Noticing

The cloud pricing model is designed for convenience, not frugality. Resources are easy to create (one CLI command), but difficult to track (distributed across services, regions, and accounts). Common waste patterns:

  • Forgotten resources — an EC2 instance from a testing spike, a NAT gateway in a dev VPC that nobody uses, an RDS instance from a project that was cancelled.
  • Overprovisioned instances — a t3.xlarge running at 3% CPU because someone provisioned it "just in case", when a t3.small would be sufficient.
  • Data transfer costs — moving data between AWS regions or from AWS to the internet is billed by the GB. Multi-region architectures can easily generate thousands of dollars in unnoticed transfer costs.
  • Uncompressed logs — CloudWatch Logs charged by ingestion. An application logging every SQL query at DEBUG level can generate gigabytes per hour.

Platform Engineering

You've built the entire DevOps stack. Now imagine doing all of this for 50 development teams instead of one. Platform engineering is the discipline of building the internal tools and golden paths that let every team practice DevOps without becoming infrastructure experts themselves.

Why Platform Engineering Emerges

At small scale, every developer owns their own infrastructure — they know how to set up a CI pipeline, write a Dockerfile, configure a Kubernetes deployment. This works for a team of 5. It doesn't work for a team of 500.

At scale, the friction compounds: each team reinvents the same Docker best practices, the same CI pipeline structure, the same Terraform modules, the same Grafana dashboards. Security policies get applied inconsistently. New engineers spend their first two weeks just figuring out how to deploy. Platform engineering solves this by treating internal tools as a product — with proper UX, documentation, and support — so development teams can self-serve without needing platform team tickets.

The Golden Path Concept

A golden path is the opinionated, well-supported route to accomplish a common task. It's not the only way — teams can deviate if they have good reasons — but it's the path that works, is maintained, and comes with documentation and support. At Spotify (who coined the term), the golden path for a new service is: use this Backstage template → you get CI/CD, K8s manifests, monitoring, and service catalogue registration automatically.

Consul Architecture — Agents, Servers, and Clients

Consul runs as a cluster of agents in two modes. Server agents form the cluster quorum — you run 3 or 5 of them and they replicate all state using Raft consensus. Client agents run on every node that hosts services. They register local services, forward queries to servers, and cache answers locally for sub-millisecond response. The separation means most queries never leave the local machine.

Step 2 — The Consul Client Module

javascriptsrc/consul.js — everything the app needs to talk to Consul
/**
 * consul.js
 * Wraps the Consul HTTP API so other modules don't deal with raw fetch calls.
 * Three responsibilities:
 *   1. Register this service on startup
 *   2. Deregister on graceful shutdown (so Consul doesn't wait 60s to notice)
 *   3. Discover other services by name when we need to call them
 */

const CONSUL = process.env.CONSUL_HTTP_ADDR || 'http://localhost:8500';

// ── Registration ────────────────────────────────────────────────────────────

/**
 * Register this service instance with Consul.
 * @param {object} opts
 *   name     - logical service name  (e.g. "notifyhub-api")
 *   id       - unique instance id    (e.g. "notifyhub-api-hostname-1")
 *   host     - address Consul should advertise for this instance
 *   port     - TCP port this instance listens on
 *   tags     - array of strings for filtering/routing  (e.g. ["v1","production"])
 *   healthPath - HTTP path Consul polls every 10s     (e.g. "/health")
 */
async function register({ name, id, host, port, tags = [], healthPath = '/health' }) {
  const payload = {
    ID: id,
    Name: name,
    Address: host,
    Port: port,
    Tags: tags,
    // Meta lets you store arbitrary key-value pairs alongside the registration.
    // Useful for version info, environment, or routing hints.
    Meta: {
      version: process.env.APP_VERSION || '1.0.0',
      startedAt: new Date().toISOString()
    },
    Check: {
      // Consul will GET this URL every 10 seconds.
      // If it returns non-2xx or times out, the service is marked "critical"
      // and excluded from service-discovery results automatically.
      HTTP: `http://${host}:${port}${healthPath}`,
      Interval: '10s',
      Timeout: '3s',
      // If the service stays critical for 60 s it is fully removed from
      // the catalog, not just excluded from queries.
      DeregisterCriticalServiceAfter: '60s'
    }
  };

  const res = await fetch(`${CONSUL}/v1/agent/service/register`, {
    method: 'PUT',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify(payload)
  });

  if (!res.ok) throw new Error(`Consul register failed: HTTP ${res.status}`);
  console.log(`[consul] registered "${name}" (${id}) on ${host}:${port}`);
}

/**
 * Tell Consul this instance is going away.
 * Without this, Consul waits 60 s (DeregisterCriticalServiceAfter) before
 * removing it — callers would see failures during that window.
 */
async function deregister(id) {
  await fetch(`${CONSUL}/v1/agent/service/deregister/${id}`, { method: 'PUT' });
  console.log(`[consul] deregistered "${id}"`);
}

// ── Discovery ───────────────────────────────────────────────────────────────

/**
 * Look up healthy instances of a named service.
 * Consul returns only instances that are currently passing their health check.
 * We pick one at random — a simple client-side load balancer.
 *
 * @param  {string} name  logical service name to look up
 * @returns {string}      base URL, e.g. "http://10.0.0.5:4001"
 * @throws  if no healthy instance is registered
 */
async function discover(name) {
  // ?passing=true tells Consul to exclude any instance that is failing its check
  const res = await fetch(`${CONSUL}/v1/health/service/${name}?passing=true`);
  const instances = await res.json();

  if (!instances.length)
    throw new Error(`No healthy instances of "${name}" found in Consul`);

  // Random selection distributes calls across all healthy instances equally
  const pick = instances[Math.floor(Math.random() * instances.length)];
  return `http://${pick.Service.Address}:${pick.Service.Port}`;
}

// ── Key-Value Store ─────────────────────────────────────────────────────────

/**
 * Read a single key from the Consul KV store.
 * Consul stores values as base64 strings — we decode them here.
 * Returns null if the key doesn't exist.
 */
async function kvGet(key) {
  const res = await fetch(`${CONSUL}/v1/kv/${key}`);
  if (res.status === 404) return null;
  const [item] = await res.json();
  return Buffer.from(item.Value, 'base64').toString();
}

/**
 * Write a value to the Consul KV store.
 * The value is stored as-is (Consul will base64-encode it internally).
 */
async function kvPut(key, value) {
  await fetch(`${CONSUL}/v1/kv/${key}`, {
    method: 'PUT',
    body: String(value)
  });
}

module.exports = { register, deregister, discover, kvGet, kvPut };

Step 5 — KV-Driven Config (Live Updates Without Restart)

javascriptsrc/config.js — live config reload from consul kv
/**
 * config.js
 *
 * Provides a simple config cache backed by Consul KV.
 * On every read it checks its local cache first. If stale (older than
 * TTL_MS), it fetches fresh values from Consul.
 *
 * This pattern lets operators change config — rate limits, feature flags,
 * routing rules — without redeploying or restarting services.
 */

const consul   = require('./consul');
const TTL_MS   = 30_000;  // refresh from Consul every 30 seconds
const PREFIX   = 'notifyhub/config/';

// Defaults used when Consul is unavailable or a key hasn't been set yet
const DEFAULTS = {
  rate_limit_per_minute: 60,
  max_message_length:    500,
  slack_channel_prefix:  '#'
};

let cache     = { ...DEFAULTS };
let fetchedAt = 0;   // epoch ms of last successful fetch (0 = never)

async function refresh() {
  try {
    // Read every key under the prefix in one request (?recurse=true)
    const res = await fetch(
      `http://localhost:8500/v1/kv/${PREFIX}?recurse=true`
    );

    if (res.ok) {
      const items = await res.json();
      // items is an array like: [{ Key: "notifyhub/config/rate_limit_per_minute", Value: "NjA=" }]
      // Value is base64 — Buffer.from(..., 'base64').toString() decodes it
      const fresh = { ...DEFAULTS };
      items.forEach(({ Key, Value }) => {
        const shortKey = Key.replace(PREFIX, '');
        const decoded  = Buffer.from(Value, 'base64').toString();
        // Coerce numbers where we expect them, keep strings otherwise
        fresh[shortKey] = isNaN(decoded) ? decoded : Number(decoded);
      });
      cache     = fresh;
      fetchedAt = Date.now();
    }
  } catch (_) {
    // Consul unreachable — keep using the last known values
  }
}

/**
 * get(key) returns the current value for a config key.
 * If the cache is stale it triggers a background refresh,
 * but still returns the current (slightly old) value immediately —
 * this is the "stale-while-revalidate" pattern.
 */
async function get(key) {
  if (Date.now() - fetchedAt > TTL_MS) {
    refresh();  // fire-and-forget, don't await
  }
  return cache[key] ?? DEFAULTS[key];
}

// Pre-warm the cache so the first request doesn't cause a Consul round-trip
refresh();

module.exports = { get };

Infrastructure — Chapter 19

Redpanda — Event Streaming for NotifyHub

When NotifyHub receives a notification request, it shouldn't process it synchronously in the HTTP handler. If the email provider is slow, every HTTP request blocks. If the process crashes mid-delivery, work is lost. Instead, we publish an event to Redpanda. Workers consume it at their own pace, independently retryable, independently scalable.

Why Streaming, Not Direct Calls

The naive approach: NotifyHub's API calls the email provider's API directly inside the HTTP handler and returns 200 OK when the email is sent. This creates two problems: (1) the HTTP response time is now tied to how fast the email provider responds — 2 seconds, 5 seconds, timeout? Your API clients wait for all of it. (2) If the email provider is having an outage, your API starts failing too. A slow dependency becomes your outage.

With Redpanda: the API writes an event ("deliver this email") to a topic and returns 202 Accepted immediately. A separate worker process reads that event, calls the email provider, and retries independently if it fails. Your API is now decoupled from the delivery mechanism. It's fast, it's resilient, and you can scale workers independently from the API.

📨
Topic
Named append-only log. Producers write to it. Consumers read from it at their own pace. Messages are retained for N days regardless of whether they've been read.
🔀
Partition
A topic is split into N parallel shards. More partitions = more consumer parallelism. Messages with the same key always land on the same partition — order is preserved per key.
📍
Offset
The sequential position of a message within a partition. Consumers track their offset — this is how they know where to resume after a restart without re-reading messages already processed.
👥
Consumer Group
Multiple consumers sharing a topic. Redpanda assigns each partition to exactly one group member. Add a consumer and it automatically takes over some partitions — horizontal scaling with no coordination code.

Step 2 — Add the Event Producer to NotifyHub API

javascriptsrc/producer.js — publishes notification events to redpanda
/**
 * producer.js
 *
 * Wraps kafkajs to publish notification events to Redpanda.
 * Redpanda is fully Kafka API-compatible, so this code works with
 * both Redpanda and Apache Kafka without any changes.
 *
 * Design decisions explained inline:
 *   - idempotent: true      prevents duplicate messages on network retry
 *   - acks: 'all'           waits for all replicas to confirm (safe in prod)
 *   - key = channel         ensures all events for same channel stay ordered
 */

const { Kafka } = require('kafkajs');

// Kafka/Redpanda broker address(es) — comma-separated for multi-broker clusters
const BROKERS = (process.env.REDPANDA_BROKERS || 'localhost:9092').split(',');

const kafka = new Kafka({
  clientId: 'notifyhub-api',   // appears in broker logs for debugging
  brokers:  BROKERS,
  // Retry policy: if a publish fails, retry up to 5 times with increasing delay
  // before surfacing the error to the caller
  retry: { initialRetryTime: 100, retries: 5 }
});

const producer = kafka.producer({
  // idempotent = true: Redpanda deduplicates retried messages using a producer ID
  // and sequence number. Without this, a network retry could write the same
  // message twice.
  idempotent: true,
  // -1 (all): don't ack until EVERY in-sync replica has the message on disk.
  // This is the safest option — use 1 (leader only) if you need higher throughput.
  acks: -1
});

let connected = false;

/**
 * Connects the producer to the broker.
 * Safe to call multiple times — no-ops if already connected.
 */
async function connect() {
  if (connected) return;
  await producer.connect();
  connected = true;
  console.log(`[producer] connected to Redpanda @ ${BROKERS}`);
}

/**
 * Publish a notification event to the "notifications" topic.
 *
 * @param {object} notification  The full notification record from the API
 *
 * Key strategy: we use `notification.channel` as the message key.
 * Redpanda hashes the key to pick a partition. All events for the same
 * channel (e.g. all "email" events) land on the same partition, preserving
 * their order. This matters if a worker needs to process email events
 * sequentially (e.g. rate limiting per channel).
 */
async function publish(notification) {
  await connect();

  await producer.send({
    topic: 'notifications',
    messages: [
      {
        key:   notification.channel,   // consistent partition per channel
        value: JSON.stringify(notification),
        // Headers are metadata — not part of the value, not searched,
        // but useful for routing and debugging without deserialising the body
        headers: {
          'event-type':     'notification.queued',
          'source-service': 'notifyhub-api',
          'content-type':   'application/json'
        }
      }
    ]
  });

  console.log(`[producer] published notification #${notification.id} → topic:notifications`);
}

async function disconnect() {
  if (connected) { await producer.disconnect(); connected = false; }
}

module.exports = { publish, disconnect };

// ── Consumer loop ───────────────────────────────────────────────────────────

async function run() {
  await consumer.connect();
  console.log(`[worker-${WORKER_ID}] connected, joining group "notifyhub-delivery-workers"`);

  // Subscribe to the notifications topic.
  // fromBeginning: false → only process NEW messages (not ones already there).
  // Set to true if you want to replay all messages — useful when fixing bugs.
  await consumer.subscribe({ topic: 'notifications', fromBeginning: false });

  await consumer.run({
    // eachMessage is called once per message, sequentially within a partition.
    // The offset is committed (marked as processed) only when this function
    // returns without throwing. If it throws, Redpanda redelivers the message.
    eachMessage: async ({ topic, partition, message }) => {
      const notification = JSON.parse(message.value.toString());

      console.log(`[worker-${WORKER_ID}] received #${notification.id} ` +
        `[partition=${partition} offset=${message.offset}]`);

      const handler = HANDLERS[notification.channel];
      if (!handler) {
        console.error(`  unknown channel: ${notification.channel} — skipping`);
        return;  // returning without throwing commits the offset (message consumed)
      }

      try {
        await handler(notification);
        console.log(`  ✅ delivered #${notification.id}`);
      } catch (err) {
        // Throwing here causes Redpanda to redeliver this message.
        // Be careful — without a retry limit this can loop forever.
        // In production, add a dead-letter mechanism (Chapter 20 shows this).
        console.error(`  ❌ delivery failed #${notification.id}:`, err.message`);
        throw err;
      }
    }
  });
}

// Graceful shutdown: finish the current message, then disconnect cleanly
process.on('SIGTERM', async () => { await consumer.disconnect(); process.exit(0); });
process.on('SIGINT',  async () => { await consumer.disconnect(); process.exit(0); });

run().catch(err => { console.error('Fatal worker error:', err); process.exit(1); });

Infrastructure — Chapter 20

RabbitMQ — Reliable Task Queuing

Redpanda is great for high-throughput event streaming where you want retention and replay. But NotifyHub also needs a dead-letter strategy — when delivery fails after retries, the message must land somewhere safe for investigation, not disappear. RabbitMQ's exchange/queue routing and native dead-letter support are designed exactly for this.

Redpanda vs RabbitMQ — Why Both?

Redpanda (like Kafka) is a log. Messages are appended and retained whether or not anyone has read them. It excels at streaming and replay. RabbitMQ is a broker. It actively routes messages between producers and consumers and removes them once acknowledged. It excels at reliable point-to-point delivery with complex routing rules.

In NotifyHub we use both: Redpanda carries the high-volume event stream from the API to workers. RabbitMQ handles the reliable delivery retry queue — when a worker pulls from Redpanda and the provider call fails, it publishes the failed job to RabbitMQ's retry exchange, which routes it back to a delay queue, and then re-delivers it after a backoff period. Dead-lettered jobs (failed after 3 retries) go to a separate queue for engineers to inspect.

📤
Exchange
Receives messages from producers, applies routing rules, and forwards them to one or more queues. Four types: direct, fanout, topic, headers.
📦
Queue
Holds messages until a consumer picks them up. Durable queues survive broker restart. Messages are removed once a consumer ACKs them.
🔑
Routing Key
A string label on every message. The exchange uses it (with bindings) to decide which queues receive the message.
💀
Dead Letter Exchange
When a message is rejected, expired, or a queue overflows, RabbitMQ forwards it to the DLX. This is where failed jobs land for inspection.
⏰
Message TTL + DLQ Retry
Publish a failed job to a "delay" queue with a TTL. When it expires, the DLX forwards it to the main queue — a retry-after-delay pattern with no timers in code.
✅
Acknowledgement
Consumer must explicitly ACK each message. If the consumer crashes before ACKing, RabbitMQ redelivers to another consumer. No data loss.

Step 2 — Topology Setup and Publisher

javascriptsrc/rabbitmq.js — topology, publisher, and connection manager
/**
 * rabbitmq.js
 *
 * Manages the RabbitMQ connection and declares the full exchange/queue topology.
 * Every service that connects must call setupTopology() first — it is idempotent
 * (safe to call multiple times, only creates resources that don't exist yet).
 *
 * Topology overview:
 *
 *   Producer
 *      │  routing key = "notify.email" / "notify.sms" / "notify.slack"
 *      ▼
 *   notifyhub.events  (topic exchange)
 *      │  binding: notify.email  → queue: notify.email
 *      │  binding: notify.sms   → queue: notify.sms
 *      │  binding: notify.slack → queue: notify.slack
 *      ▼
 *   Per-channel queues  (durable, dead-letter-exchange = notifyhub.dlx)
 *      │  consumer NACKs with requeue=false  OR  message TTL expires
 *      ▼
 *   notifyhub.dlx  (dead-letter exchange, fanout)
 *      │  routes ALL dead letters to:
 *      ▼
 *   notify.dead  (dead-letter queue — engineers inspect this)
 */

const amqp = require('amqplib');

const AMQP_URL = process.env.RABBITMQ_URL || 'amqp://admin:password@localhost:5672';

// Exchange names — define as constants to avoid typos scattered in the code
const EXCHANGE     = 'notifyhub.events';   // main topic exchange
const DLX          = 'notifyhub.dlx';       // dead-letter exchange
const DEAD_QUEUE   = 'notify.dead';          // where permanently failed messages land
const DELAY_QUEUE  = 'notify.delay';         // retry-after-delay holding area

let connection = null;
let channel    = null;

/**
 * Connect to RabbitMQ and declare all exchanges and queues.
 * Returns the confirm channel (used to get publish confirmations).
 */
async function connect() {
  if (channel) return channel;

  connection = await amqp.connect(AMQP_URL);

  // createConfirmChannel: publish() returns a promise that resolves only after
  // the broker has written the message to disk. Slower than a regular channel
  // but guarantees durability — no silent message loss on broker crash.
  channel = await connection.createConfirmChannel();

  await setupTopology(channel);

  // Reconnect automatically if the connection drops
  connection.on('error', () => { channel = null; setTimeout(connect, 5000); });
  connection.on('close', () => { channel = null; setTimeout(connect, 5000); });

  console.log('[rmq] connected and topology declared');
  return channel;
}

/**
 * Declare all exchanges, queues, and bindings.
 * assertExchange/assertQueue: create if absent, verify config if present.
 * This is safe to call on every startup — it's idempotent.
 */
async function setupTopology(ch) {
  // ── Dead-letter infrastructure ─────────────────────────────────────────────
  // Set up DLX FIRST — the per-channel queues reference it.
  // If DLX doesn't exist when we declare those queues, RabbitMQ will error.
  await ch.assertExchange(DLX, 'fanout', { durable: true });
  await ch.assertQueue(DEAD_QUEUE, { durable: true });
  await ch.bindQueue(DEAD_QUEUE, DLX, '');
  // binding key '' matches all messages on a fanout exchange

  // ── Delay queue (retry-after-backoff) ──────────────────────────────────────
  // Messages published here expire after 30 s (x-message-ttl).
  // When they expire, the DLX forwards them — but we bind the delay queue's
  // DLX to the MAIN exchange, so expired messages re-appear in the main queue.
  // This implements "retry after 30 s" with no timers or cron jobs.
  await ch.assertQueue(DELAY_QUEUE, {
    durable: true,
    arguments: {
      'x-dead-letter-exchange': EXCHANGE,    // expired messages go back to main exchange
      'x-message-ttl': 30000                 // 30 second delay
    }
  });

  // ── Main exchange ──────────────────────────────────────────────────────────
  // 'topic' type: routing key "notify.email" matches binding pattern "notify.#"
  // '#' = zero or more dot-separated words (like a wildcard)
  await ch.assertExchange(EXCHANGE, 'topic', { durable: true });

  // ── Per-channel queues ─────────────────────────────────────────────────────
  // Each queue has x-dead-letter-exchange set to DLX.
  // If a consumer NACKs (rejects) a message, it goes to DLX → notify.dead.
  // x-max-length: if the queue grows beyond 10,000 the oldest messages spill to DLX.
  const channels = ['email', 'sms', 'slack'];
  for (const ch_name of channels) {
    const queueName   = `notify.${ch_name}`;
    const routingKey  = `notify.${ch_name}`;

    await ch.assertQueue(queueName, {
      durable: true,
      arguments: {
        'x-dead-letter-exchange': DLX,
        'x-max-length': 10000
      }
    });

    // Bind this queue to the main exchange with an exact routing key match
    await ch.bindQueue(queueName, EXCHANGE, routingKey);
    console.log(`  bound ${EXCHANGE}[${routingKey}] → ${queueName}`);
  }
}

/**
 * Publish a notification to the correct queue via routing key.
 * Uses a Promise wrapper around the confirm channel so we can await delivery.
 *
 * @param {string} channel   "email", "sms", or "slack"
 * @param {object} payload   The notification object to deliver
 * @param {number} retryCount  How many times this has been retried (for DLQ routing)
 */
async function publish(channel, payload, retryCount = 0) {
  const ch         = await connect();
  const routingKey = `notify.${channel}`;

  return new Promise((resolve, reject) => {
    ch.publish(
      EXCHANGE,
      routingKey,
      Buffer.from(JSON.stringify(payload)),
      {
        persistent:  true,              // survive broker restart
        contentType: 'application/json',
        headers: {
          'x-retry-count': retryCount,  // workers read this to decide whether to DLQ
          'x-source': 'notifyhub-api'
        }
      },
      // confirm channel callback: err=null means broker confirmed receipt
      (err) => err ? reject(err) : resolve()
    );
  });
}

/**
 * Publish a failed message to the delay queue for retry after 30 s.
 * Uses the routing key of the original message so it lands back in the
 * correct per-channel queue after the delay expires.
 */
async function publishToDelay(originalRoutingKey, payload, retryCount) {
  const ch = await connect();
  // Publish directly to the delay queue (not via exchange) using the default exchange
  // The delay queue's DLX routes back to EXCHANGE with the stored routing key
  return new Promise((resolve, reject) => {
    ch.sendToQueue(
      DELAY_QUEUE,
      Buffer.from(JSON.stringify(payload)),
      {
        persistent:  true,
        headers: {
          'x-retry-count':         retryCount,
          'x-original-routing-key': originalRoutingKey
        }
      },
      (err) => err ? reject(err) : resolve()
    );
  });
}

module.exports = { connect, publish, publishToDelay, EXCHANGE, DEAD_QUEUE };

/**
 * rmq-worker.js
 *
 * Consumes from all three notification queues (email, sms, slack).
 * On failure: retries up to MAX_RETRIES times (30 s delay between each).
 * After MAX_RETRIES: NACKs the message → it goes to notify.dead for inspection.
 *
 * Run with:  CHANNEL=email node workers/rmq-worker.js
 * Or consume all:  node workers/rmq-worker.js
 */

const amqp = require('amqplib');
const { publishToDelay } = require('../src/rabbitmq');

const AMQP_URL    = process.env.RABBITMQ_URL || 'amqp://admin:password@localhost:5672';
const MAX_RETRIES = 3;
const QUEUES      = process.env.CHANNEL
  ? [`notify.${process.env.CHANNEL}`]
  : ['notify.email', 'notify.sms', 'notify.slack'];

// Simulated delivery — replace with real provider SDKs
const HANDLERS = {
  'notify.email': async (n) => {
    console.log(`  📧 Email → ${n.recipient}: "${n.message}"`);
    if (Math.random() < 0.1) throw new Error('SMTP connection refused'); // 10% failure
  },
  'notify.sms': async (n) => {
    console.log(`  📱 SMS  → ${n.recipient}: "${n.message}"`);
  },
  'notify.slack': async (n) => {
    console.log(`  💬 Slack→ ${n.recipient}: "${n.message}"`);
  }
};

async function startWorker() {
  const conn = await amqp.connect(AMQP_URL);
  const ch   = await conn.createChannel();

  // prefetch(1): don't give this worker a second message until it
  // ACKs (or NACKs) the first. Ensures fair distribution across workers —
  // a slow worker doesn't pile up messages while fast workers sit idle.
  ch.prefetch(1);

  for (const queue of QUEUES) {
    ch.consume(queue, async (msg) => {
      if (!msg) return;  // null = queue was cancelled

      const notification = JSON.parse(msg.content.toString());
      // x-retry-count is set in the headers each time we re-publish to the delay queue
      const retryCount   = msg.properties.headers?.['x-retry-count'] || 0;

      console.log(`[worker] ${queue} — processing #${notification.id} (attempt ${retryCount + 1}/${MAX_RETRIES + 1})`);

      try {
        await HANDLERS[queue](notification);
        // ACK: "I processed this message successfully, remove it from the queue"
        ch.ack(msg);
        console.log(`  ✅ acked #${notification.id}`);
      } catch (err) {
        console.error(`  ❌ failed #${notification.id}: ${err.message}`);

        if (retryCount < MAX_RETRIES) {
          // Retry path: ACK the current message (remove it from this queue),
          // then publish it to the delay queue with an incremented retry count.
          // After 30 s the delay queue's TTL fires and sends it back here.
          ch.ack(msg);
          await publishToDelay(queue, notification, retryCount + 1);
          console.log(`  🔁 scheduled retry ${retryCount + 1} in 30 s`);
        } else {
          // Dead-letter path: we've exhausted retries.
          // NACK with requeue=false sends the message to the DLX → notify.dead.
          // Engineers can inspect notify.dead in the management UI to understand
          // what went wrong and manually re-queue or discard messages.
          ch.nack(msg, false, false);
          console.log(`  ☠️  dead-lettered #${notification.id} after ${MAX_RETRIES} retries`);
        }
      }
    });
    console.log(`[worker] listening on "${queue}"`);
  }
}

process.on('SIGINT',  () => process.exit(0));
process.on('SIGTERM', () => process.exit(0));
startWorker().catch(err => { console.error('Fatal:', err); process.exit(1); });

Apache Kafka — Audit Logs and Analytics

NotifyHub needs a tamper-proof, permanently retained audit trail of every notification ever sent. Redpanda works for real-time delivery, but Kafka — the industry standard for high-throughput event streaming — is the right tool for the audit log because of its ecosystem: Kafka Streams for real-time aggregation, Kafka Connect for sinking to data warehouses, and KSQL for SQL queries over event streams.

Kafka's Architecture — Why It Scales

Three design decisions make Kafka extraordinarily fast:

1

Sequential disk writes

Kafka appends messages to a partition log file sequentially. Sequential disk I/O on modern SSDs approaches network bandwidth speeds. Random reads/writes (like a database index) are 10–100× slower. This is why Kafka can write millions of messages per second.

2

Zero-copy transfer

When a consumer reads messages, Kafka uses the Linux sendfile() syscall to copy data directly from the page cache to the network socket, bypassing application memory entirely. This halves CPU usage for read-heavy workloads.

3

Consumer-controlled offsets

Unlike RabbitMQ (where the broker tracks what's been delivered), in Kafka each consumer group tracks its own offset. This means Kafka can serve the same data to unlimited independent consumer groups simultaneously — a single topic feeds real-time delivery workers, an analytics pipeline, a billing system, and a compliance audit system all at once.

javascriptsrc/audit.js — kafka producer for the audit log
/**
 * audit.js
 *
 * Writes every notification event to the Kafka "audit-log" topic.
 * The audit log is separate from the delivery stream (Redpanda) for two reasons:
 *
 *   1. Different retention: delivery events expire after 7 days; audit log is forever.
 *   2. Different consumers: delivery workers need speed; compliance consumers need
 *      ordering guarantees and replay capability.
 *
 * This is the "dual-write" pattern: one write to the delivery broker (Redpanda)
 * for operational processing, one write to the audit broker (Kafka) for
 * compliance and analytics. Both writes happen in the HTTP handler.
 */

const { Kafka, CompressionTypes } = require('kafkajs');

const KAFKA_BROKERS = (process.env.KAFKA_BROKERS || 'localhost:9093').split(',');

const kafka = new Kafka({
  clientId: 'notifyhub-audit',
  brokers:  KAFKA_BROKERS,
  // Retry aggressively for the audit log — we must not lose compliance records
  retry: { initialRetryTime: 200, retries: 10 }
});

const producer = kafka.producer({
  idempotent: true,    // deduplicates retried messages — critical for an audit log
  acks: -1,            // wait for all replicas to confirm before returning
});

let ready = false;

async function ensureConnected() {
  if (!ready) { await producer.connect(); ready = true; }
}

/**
 * Write an audit event to Kafka.
 *
 * @param {string} eventType  e.g. "notification.queued", "notification.delivered", "notification.failed"
 * @param {object} notification  The full notification object
 * @param {object} extra  Any additional context (error message, worker ID, etc.)
 */
async function writeAudit(eventType, notification, extra = {}) {
  await ensureConnected();

  const auditEvent = {
    eventType,
    notificationId: notification.id,
    channel:        notification.channel,
    recipient:      notification.recipient,
    // Omit message body from audit log if it might contain PII
    // Adjust based on your data protection requirements
    messageLength:  notification.message?.length,
    timestamp:      new Date().toISOString(),
    service:        'notifyhub',
    ...extra
  };

  await producer.send({
    topic: 'audit-log',
    // GZIP compression: reduces storage by ~70% for JSON payloads.
    // CPU cost is negligible for audit logs (low write rate).
    compression: CompressionTypes.GZIP,
    messages: [
      {
        // Key = notificationId: all events for the same notification land on
        // the same partition, preserving chronological order per notification
        key:   String(notification.id),
        value: JSON.stringify(auditEvent)
      }
    ]
  });

  console.log(`[audit] wrote ${eventType} for notification #${notification.id}`);
}

module.exports = { writeAudit };

        const event = JSON.parse(message.value.toString());

        // Update aggregate stats based on event type
        switch (event.eventType) {
          case 'notification.queued':
            stats.totalQueued++;
            if (event.channel in stats.byChannel) stats.byChannel[event.channel]++;
            break;
          case 'notification.delivered': stats.totalDelivered++; break;
          case 'notification.failed':    stats.totalFailed++;    break;
        }

        stats.lastProcessedAt = event.timestamp;

        // resolveOffset: marks this message as processed within the batch.
        // Must be called for each message, not just at the end of the batch.
        resolveOffset(message.offset);

        // heartbeat: tells Kafka "I'm still alive" during long batch processing.
        // Without this, Kafka thinks the consumer died and triggers a rebalance.
        await heartbeat();
      }

      // Commit offsets after the entire batch is processed — not per-message.
      // If we crash mid-batch, we'll reprocess that batch on restart (at-least-once).
      await commitOffsetsIfNecessary();
    }
  });
}

// Expose a lightweight HTTP server so you can query stats with curl
const httpServer = http.createServer((req, res) => {
  if (req.url === '/stats') {
    res.writeHead(200, { 'Content-Type': 'application/json' });
    res.end(JSON.stringify(stats, null, 2));
  } else {
    res.writeHead(404); res.end();
  }
});

run().catch(err => { console.error('Fatal:', err); process.exit(1); });

Redis — Caching, Rate Limiting, and Sessions

NotifyHub's GET /notify/:id status endpoint is called frequently by clients polling for delivery confirmation. Every call currently hits the in-memory Map — fast enough now, but won't survive a process restart or horizontal scaling. Redis gives us a shared, persistent, sub-millisecond store accessible by every API instance simultaneously.

What Redis Is and Why It's Fast

Redis is an in-memory data structure server. "In-memory" is the key — data lives in RAM, not on disk. A Redis GET takes 0.1–0.5ms. A PostgreSQL query on the same data takes 5–50ms. The difference is 10–500×. For frequently-read, slowly-changing data (notification status, user sessions, rate limit counters), that difference is transformative.

Redis is not a cache-only tool. It has six primary data structures, each designed for a different access pattern:

📝
String
Any binary value up to 512 MB. Atomic counters via INCR. Used for: cached responses, session tokens, feature flags, counters.
🗃️
Hash
Map of field → value, like a flat object. Read/write individual fields without deserialising the whole object. Used for: user profiles, notification records.
📑
List
Ordered linked list. O(1) push/pop from both ends. Used for: activity feeds, recent items, lightweight task queues.
🔵
Set
Unordered unique collection. O(1) membership test. Used for: deduplication, tags, unique visitors today.
🏆
Sorted Set
Set where each member has a numeric score. Efficient range queries. Used for: leaderboards, rate limiting with sliding windows, scheduled jobs.
📡
Pub/Sub
Publish to named channels; subscribers receive messages in real time. Used for: live dashboard updates, cache invalidation across servers.

javascriptsrc/store.js — redis-backed notification store
/**
 * store.js
 *
 * Replaces the in-memory Map from Chapter 18 with a Redis Hash store.
 * Each notification is stored as a Redis Hash under the key "notif:{id}".
 * Using a Hash (instead of a JSON string) lets us update individual
 * fields (e.g. just the "status") without reading and rewriting the whole object.
 *
 * Key design choices:
 *   - TTL of 7 days: notification status is only useful for a week
 *   - Graceful degradation: if Redis is down, fall back to in-memory Map
 *   - HSET for partial updates: updating status doesn't overwrite other fields
 */

const Redis = require('ioredis');

const redis = new Redis({
  host:     process.env.REDIS_HOST || 'localhost',
  port:     parseInt(process.env.REDIS_PORT) || 6379',
  password: process.env.REDIS_PASSWORD || undefined,
  // retryStrategy: called with number of consecutive failures.
  // Returns ms to wait before next attempt, or null to stop retrying.
  // Math.min caps the delay at 3 seconds so we don't wait forever.
  retryStrategy: (times) => Math.min(times * 200, 3000),
  // Keep commands queued while Redis is reconnecting, up to 100 commands
  maxRetriesPerRequest: null
});

redis.on('error',   (err) => console.warn(`[redis] ${err.message}`));
redis.on('connect', ()    => console.log('[redis] connected'));

const TTL_SECONDS = 7 * 24 * 60 * 60;  // 7 days

/**
 * Save a notification to Redis as a Hash.
 * HSET stores each field separately — no JSON serialisation needed.
 * EXPIRE sets the TTL so old records are cleaned up automatically.
 */
async function save(notification) {
  const key = `notif:${notification.id}`;

  // HSET accepts alternating field/value pairs.
  // We flatten the object into [field, value, field, value, ...]
  await redis.hset(key, ...Object.entries(notification).flat());

  // Always set a TTL — keys without TTL accumulate forever and eventually
  // fill memory. Redis will evict them automatically when it hits maxmemory,
  // but that causes unpredictable behaviour. Explicit TTLs are safer.
  await redis.expire(key, TTL_SECONDS);

  return notification;
}

/**
 * Retrieve a notification by ID.
 * HGETALL returns all fields of the Hash as a plain object.
 * Returns null if the key doesn't exist (expired or never created).
 */
async function findById(id) {
  const key  = `notif:${id}`;
  const data = await redis.hgetall(key);

  // hgetall returns {} for a missing key — check for at least one field
  if (!data || !data.id) return null;

  // Redis stores everything as strings — coerce types back
  return { ...data, id: parseInt(data.id) };
}

/**
 * Update a single field on a notification without touching others.
 * This is the advantage of Hash over JSON String — a HSET on one field
 * is atomic and doesn't require a read-modify-write cycle.
 */
async function updateStatus(id, status, extra = {}) {
  const key = `notif:${id}`;
  await redis.hset(key, 'status', status, ...Object.entries(extra).flat());
  return findById(id);
}

module.exports = { save, findById, updateStatus, redis };

Step 3 — Rate Limiting With Redis

javascriptsrc/ratelimit.js — fixed-window rate limiter using atomic incr
/**
 * ratelimit.js
 *
 * Limits how many notifications a client can queue per minute.
 * Uses Redis INCR + EXPIRE for a fixed-window counter.
 *
 * Why Redis for rate limiting (not in-memory)?
 * With multiple API instances, an in-memory counter only knows about
 * the requests it personally received. A client hitting 3 instances
 * with 20 req/min each gets 60 req/min total — 3× your limit.
 * Redis provides a single counter shared across all instances.
 *
 * INCR is atomic in Redis — no two increments can interleave,
 * so there are no race conditions without needing locks.
 */

const { redis } = require('./store');

/**
 * Check and increment the rate limit counter for an identifier.
 *
 * @param {string} identifier   Usually IP address, or user ID for auth'd requests
 * @param {number} limit        Max allowed requests in the window
 * @param {number} windowSecs   Window size in seconds (default 60)
 * @returns {{ allowed: boolean, remaining: number, resetAt: Date }}
 */
async function checkLimit(identifier, limit = 60, windowSecs = 60) {
  const key = `ratelimit:${identifier}`;

  // Pipeline executes both commands in a single round-trip to Redis.
  // Without a pipeline we'd need two round-trips (INCR, then TTL).
  // The pipeline returns an array of [error, result] pairs.
  const [[, count], [, ttl]] = await redis.pipeline()
    .incr(key)
    .ttl(key)
    .exec();

  if (count === 1) {
    // First request in this window — set expiry.
    // We check count === 1 to avoid resetting the TTL on every request.
    // If we called EXPIRE unconditionally, a burst of requests would keep
    // extending the window and the limit would never reset.
    await redis.expire(key, windowSecs);
  }

  const remaining = Math.max(0, limit - count);
  const resetAt   = new Date(Date.now() + (ttl > 0 ? ttl : windowSecs) * 1000);

  return { allowed: count <= limit, remaining, resetAt, count };
}

/**
 * Express middleware factory.
 * Usage: app.use('/notify', rateLimitMiddleware(100, 60))
 *        → 100 requests per minute per IP
 */
function rateLimitMiddleware(limit = 60, windowSecs = 60) {
  return async (req, res, next) => {
    // X-Forwarded-For is set by load balancers — use it if present,
    // otherwise fall back to the direct connection IP
    const ip     = req.headers['x-forwarded-for'] || req.socket.remoteAddress;
    const result = await checkLimit(ip, limit, windowSecs);

    // Standard rate-limit headers — clients use these to implement backoff
    res.setHeader('X-RateLimit-Limit',     limit);
    res.setHeader('X-RateLimit-Remaining', result.remaining);
    res.setHeader('X-RateLimit-Reset',     result.resetAt.toISOString());

    if (!result.allowed) {
      return res.status(429).json({
        error:      'Rate limit exceeded',
        retryAfter: result.resetAt,
        limit,
        windowSecs
      });
    }
    next();
  };
}

module.exports = { checkLimit, rateLimitMiddleware };

javascriptsrc/logger.js — structured json logger with logstash transport
/**
 * logger.js
 *
 * Creates a Winston logger that writes JSON to two outputs:
 *   1. Console (always) — visible in docker logs / terminal
 *   2. Logstash TCP (when LOGSTASH_HOST is set) — ships to ELK Stack
 *
 * Why structured JSON instead of printf-style strings?
 *   - Every field is queryable in Kibana: "show me all requests where statusCode=404"
 *   - Grep works on strings; structured logs work with analytics tools
 *   - Adding a field costs nothing; removing it from grep is impossible
 */

const winston = require('winston');
const net     = require('net');

// ── Custom Logstash TCP Transport ───────────────────────────────────────────

/**
 * Sends each log line as a JSON string over TCP to Logstash.
 * Creates a new TCP connection per log entry — simple and stateless.
 * In high-throughput production use, replace with a persistent connection pool.
 */
class LogstashTransport extends winston.Transport {
  constructor(opts = {}) {
    super(opts);
    this.host = opts.host || 'localhost';
    this.port = opts.port || 5000;
  }

  log(info, callback) {
    // Emit 'logged' immediately so Winston doesn't wait for the TCP write
    setImmediate(() => this.emit('logged', info));

    const client = net.createConnection({ host: this.host, port: this.port });

    // Write the JSON log line followed by a newline (json_lines codec expects \n)
    client.write(JSON.stringify(info) + '\n');
    client.end();

    // Silently ignore errors — if Logstash is down, logs still go to console
    client.on('error', () => {});

    callback();
  }
}

// ── Build the logger ─────────────────────────────────────────────────────────

const transports = [
  // Console transport: always active for local development and docker logs
  new winston.transports.Console({
    format: winston.format.combine(
      winston.format.colorize(),   // adds colour in terminal
      winston.format.simple()      // "level: message" in terminal
    )
  })
];

// Add Logstash transport when LOGSTASH_HOST is set (non-local environments)
if (process.env.LOGSTASH_HOST) {
  transports.push(new LogstashTransport({
    host: process.env.LOGSTASH_HOST,
    port: parseInt(process.env.LOGSTASH_PORT) || 5000
  }));
  console.log(`[logger] shipping to Logstash @ ${process.env.LOGSTASH_HOST}:${process.env.LOGSTASH_PORT || 5000}`);
}

const logger = winston.createLogger({
  level: process.env.LOG_LEVEL || 'info',
  // JSON format for all transports — Logstash and Elasticsearch expect JSON

Step 4 — Request Logging Middleware

javascriptsrc/app.js — structured request logging middleware
const logger = require('./logger');

/**
 * Request logging middleware.
 * Logs every HTTP request with timing information after the response is sent.
 * We log AFTER the response (on the 'finish' event) so we know the status code.
 *
 * Fields logged:
 *   method, path, statusCode, durationMs — standard HTTP access log fields
 *   ip — for rate limit debugging and security analysis
 * Fields intentionally NOT logged:
 *   request body — may contain sensitive data (PII, passwords, notification content)
 *   query strings — may contain tokens
 */
app.use((req, res, next) => {
  const startedAt = Date.now();

  // res.on('finish') fires when the response has been fully sent to the client
  res.on('finish', () => {
    const durationMs = Date.now() - startedAt;

    // Use different log levels based on status code:
    //   info  for 2xx/3xx — normal operations
    //   warn  for 4xx    — client errors (may indicate abuse or bugs)
    //   error for 5xx    — server errors (always actionable)
    const level = res.statusCode >= 500 ? 'error'
                : res.statusCode >= 400 ? 'warn'
                : 'info';

    logger[level]('http request', {
      method:     req.method,
      path:       req.path,
      statusCode: res.statusCode,
      durationMs,
      ip: req.headers['x-forwarded-for'] || req.socket.remoteAddress
    });
  });

  next();
});

/**
 * Global error handler.
 * Catches any error thrown inside route handlers that wasn't caught locally.
 * Logs with full stack trace and returns a generic 500 to the client.
 * Four-argument signature tells Express this is an error handler.
 */
app.use((err, req, res, next) => {
  logger.error('unhandled error', {
    error:   err.message,
    stack:   err.stack,
    method:  req.method,
    path:    req.path
  });
  res.status(500).json({ error: 'Internal server error' });
});

# Create an ILM policy that:
# hot phase:    receive writes, rollover when index hits 10 GB or 1 day old
# warm phase:   stop receiving writes, optimise for search (force merge)
# delete phase: delete the index after 30 days total age
# Without ILM, Elasticsearch indexes grow forever and fill your disk.

  -H "Content-Type: application/json" \
  -d '{
    "policy": {
      "phases": {
        "hot": {
          "min_age": "0ms",
          "actions": {
            "rollover": {
              "max_size":  "10gb",
              "max_age":   "1d"
            }
          }
        },
        "warm": {
          "min_age": "1d",
          "actions": {
            "forcemerge": { "max_num_segments": 1 }
          }
        },
        "delete": {

NotifyHub — The Full Stack Running Together

NotifyHub is now a complete, production-pattern notification service. Here's the full flow when you POST to /notify:

1

Consul registers the API on startup

Other services discover it by name. Live config (rate limits, feature flags) is read from the Consul KV store without restarts.

2

Rate limiter checks the Redis counter

Atomic INCR across all API instances ensures the limit is shared. The 101st request gets a 429 with retry-after headers.

3

Notification is saved to Redis

Stored as a Hash with 7-day TTL. Any API instance can read it. Process restarts don't lose state.

4

Event published to Redpanda (delivery stream)

Workers consume from the notifications topic. Scale to 3 workers and all 3 partitions are consumed in parallel.

5

Event published to Kafka (audit log)

Permanently retained, compressed, ordered by notification ID. Analytics consumer replays from the beginning to rebuild stats after restarts.

6

If delivery fails, RabbitMQ handles retries

Worker NACKs the message → delay queue holds it for 30 s → re-delivered to main queue. After 3 failures → dead-letter queue for inspection.

7

Every log line ships to Logstash → Elasticsearch → Kibana

Search all services in one place. Build dashboards. Alert on error rate spikes. ILM auto-deletes logs after 30 days.
