Chapter 01 · React Fundamentals

JSX & The Virtual DOM

Before writing a single line of code, let's understand what React actually is and the ingenious trick it uses — the Virtual DOM — to make UIs fast and predictable.

What is React?

React is a JavaScript library for building user interfaces, created by Facebook (now Meta) in 2013. React's core insight is deceptively simple but powerful: describe what the UI should look like for any given state, and React will efficiently update the DOM to match.

Unlike jQuery-style imperative code where you manually find and mutate elements, React is declarative. You describe the desired result; React figures out the minimum work to get there.

💡 Declarative vs Imperative

Imperative (jQuery): "Find the button. Remove class 'inactive'. Add class 'active'. Change text to 'Loaded'."

Declarative (React): "When isLoaded is true, render a button with class 'active' and text 'Loaded'."

The Virtual DOM

Directly manipulating the browser's real DOM is slow — every change can trigger expensive layout recalculations and repaints. React solves this with a Virtual DOM: a lightweight JavaScript copy of the real DOM, kept entirely in memory.

When your state changes, React runs through this cycle:

  1. Creates a new Virtual DOM tree reflecting the new state
  2. Diffs the new tree against the previous one ("reconciliation")
  3. Calculates the minimum set of changes needed
  4. Applies only those changes to the real DOM in one batch ("committing")

What is JSX?

JSX (JavaScript XML) is a syntax extension that lets you write HTML-like markup directly inside JavaScript. It's not a template language — Babel compiles it down to regular React.createElement() function calls at build time.

Without JSX vs With JSX
JSX
// Without JSX — what React actually runs under the hood
const element = React.createElement(
  'h1',
  { className: 'title', id: 'main' },
  'Hello, World!'
);

// With JSX — Babel transforms this into the above
const element = <h1 className="title" id="main">Hello, World!</h1>;

JSX Rules You Must Know

JSX looks like HTML but has important differences. Breaking these rules causes compile errors.

JSX expressions and rules
TSX
const name = "Amara";
const tasks = ["Write docs", "Review PR", "Deploy"];
const isAdmin = true;

const element = (
  <div className="dashboard">  {/* className, NOT class */}

    {/* Curly braces embed any JS expression */}
    <h1>Welcome, {name}!</h1>

    {/* Conditional rendering with && or ternary */}
    {isAdmin && <span className="badge">Admin</span>}
    {isAdmin ? <p>Full access</p> : <p>Limited access</p>}

    {/* Map arrays to JSX elements — always add a unique key */}
    <ul>
      {tasks.map((task, i) => (
        <li key={i}>{task}</li>  {/* key tells React which item changed */}
      ))}
    </ul>

    {/* Inline styles use JS objects with camelCase properties */}
    <p style={{ color: '#f87171', fontSize: '14px', fontWeight: 600 }}>
      {tasks.length} tasks pending
    </p>

    {/* Self-close empty tags — required in JSX */}
    <input type="text" />
    <br />
    <img src="/logo.png" alt="Logo" />
  </div>
);

Fragments — One Root Without Extra Nodes

Every JSX expression must return exactly one root element. When you don't want an extra wrapper <div> in the DOM, use a Fragment.

Fragments
TSX
// ❌ Invalid — two root elements
return (
  <h1>Title</h1>
  <p>Paragraph</p>
);

// ✅ Fragment shorthand — no extra DOM node created
return (
  <>
    <h1>Title</h1>
    <p>Paragraph</p>
  </>
);

// ✅ Named Fragment — required when you need a key prop
import { Fragment } from 'react';
tasks.map((task) => (
  <Fragment key={task.id}>
    <dt>{task.title}</dt>
    <dd>{task.description}</dd>
  </Fragment>
));
✅ Key Takeaways

JSX compiles to React.createElement() calls. The Virtual DOM enables React to batch and minimize real DOM operations. Use className (not class), always self-close empty tags, and expressions inside {}. Fragments let you return multiple elements without extra DOM nodes.

Components & Props

Components are the fundamental building blocks of React. Think of them as custom, reusable HTML elements — each one a self-contained piece of UI with its own logic and appearance.

Functional Components

A React component is simply a JavaScript function that accepts props and returns JSX. The one hard rule: component names must start with a capital letter. This is how React distinguishes them from regular HTML tags like <div>.

Your first component
TSX
// Function declaration style
function TaskCard() {
  return (
    <div className="task-card">
      <h3>Write tests</h3>
      <p>Due: Tomorrow</p>
    </div>
  );
}

// Arrow function style — identical result
const TaskCard = () => (
  <div className="task-card">
    <h3>Write tests</h3>
  </div>
);

// Use it like an HTML tag — self-closing since no children
const app = <TaskCard />;

Props — Passing Data In

Props (short for "properties") are how you pass data into a component, exactly like HTML attributes. Components receive all their props as a single object argument. This is where TypeScript transforms the experience — we define the shape of props with an interface, and get autocomplete, error checking, and self-documenting code for free.

TaskCard.tsx — typed props
TSX
// Step 1: Define the props contract with a TypeScript interface
interface TaskCardProps {
  title: string;
  dueDate: string;
  priority: 'low' | 'medium' | 'high';  // Union type — only these 3 strings
  isCompleted?: boolean;                    // ? makes it optional
  tags?: string[];                           // optional array of strings
}

// Step 2: Destructure props in the function signature
function TaskCard({
  title,
  dueDate,
  priority,
  isCompleted = false,  // default value for optional prop
  tags = [],
}: TaskCardProps) {
  const priorityColor = {
    low: '#34d399',
    medium: '#fbbf24',
    high: '#f87171',
  }[priority];

  return (
    <div className={`task-card ${isCompleted ? 'done' : ''}`}>
      <div className="task-header">
        <h3>{title}</h3>
        <span style={{ color: priorityColor }}>● {priority}</span>
      </div>
      <p>Due: {dueDate}</p>
      {tags.length > 0 && (
        <div className="tags">
          {tags.map((tag) => (
            <span key={tag} className="tag">{tag}</span>
          ))}
        </div>
      )}
    </div>
  );
}

// Step 3: Use it — TypeScript errors if props are wrong or missing
<TaskCard
  title="Write unit tests"
  dueDate="2025-07-01"
  priority="high"              // ❌ 'critical' would be a TS error
  tags={["testing", "backend"]}
/>

The children Prop

The special children prop lets a component wrap arbitrary content — just like HTML nesting. The TypeScript type for anything renderable is ReactNode.

Card.tsx — children pattern
TSX
import { type ReactNode } from 'react';

interface CardProps {
  title: string;
  children: ReactNode;  // string, JSX, array, null — anything renderable
  footer?: ReactNode;
}

function Card({ title, children, footer }: CardProps) {
  return (
    <div className="card">
      <h2 className="card-title">{title}</h2>
      <div className="card-body">{children}</div>
      {footer && <div className="card-footer">{footer}</div>}
    </div>
  );
}

// Everything between the tags becomes 'children'
<Card
  title="My Tasks"
  footer={<button>Add Task</button>}
>
  <TaskCard title="Write docs" dueDate="soon" priority="medium" />
  <TaskCard title="Review PR" dueDate="today" priority="high" />
</Card>

Callback Props — Child → Parent Communication

Props flow one direction only: parent → child. For a child to communicate up, the parent passes a function as a prop, and the child calls it. Never mutate props directly.

Callback props pattern
TSX
interface TaskRowProps {
  id: number;
  title: string;
  onDelete: (id: number) => void;   // callback type annotation
  onToggle: (id: number) => void;
}

function TaskRow({ id, title, onDelete, onToggle }: TaskRowProps) {
  return (
    <div>
      <span>{title}</span>
      {/* Child calls parent's function — the parent handles the state */}
      <button onClick={() => onToggle(id)}>✓ Toggle</button>
      <button onClick={() => onDelete(id)}>✕ Delete</button>
    </div>
  );
}
✅ Key Takeaways

Components are functions returning JSX. Props are typed with TypeScript interfaces — you get autocomplete and compile-time safety. Props flow one way (parent → child); use callback functions for the reverse. ReactNode is the type for children. Optional props use ? and can have defaults.

Chapter 03 · React Fundamentals

State & useState

State is data owned by a component that can change over time, triggering a re-render. It's the engine of interactivity. The useState hook is React's primary tool for managing it.

Props vs State

Props are data passed into a component from outside — read-only, owned by the parent. State is data a component owns and manages internally. When state changes, React re-renders the component automatically.

⚠️ The Golden Rule

Never directly mutate state. Always use the setter function returned by useState. Direct mutation won't trigger a re-render and causes silent, hard-to-debug bugs. state.count++ is wrong. setCount(count + 1) is right.

useState Basics

useState returns a tuple: the current value and a setter function. TypeScript infers the type from the initial value — but you can annotate it explicitly when needed, especially for complex types or when starting with null.

useState patterns
TSX
import { useState } from 'react';

function Counter() {
  // TypeScript infers: count → number, setCount → (n: number) => void
  const [count, setCount] = useState(0);

  // Explicit generics — useful when initial value is null or ambiguous
  const [name, setName] = useState<string>('');
  const [items, setItems] = useState<string[]>([]);
  const [user, setUser] = useState<User | null>(null); // starts null, becomes User

  return (
    <div>
      <p>Count: {count}</p>
      <button onClick={() => setCount(count + 1)}>Increment</button>
      <button onClick={() => setCount(count - 1)}>Decrement</button>
      <button onClick={() => setCount(0)}>Reset</button>
    </div>
  );
}

State with Objects — The Spread Pattern

When state is an object, you must create a new object — spread the existing state and override only the changed fields. React uses shallow reference equality to detect changes; mutating the object in place won't trigger a re-render.

TaskForm.tsx — object state
TSX
interface TaskFormData {
  title: string;
  description: string;
  priority: 'low' | 'medium' | 'high';
  dueDate: string;
}

function NewTaskForm() {
  const [form, setForm] = useState<TaskFormData>({
    title: '',
    description: '',
    priority: 'medium',
    dueDate: '',
  });

  // keyof TaskFormData = 'title' | 'description' | 'priority' | 'dueDate'
  const handleChange = (field: keyof TaskFormData, value: string) => {
    setForm((prev) => ({
      ...prev,        // copy ALL existing fields
      [field]: value, // computed property key — override just this one
    }));
  };

  // ❌ WRONG — mutates existing object, no re-render!
  // form.title = 'new title'; setForm(form);

  return (
    <form>
      <input
        value={form.title}
        onChange={(e) => handleChange('title', e.target.value)}
        placeholder="Task title"
      />
      <select
        value={form.priority}
        onChange={(e) => handleChange('priority', e.target.value)}
      >
        <option value="low">Low</option>
        <option value="medium">Medium</option>
        <option value="high">High</option>
      </select>
    </form>
  );
}

Functional Updates — Avoiding Stale State

When new state depends on old state, always use the functional form: pass a callback to the setter instead of a direct value. This guarantees you're working with the latest state — critical in async callbacks, event handlers, and effects where closures can capture stale values.

TaskList.tsx — functional updates
TSX
interface Task { id: number; title: string; done: boolean }

function TaskList() {
  const [tasks, setTasks] = useState<Task[]>([]);

  // 'prev' is guaranteed to be the LATEST state, not a stale closure
  const addTask = (title: string) => {
    setTasks((prev) => [
      ...prev,
      { id: Date.now(), title, done: false },
    ]);
  };

  const toggleTask = (id: number) => {
    setTasks((prev) =>
      prev.map((t) => t.id === id ? { ...t, done: !t.done } : t)
    );
  };

  const deleteTask = (id: number) => {
    setTasks((prev) => prev.filter((t) => t.id !== id));
  };

  return (
    <>
      <button onClick={() => addTask('New Task')}>+ Add Task</button>
      <ul>
        {tasks.map((task) => (
          <li key={task.id}>
            <span style={{ textDecoration: task.done ? 'line-through' : 'none' }}>
              {task.title}
            </span>
            <button onClick={() => toggleTask(task.id)}>✓</button>
            <button onClick={() => deleteTask(task.id)}>✕</button>
          </li>
        ))}
      </ul>
    </>
  );
}
✅ Key Takeaways

State belongs to the component and triggers re-renders when changed. Never mutate directly — use the setter. For object/array state, always spread and create a new reference. Use the functional form setState(prev => ...) whenever new state depends on previous state.

Effects & useEffect

Effects let you step outside React's pure rendering model to interact with the outside world — fetching data, setting up event listeners, or manipulating the DOM directly.

What is a Side Effect?

React components should be pure functions: same props + state always produces the same JSX. But real apps need to interact with the outside world — APIs, timers, browser APIs. These "side effects" don't belong in the render function. useEffect is React's designated place for them.

The Three Dependency Array Patterns

useEffect timing patterns
TSX
import { useEffect, useState } from 'react';

function Demo() {
  const [count, setCount] = useState(0);

  // 1. No deps array → runs after EVERY render
  useEffect(() => {
    console.log('Component rendered');
  }); // ← no array! Usually not what you want.

  // 2. Empty array → runs ONCE after mount (like componentDidMount)
  useEffect(() => {
    console.log('Component mounted — fetch initial data here');
    return () => {
      console.log('Component unmounted — cleanup here');
    };
  }, []); // ← empty array

  // 3. [count] → runs whenever 'count' changes
  useEffect(() => {
    document.title = `Count: ${count}`;
  }, [count]); // ← re-runs only when count changes
}

Fetching Data — The Full Pattern

The most common effect: fetch data when the component mounts. The key insight is that useEffect's callback cannot be async directly (it would return a Promise, not a cleanup function), so you define an async function inside and call it immediately.

TaskList.tsx — data fetching
TSX
interface Task { id: number; title: string; completed: boolean }

function TaskList() {
  const [tasks, setTasks] = useState<Task[]>([]);
  const [loading, setLoading] = useState(true);
  const [error, setError] = useState<string | null>(null);

  useEffect(() => {
    // AbortController lets us cancel the fetch if the component unmounts
    const controller = new AbortController();

    const fetchTasks = async () => {
      try {
        setLoading(true);
        setError(null);

        const res = await fetch('http://localhost:3001/api/tasks', {
          signal: controller.signal,
        });

        if (!res.ok) throw new Error(`HTTP ${res.status}: ${res.statusText}`);

        const data: Task[] = await res.json();
        setTasks(data);
      } catch (err) {
        if ((err as Error).name !== 'AbortError') {
          setError((err as Error).message);
        }
      } finally {
        setLoading(false);
      }
    };

    fetchTasks();

    // Cleanup: if component unmounts before fetch completes, abort it
    return () => controller.abort();
  }, []); // empty array: run once on mount

  if (loading) return <div className="spinner">Loading...</div>;
  if (error)   return <div className="error">Error: {error}</div>;

  return (
    <ul>
      {tasks.map((t) => (
        <li key={t.id}>{t.completed ? '✅' : '⬜'} {t.title}</li>
      ))}
    </ul>
  );
}

Cleanup Functions

The function you optionally return from useEffect is called the cleanup function. React calls it when the component unmounts, and also before running the effect again (on subsequent runs). Without proper cleanup, you get memory leaks from dangling timers, subscriptions, or WebSocket connections.

Cleanup patterns
TSX
// Timer cleanup
useEffect(() => {
  const id = setInterval(() => setTime(new Date()), 1000);
  return () => clearInterval(id); // stops the clock on unmount
}, []);

// Event listener cleanup
useEffect(() => {
  const handleResize = () => setWidth(window.innerWidth);
  window.addEventListener('resize', handleResize);
  return () => window.removeEventListener('resize', handleResize);
}, []);

// WebSocket cleanup
useEffect(() => {
  const ws = new WebSocket('wss://api.taskvault.dev/live');
  ws.onmessage = (e) => setMessages((prev) => [...prev, e.data]);
  return () => ws.close(); // close connection on unmount
}, []);
⚠️ Missing Dependencies Bug

If your effect uses a variable from the component's scope, it must go in the dependency array. Forgetting this creates "stale closures" — the effect sees an old value. Install the eslint-plugin-react-hooks package; it catches these automatically with the exhaustive-deps rule.

Context & useContext

Context solves "prop drilling" — the pain of passing data through many component layers just to reach a deeply nested child. It's React's built-in mechanism for sharing values that many components need.

The Prop Drilling Problem

Imagine user auth state at the top of your app, needed 5 levels deep. Without Context, every intermediate component must accept and pass along the prop, even if it doesn't use it:

The problem
TSX
// App → Layout → Sidebar → NavMenu → UserAvatar
// Every single component needs user — even those that never USE it
<App user={user} />
  <Layout user={user} />      // doesn't use user, just passes it down
    <Sidebar user={user} />   // same
      <NavMenu user={user} /> // same
        <UserAvatar user={user} /> // finally uses it!

Creating Context — The Full Pattern

The cleanest approach: create the context, a Provider component that manages state, and a custom hook that validates you're inside the Provider.

contexts/AuthContext.tsx
TSX
import { createContext, useContext, useState, type ReactNode } from 'react';

// 1. Define the shape of what the context provides
interface User { id: number; name: string; email: string; role: 'admin' | 'user' }

interface AuthContextType {
  user: User | null;
  isAuthenticated: boolean;
  login: (email: string, password: string) => Promise<void>;
  logout: () => void;
}

// 2. Create context — null initial value, typed explicitly
const AuthContext = createContext<AuthContextType | null>(null);

// 3. Custom hook — throws if used outside Provider (great DX!)
export function useAuth(): AuthContextType {
  const ctx = useContext(AuthContext);
  if (!ctx) throw new Error('useAuth must be used inside <AuthProvider>');
  return ctx;
}

// 4. Provider — owns the state, wraps the tree
export function AuthProvider({ children }: { children: ReactNode }) {
  const [user, setUser] = useState<User | null>(null);

  const login = async (email: string, password: string) => {
    const res = await fetch('/api/auth/login', {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify({ email, password }),
    });
    if (!res.ok) throw new Error('Invalid credentials');
    const data: User = await res.json();
    setUser(data);
  };

  return (
    <AuthContext.Provider value={{ user, isAuthenticated: !!user, login, logout: () => setUser(null) }}>
      {children}
    </AuthContext.Provider>
  );
}

// 5. Consume anywhere in the tree — zero prop drilling!
function UserAvatar() {
  const { user, logout } = useAuth(); // ✅ type-safe, no props needed
  return (
    <div>
      <span>{user?.name}</span>
      <button onClick={logout}>Sign Out</button>
    </div>
  );
}

Providing Context at App Root

main.tsx
TSX
import ReactDOM from 'react-dom/client';
import { AuthProvider } from './contexts/AuthContext';

ReactDOM.createRoot(document.getElementById('root')!).render(
  <AuthProvider>         {/* everything inside can call useAuth() */}
    <App />
  </AuthProvider>
);
⚠️ Context is Not a Redux Replacement

Context re-renders all consumers on every value change. It's ideal for low-frequency data like auth, theme, or locale. For high-frequency updates (search input, real-time data), use Zustand, Jotai, or Redux Toolkit instead.

useRef & DOM Access

useRef creates a mutable container that persists across renders without triggering re-renders. It has two distinct use cases: direct DOM access and storing mutable values that shouldn't cause updates.

Use Case 1 — DOM Element Access

Sometimes you need to imperatively control a DOM element: focus an input, measure dimensions, or integrate a third-party (non-React) library. useRef is the React-sanctioned way to hold a reference to a DOM node.

SearchInput.tsx
TSX
import { useRef, useEffect } from 'react';

function SearchInput() {
  // Tell TypeScript: this ref holds an HTMLInputElement (or null before mount)
  const inputRef = useRef<HTMLInputElement>(null);

  // Auto-focus on mount — needs DOM access, so goes in useEffect
  useEffect(() => {
    inputRef.current?.focus(); // optional chaining: safe if null
  }, []);

  const clearAndFocus = () => {
    if (inputRef.current) {
      inputRef.current.value = '';
      inputRef.current.focus();
    }
  };

  const selectAll = () => inputRef.current?.select();

  return (
    <div>
      {/* The ref prop connects this to inputRef.current */}
      <input ref={inputRef} type="text" placeholder="Search tasks..." />
      <button onClick={clearAndFocus}>Clear</button>
      <button onClick={selectAll}>Select All</button>
    </div>
  );
}

Use Case 2 — Mutable Values Without Re-renders

A ref's .current property can hold any mutable value. Updating it does not trigger a re-render — unlike state. Use this for tracking things like timer IDs, previous values, or render counts.

AutoSave.tsx — debounce with ref
TSX
import { useRef, useState } from 'react';

function AutoSaveEditor() {
  const [content, setContent] = useState('');
  const [status, setStatus] = useState<'idle'|'saving'|'saved'>('idle');

  // Store the timer ID — changing it MUST NOT trigger a re-render
  const timerRef = useRef<ReturnType<typeof setTimeout> | null>(null);
  const renderCount = useRef(0);
  renderCount.current += 1; // increments silently on every render

  const handleChange = (e: React.ChangeEvent<HTMLTextAreaElement>) => {
    setContent(e.target.value);
    setStatus('idle');

    // Debounce: clear old timer, start fresh
    if (timerRef.current) clearTimeout(timerRef.current);

    timerRef.current = setTimeout(async () => {
      setStatus('saving');
      await fetch('/api/draft', { method: 'POST', body: e.target.value });
      setStatus('saved');
    }, 1200); // save 1.2s after last keystroke
  };

  return (
    <div>
      <textarea value={content} onChange={handleChange} />
      <small>
        {status === 'saving' && 'Saving...'}
        {status === 'saved' && '✓ Saved'}
         (render #{renderCount.current})
      </small>
    </div>
  );
}

forwardRef — Exposing a Ref to Parent Components

By default you can't pass a ref prop to a custom component. Wrap it in forwardRef to forward the ref to an internal DOM element. Essential for building reusable input components in design systems.

Input.tsx — forwardRef
TSX
import { forwardRef } from 'react';

interface InputProps extends React.InputHTMLAttributes<HTMLInputElement> {
  label: string;
  error?: string;
}

// forwardRef<RefType, PropsType>
const Input = forwardRef<HTMLInputElement, InputProps>(
  ({ label, error, ...rest }, ref) => (
    <div className="field">
      <label>{label}</label>
      <input ref={ref} className={error ? 'input error' : 'input'} {...rest} />
      {error && <span className="error-msg">{error}</span>}
    </div>
  )
);
Input.displayName = 'Input'; // helps React DevTools show a useful name

// Usage — parent controls focus directly
const titleRef = useRef<HTMLInputElement>(null);
const focusTitle = () => titleRef.current?.focus();
<Input ref={titleRef} label="Task Title" placeholder="What needs doing?" />

Chapter 07 · React Patterns

Custom Hooks

Custom hooks let you extract and share stateful logic across components. They're one of the most powerful React patterns — replacing messy copy-paste with clean, testable, reusable abstractions.

What Makes a Custom Hook?

A custom hook is just a function whose name starts with use that may call other hooks inside. The naming convention tells React (and its linters) to enforce the rules of hooks for this function. No special API, no magic — just a naming convention with powerful implications.

useFetch — Reusable Data Fetching

Instead of copy-pasting the loading/error/data pattern into every component (as we did in Chapter 4), extract it into a hook. Now every component gets data fetching in one line.

hooks/useFetch.ts
TS
import { useState, useEffect, useCallback } from 'react';

// Generic — works for any response type T
function useFetch<T>(url: string) {
  const [data, setData] = useState<T | null>(null);
  const [loading, setLoading] = useState(true);
  const [error, setError] = useState<string | null>(null);
  const [refreshKey, setRefreshKey] = useState(0);

  useEffect(() => {
    const controller = new AbortController();

    (async () => {
      try {
        setLoading(true); setError(null);
        const res = await fetch(url, { signal: controller.signal });
        if (!res.ok) throw new Error(`${res.status} ${res.statusText}`);
        setData(await res.json() as T);
      } catch (e) {
        if ((e as Error).name !== 'AbortError')
          setError((e as Error).message);
      } finally {
        setLoading(false);
      }
    })();

    return () => controller.abort();
  }, [url, refreshKey]);

  // Call this to re-fetch without changing the URL
  const refetch = useCallback(() => setRefreshKey((k) => k + 1), []);

  return { data, loading, error, refetch };
}

  const [storedValue, setStoredValue] = useState<T>(() => {

  }, [key, storedValue]);

}

Performance: memo, useCallback & useMemo

React is fast by default. But for expensive renders, large lists, or heavy computations, three tools help you skip unnecessary work: React.memo, useCallback, and useMemo.

The Re-render Cascade

When a parent re-renders, all its children re-render too by default — even if their props didn't change. For a simple app this is fine. But if a child renders a list of 500 items and an unrelated parent state changes, that's wasted work.

React.memo — Skip Re-renders When Props Are Unchanged

React.memo wraps a component and does a shallow comparison of its props before every render. If nothing changed, React skips the render entirely and reuses the previous output.

TaskRow.tsx — memo
TSX
import { memo } from 'react';

interface TaskRowProps {
  id: number; title: string; completed: boolean;
  onToggle: (id: number) => void;
}

// memo: only re-renders if id, title, completed, or onToggle changes
const TaskRow = memo(({ id, title, completed, onToggle }: TaskRowProps) => {
  console.log(`Rendering: ${title}`); // watch this in DevTools Profiler
  return (
    <div className={`row ${completed ? 'done' : ''}`}>
      <input type="checkbox" checked={completed} onChange={() => onToggle(id)} />
      <span>{title}</span>
    </div>
  );
});
TaskRow.displayName = 'TaskRow';

useCallback — Stabilize Function References

Here's the catch with memo: if you pass a function as a prop, JavaScript creates a new function reference on every render, breaking memo's shallow comparison. useCallback memoizes the function so its reference stays stable.

useReducer & Complex State

When state logic grows complex — many sub-values, many actions, or transitions that depend on each other — useReducer brings order and testability. It's the same pattern Redux is built on, built right into React.

When useState Starts to Hurt

If you have five related useState calls that all update together, or a complex set of actions ("add", "edit", "delete", "reorder", "filter"...), it's time for useReducer. The key benefit: all state transition logic lives in one pure function that's trivially easy to test.

The Reducer Pattern with TypeScript Discriminated Unions

taskReducer.ts
TS
interface Task {
  id: number; title: string; completed: boolean;
  priority: 'low' | 'medium' | 'high';
}

interface TaskState {
  tasks: Task[];
  filter: 'all' | 'active' | 'completed';
  loading: boolean;
  error: string | null;
}

// Discriminated union: every action has a unique 'type' tag
// TypeScript narrows the payload type based on which case we're in
type TaskAction =
  | { type: 'ADD_TASK';    payload: Omit<Task, 'id'> }
  | { type: 'TOGGLE_TASK'; payload: { id: number } }
  | { type: 'DELETE_TASK'; payload: { id: number } }
  | { type: 'SET_FILTER';  payload: TaskState['filter'] }
  | { type: 'LOAD_TASKS';  payload: Task[] }
  | { type: 'SET_ERROR';   payload: string };

const initialState: TaskState = {
  tasks: [], filter: 'all', loading: false, error: null,
};

// Pure function: (state, action) → newState — never mutates state!
function taskReducer(state: TaskState, action: TaskAction): TaskState {
  switch (action.type) {
    case 'ADD_TASK':
      return {
        ...state,
        tasks: [...state.tasks, { ...action.payload, id: Date.now() }],
      };

    case 'TOGGLE_TASK':
      return {
        ...state,
        tasks: state.tasks.map((t) =>
          t.id === action.payload.id ? { ...t, completed: !t.completed } : t
        ),
      };

    case 'DELETE_TASK':
      return { ...state, tasks: state.tasks.filter((t) => t.id !== action.payload.id) };

    case 'SET_FILTER':
      return { ...state, filter: action.payload };

    case 'LOAD_TASKS':
      return { ...state, tasks: action.payload, loading: false, error: null };

    case 'SET_ERROR':
      return { ...state, error: action.payload, loading: false };

    default: {
      // Exhaustiveness check: TypeScript errors if you add an action type
      // to the union but forget to handle it in the switch
      const _never: never = action;
      return state;
    }
  }
}

Error Boundaries

An Error Boundary catches JavaScript errors in its child component tree, logs them, and renders a fallback instead of a blank white screen. They must be class components — one of the few remaining cases where you need them in modern React.

ErrorBoundary.tsx
TSX
import { Component, type ErrorInfo, type ReactNode } from 'react';

interface Props { children: ReactNode; fallback?: ReactNode }
interface State { hasError: boolean; error: Error | null }

class ErrorBoundary extends Component<Props, State> {
  state: State = { hasError: false, error: null };

  // Called when a descendant throws — sets state to show fallback
  static getDerivedStateFromError(error: Error): State {
    return { hasError: true, error };
  }

  // Called for side effects like logging to Sentry/Datadog
  componentDidCatch(error: Error, info: ErrorInfo) {
    console.error('ErrorBoundary caught:', error, info.componentStack);
    // Sentry.captureException(error, { extra: info });
  }

  render() {
    if (this.state.hasError) {
      return this.props.fallback ?? (
        <div role="alert" className="error-fallback">
          <h2>Something went wrong</h2>
          <pre>{this.state.error?.message}</pre>
          <button onClick={() => this.setState({ hasError: false, error: null })}>
            Try Again
          </button>
        </div>
      );
    }
    return this.props.children;
  }
}

// Combine with Suspense for a rock-solid loading + error pattern
function SafeSection({ children }: { children: ReactNode }) {
  return (
    <ErrorBoundary fallback={<p>This section failed to load.</p>}>
      <Suspense fallback={<Spinner />}>
        {children}
      </Suspense>
    </ErrorBoundary>
  );
}

Generics

Generics are TypeScript's way of writing reusable, type-safe code that works across many types. Think of them as type variables — placeholders that get filled in at call time, giving you both flexibility and safety.

The Problem Generics Solve

Without generics, you're forced to choose between writing one function per type (verbose, copy-pasta) or using any (loses all type safety). Generics give you the best of both: write once, work everywhere, still fully typed.

generics-intro.ts
TS
// ❌ Without generics: one function per type

function firstNumber(arr: number[]): number  { return arr[0]; }
function firstTask(arr: Task[]): Task       { return arr[0]; }

// ✅ With generics: T is a type variable, resolved at call time
function first<T>(arr: T[]): T | undefined {
  return arr[0];
}

const s = first(['a', 'b']);   // TypeScript infers T = string → returns string
const n = first([1, 2, 3]);   // infers T = number → returns number
const t = first(taskArray);    // infers T = Task → returns Task

// Multiple type parameters
function zipWith<A, B, C>(as: A[], bs: B[], fn: (a: A, b: B) => C): C[] {
  return as.map((a, i) => fn(a, bs[i]));
}

Union types let a value be one of several types. Type guards are the runtime checks that narrow a union down to a specific type, giving you full type safety inside conditional branches.

Discriminated Unions — The Crown Jewel

A discriminated union is a union where every member has a literal tag field (like kind or type) that uniquely identifies which variant you're dealing with. TypeScript narrows the type automatically in switch/if blocks.

  | { type: 'UPDATE'; id: number; changes: Partial<Task> }
  | { type: 'DELETE'; id: number }
  | { type: 'ASSIGN'; taskId: number; userId: number };

    case 'CREATE':
      // TypeScript knows: action.title and action.priority exist here
      return `Creating "${action.title}" [${action.priority}]`;

    case 'UPDATE':
      // TypeScript knows: action.id and action.changes exist here
      return `Updating task ${action.id}`;

    case 'DELETE':
      return `Deleting task ${action.id}`;

    case 'ASSIGN':
      return `Assigning task ${action.taskId} to user ${action.userId}`;

  return id;                                                              // id is string
}

We're building TaskVault end-to-end: a Node.js/Express API backed by SQLite. We use Knex.js as our query builder — giving us composable, safe SQL with a fluent API, migrations as code, and seeding built in. No raw SQL strings, no ORM magic.

Why Knex over raw SQL?

Raw SQL strings are error-prone and hard to compose. Full ORMs (like Prisma) are great but add complexity. Knex hits the sweet spot: type-safe, composable queries that compile to SQL you can inspect, with built-in migration and seed runners.

Migrations — schema changes as versioned JS files, tracked in a table. Run knex migrate:latest to apply, knex migrate:rollback to undo. Seeds — repeatable data insertion with knex seed:run. Query builder — chainable, SQL-injection-safe queries with full TypeScript support via knex types.

// db.js — singleton Knex instance imported across routes
const knex = require('knex');
const config = require('./knexfile');
module.exports = knex(config.development);

// ─── routes/tasks.js ──────────────────────────────────────────────────────
const express = require('express');
const db      = require('../db');
const router  = express.Router();

// GET /api/tasks — composable filters with Knex query builder
router.get('/', async (req, res) => {
  const { status, priority, project_id } = req.query;

  const query = db('tasks as t')
    .select(
      't.*',
      'u.name as assignee_name',
      'p.name as project_name'
    )
    .leftJoin('users as u',    't.assignee_id', 'u.id')
    .leftJoin('projects as p', 't.project_id',  'p.id')
    .orderBy('t.created_at', 'desc');

  // Conditionally chain filters — only if the query param exists
  if (status)     query.where('t.status', status);
  if (priority)   query.where('t.priority', priority);
  if (project_id) query.where('t.project_id', project_id);

  const tasks = await query;
  res.json(tasks);
});

// POST /api/tasks
router.post('/', async (req, res) => {
  const { title, description, priority = 'medium', project_id, assignee_id, due_date } = req.body;
  if (!title?.trim()) return res.status(400).json({ error: 'title required' });

  const [id] = await db('tasks').insert({
    title: title.trim(), description, priority, project_id, assignee_id, due_date,
  });

  const task = await db('tasks').where({ id }).first();
  res.status(201).json(task);
});

// PATCH /api/tasks/:id — update only provided fields
router.patch('/:id', async (req, res) => {
  const allowed = ['title', 'description', 'status', 'priority', 'assignee_id', 'due_date'];
  const updates = Object.fromEntries(
    Object.entries(req.body).filter(([k]) => allowed.includes(k))
  );

  if (!Object.keys(updates).length)
    return res.status(400).json({ error: 'no valid fields' });

  await db('tasks').where({ id: req.params.id }).update(updates);
  const task = await db('tasks').where({ id: req.params.id }).first();
  task ? res.json(task) : res.status(404).json({ error: 'not found' });
});

// DELETE /api/tasks/:id
router.delete('/:id', async (req, res) => {
  await db('tasks').where({ id: req.params.id }).delete();
  res.status(204).send();
});

module.exports = router;

import { createContext, useContext, useReducer, useEffect, type ReactNode } from 'react';
import { taskApi } from '../api/taskApi';
import type { Task, CreateTaskPayload, UpdateTaskPayload } from '../types';

// State & Action types (from Chapter 9)
interface State {
  tasks: Task[]; filter: 'all'|'todo'|'in_progress'|'done';
  loading: boolean; error: string | null;
}
type Action =
  | { type: 'LOAD';   payload: Task[] }
  | { type: 'ADD';    payload: Task }
  | { type: 'UPDATE'; payload: Task }
  | { type: 'DELETE'; payload: number }
  | { type: 'FILTER'; payload: State['filter'] }
  | { type: 'ERROR';  payload: string };

function reducer(state: State, action: Action): State {
  switch (action.type) {
    case 'LOAD':   return { ...state, tasks: action.payload, loading: false, error: null };
    case 'ADD':    return { ...state, tasks: [action.payload, ...state.tasks] };
    case 'UPDATE': return { ...state, tasks: state.tasks.map((t) => t.id === action.payload.id ? action.payload : t) };
    case 'DELETE': return { ...state, tasks: state.tasks.filter((t) => t.id !== action.payload) };
    case 'FILTER': return { ...state, filter: action.payload };
    case 'ERROR':  return { ...state, error: action.payload, loading: false };
    default: return state;
  }
}

interface ContextValue {
  state: State;
  addTask: (payload: CreateTaskPayload) => Promise<void>;
  updateTask: (id: number, payload: UpdateTaskPayload) => Promise<void>;
  deleteTask: (id: number) => Promise<void>;
  setFilter: (f: State['filter']) => void;
}
const TaskCtx = createContext<ContextValue | null>(null);
export const useTasks = () => {
  const ctx = useContext(TaskCtx);
  if (!ctx) throw new Error('useTasks must be inside TaskProvider');
  return ctx;
};

export function TaskProvider({ children }: { children: ReactNode }) {
  const [state, dispatch] = useReducer(reducer, {
    tasks: [], filter: 'all', loading: true, error: null,
  });

  useEffect(() => {
    taskApi.getAll()
      .then((tasks) => dispatch({ type: 'LOAD', payload: tasks }))
      .catch((e) => dispatch({ type: 'ERROR', payload: e.message }));
  }, []);

  const value: ContextValue = {
    state,
    addTask: async (payload) => {
      const task = await taskApi.create(payload);
      dispatch({ type: 'ADD', payload: task });
    },
    updateTask: async (id, payload) => {
      const task = await taskApi.update(id, payload);
      dispatch({ type: 'UPDATE', payload: task });
    },
    deleteTask: async (id) => {
      await taskApi.delete(id);
      dispatch({ type: 'DELETE', payload: id });
    },
    setFilter: (f) => dispatch({ type: 'FILTER', payload: f }),
  };

  return <TaskCtx.Provider value={value}>{children}</TaskCtx.Provider>;
}

Declaration Files (.d.ts)

Declaration files teach TypeScript about JavaScript code that has no types of its own — third-party libraries, legacy code, or runtime globals. Understanding them makes you dangerous with any library in the ecosystem.

What is a .d.ts file?

A .d.ts file contains only type information — no JavaScript runtime code whatsoever. It's a pure type annotation layer placed alongside (or shipped with) a JS library. TypeScript reads it to understand what that library exports, without needing the source.

📌 Where types come from

Bundled: Modern libraries (axios, zod, react-query) ship their own .d.ts files inside the npm package. DefinitelyTyped: Community-maintained types for libraries that don't — installed as @types/lodash, @types/node, etc. You write them: For internal JS modules, local scripts, or runtime globals injected by your build tool.

Declaring a Module

When you import a JS file and TypeScript complains it "has no declaration file", you write one. The declare module syntax tells TypeScript the shape of what that module exports.

types/legacy-analytics.d.ts
TS
// Imagine this is a legacy JS analytics library with no types
// File: lib/analytics.js (JavaScript, no types)
// export function track(event, props) { ... }
// export const pageView = (url) => { ... }

// You write this declaration file alongside it:
declare module './lib/analytics' {
  interface TrackProps {
    [key: string]: string | number | boolean;
  }

  export function track(event: string, props?: TrackProps): void;
  export function pageView(url: string): void;
  export function identify(userId: string, traits?: TrackProps): void;
}

// Now this works with full type safety:
import { track, pageView } from './lib/analytics';
track('task_created', { priority: 'high', project_id: 3 }); // ✅
track('page_view', { url: {} });  // ❌ Error: object not assignable to string|number|boolean

Module Augmentation

Module augmentation lets you add new properties to existing types from third-party libraries — without modifying their source or forking them. Essential for extending Express, React, or any framework type.

The Problem It Solves

Imagine you add a JWT authentication middleware that attaches a user property to every Express Request. TypeScript doesn't know about it, so every access to req.user is a type error. Module augmentation is the clean fix.

types/express.d.ts — augmenting Express
TS
// Import the module you want to augment (this makes it a module file)
import 'express';

// Re-open the module's namespace and add to its interfaces
declare module 'express' {
  interface Request {
    // Our auth middleware attaches this after JWT verification
    user?: {
      id: number;
      email: string;
      role: 'admin' | 'user';
    };
    // Our request-id middleware
    requestId: string;
  }
}

// Now in any route handler — full type safety, no casting:
const authMiddleware = (req: Request, res: Response, next: NextFunction) => {
  const token = req.headers.authorization?.replace('Bearer ', '');
  if (!token) return res.status(401).json({ error: 'Unauthorized' });
  req.user = verifyJwt(token); // ✅ TypeScript knows req.user exists
  next();
};

app.get('/api/me', authMiddleware, (req, res) => {
  res.json({ id: req.user?.id }); // ✅ no 'Property does not exist' error
});

Type-Level Programming

TypeScript's type system is Turing-complete. You can write logic that executes entirely at compile time — recursive types, variadic tuples, deep inference — building abstractions impossible in plain JS.

Recursive Types

Types can reference themselves, enabling deep structural descriptions like nested trees, JSON, or infinitely nestable configs.

recursive-types.ts
TS
// Any JSON-serializable value — infinitely recursive
type JSONValue =
  | string | number | boolean | null
  | JSONValue[]
  | { [key: string]: JSONValue };

const valid: JSONValue = { a: [1, { b: true, c: ["deep"] }] }; // ✅
const bad:   JSONValue = { fn: () => {} };                   // ❌ functions not JSON

// Deep Partial — makes nested objects optional recursively
type DeepPartial<T> = T extends object
  ? { [K in keyof T]?: DeepPartial<T[K]> }
  : T;

interface Config {
  api:  { url: string; timeout: number; headers: { auth: string } };
  ui:   { theme: 'dark' | 'light'; fontSize: number };
}

// Every nested property is now optional — great for config overrides
const patch: DeepPartial<Config> = { api: { timeout: 5000 } }; // ✅

// Flatten nested dot-path keys — powers typed path selectors
type Paths<T, Prefix extends string = ''> = {
  [K in keyof T & string]:
    T[K] extends object
      ? Paths<T[K], `${Prefix}${K}.`>
      : `${Prefix}${K}`
}[keyof T & string];

type ConfigPaths = Paths<Config>;
// → "api.url" | "api.timeout" | "api.headers.auth" | "ui.theme" | "ui.fontSize"

Variadic Tuple Types

Variadic tuples let you write types for functions that spread and concatenate arrays — previously impossible to type correctly.

variadic-tuples.ts
TS
// Concat two tuples — the spread (...T) in a tuple position is variadic
type Concat<T extends unknown[], U extends unknown[]> = [...T, ...U];

type AB = Concat<[string, number], [boolean, Date]>;
// → [string, number, boolean, Date]

// Prepend an element to a tuple
type Prepend<T extends unknown[], E> = [E, ...T];
type WithId = Prepend<[string, boolean], number>; // [number, string, boolean]

// Fully typed curry — the holy grail of variadic types
function curry<T extends unknown[], R>(fn: (...args: T) => R) {
  return function curried(...args: Partial<T>): R | ((...rest: unknown[]) => R) {
    if (args.length >= fn.length) return fn(...args as T);
    return (...rest: unknown[]) => curried(...args, ...rest);
  };
}

// Typed pipe — composes functions left to right with inference
type Pipe<T extends [(arg: any) => any, ...((arg: any) => any)[]]> =
  T extends [(arg: infer A) => infer B]
    ? (arg: A) => B
    : T extends [(arg: infer A) => infer B, ...(arg: B) => any[]]
      ? (arg: A) => ReturnType<T[number]>
      : never;

Deep infer — Extracting Nested Types

deep-infer.ts
TS
// Extract the resolved value of a Promise chain
type Awaited<T> =
  T extends Promise<infer U>
    ? Awaited<U>   // recurse into nested promises
    : T;

type A = Awaited<Promise<Promise<string>>>; // string — unwraps both layers

// Extract first element of a tuple
type Head<T extends unknown[]> = T extends [infer H, ...unknown[]] ? H : never;
type Tail<T extends unknown[]> = T extends [unknown, ...infer R]    ? R : never;

type H = Head<[string, number, boolean]>; // string
type T = Tail<[string, number, boolean]>; // [number, boolean]

// Typed event emitter — infer handler type from event map
type EventMap = {
  taskCreated: { task: Task };
  taskDeleted: { id: number };
  userLoggedIn: { user: User; timestamp: Date };
};

type EventHandler<K extends keyof EventMap> = (payload: EventMap[K]) => void;

declare function on<K extends keyof EventMap>(event: K, handler: EventHandler<K>): void;

on('taskCreated', ({ task }) => {   // task: Task — inferred! ✅

on('userLoggedIn', ({ user, timestamp }) => { // perfectly typed ✅

Zod: Runtime Validation

TypeScript types vanish at runtime — they're erased by the compiler. Zod bridges that gap: define a schema once, get both a TypeScript type AND a runtime validator. API boundaries, forms, and env vars become bulletproof.

The Core Problem

You annotate const user: User = await res.json() — but TypeScript just trusts you. If the API returns unexpected data, your types are lying. Zod actually checks the shape at runtime and throws a detailed error if it fails.

schemas/task.ts
TS
import { z } from 'zod';

// 1. Define schema — this is the single source of truth
const TaskSchema = z.object({
  id:          z.number().int().positive(),
  title:       z.string().min(1, 'Title required').max(200),
  description: z.string().nullable(),
  status:      z.enum(['todo', 'in_progress', 'done', 'archived']),
  priority:    z.enum(['low', 'medium', 'high']),
  due_date:    z.string().date().nullable(),
  project_id:  z.number().int().positive().nullable(),
  created_at:  z.string().datetime(),
  updated_at:  z.string().datetime(),
});

// 2. Derive the TypeScript type — no duplication!
type Task = z.infer<typeof TaskSchema>;

// 3. Derive input schemas using Zod transforms
const CreateTaskSchema = TaskSchema
  .omit({ id: true, created_at: true, updated_at: true })
  .extend({
    title: z.string().trim().min(1, 'Title required'), // .trim() auto-strips whitespace
  });

const UpdateTaskSchema = CreateTaskSchema.partial(); // all fields optional

type CreateTaskInput = z.infer<typeof CreateTaskSchema>;
type UpdateTaskInput = z.infer<typeof UpdateTaskSchema>;

Key Remapping with as

The as clause inside a mapped type lets you transform key names — rename, filter, or compute them using template literals.

key-remapping.ts
TS
interface Task { id: number; title: string; completed: boolean; due_date: string }

// Prefix every key with "get" + capitalize — builds a getter interface
type Getters<T> = {
  [K in keyof T as `get${Capitalize<string & K>}`]: () => T[K]
};

type TaskGetters = Getters<Task>;
// → { getId(): number; getTitle(): string; getCompleted(): boolean; getDue_date(): string }

// Filter keys by value type — keep only the string-valued properties
type StringKeys<T> = {
  [K in keyof T as T[K] extends string ? K : never]: T[K]
};

type TaskStrings = StringKeys<Task>;
// → { title: string; due_date: string }  (id/completed filtered out)

// Extract only method keys from an object
type MethodKeys<T> = {
  [K in keyof T as T[K] extends Function ? K : never]: T[K]
};

// Rename snake_case to camelCase using template literals + infer
type SnakeToCamel<S extends string> =
  S extends `${infer Head}_${infer Tail}`
    ? `${Head}${Capitalize<SnakeToCamel<Tail>>}`
    : S;

type CamelTask = { [K in keyof Task as SnakeToCamel<string & K>]: Task[K] };
// → { id: number; title: string; completed: boolean; dueDate: string }

Distributive Conditional Types

When the type being checked in a conditional type is a naked type parameter, TypeScript automatically distributes the conditional over each member of a union. This is extremely powerful but catches people off guard.

distributive.ts
TS
// Naked T → distributes over unions automatically
type ToArray<T> = T extends any ? T[] : never;

type A = ToArray<string | number>;
// Distributes as: ToArray<string> | ToArray<number>
// → string[] | number[]  (NOT (string | number)[])

// To PREVENT distribution — wrap T in a tuple:
type ToArrayND<T> = [T] extends [any] ? T[] : never;
type B = ToArrayND<string | number>; // (string | number)[] — no distribution

// Practical: IsUnion — detects if T is a union type
type IsUnion<T, U = T> =
  T extends any
    ? [U] extends [T] ? false : true
    : never;

type C = IsUnion<string | number>; // true
type D = IsUnion<string>;           // false

// UnionToIntersection — transforms A | B | C into A & B & C
// Uses contra-variance of function parameter types
type UnionToIntersection<U> =
  (U extends any ? (x: U) => void : never) extends (x: infer I) => void
    ? I
    : never;

type ABC = UnionToIntersection<{ a: number } | { b: string } | { c: boolean }>;
// → { a: number } & { b: string } & { c: boolean }
✅ Key Takeaways

Key remapping with as lets you transform, filter, or rename keys in mapped types using template literals and never. Distributive conditionals run on each union member separately — wrap in [T] tuples to opt out. These patterns power the internals of libraries like Zod, tRPC, and Prisma.

useQuery — Fetching Data

hooks/useNotes.ts
TSX
import { useQuery, useMutation, useQueryClient } from '@tanstack/react-query';
import axios from 'axios';

interface Note { id: number; title: string; body: string; tags: string[]; updated_at: string }

// Query key factory — centralized, prevents typos and enables targeted invalidation
export const noteKeys = {
  all:    () => ['notes']                    as const,
  list:   (filter?: string) => ['notes', 'list', filter] as const,
  detail: (id: number) => ['notes', 'detail', id] as const,
};

// useQuery: manages loading, error, caching, background refresh automatically
export function useNotes(search = '') {
  return useQuery({
    queryKey: noteKeys.list(search),   // different key = separate cache entry
    queryFn:  async () => {
      const { data } = await axios.get<Note[]>('/api/notes', { params: { search } });
      return data;
    },
    placeholderData: (prev) => prev,    // show old data while new data loads (no flash)
  });
}

export function useNote(id: number) {
  return useQuery({
    queryKey: noteKeys.detail(id),
    queryFn:  () => axios.get<Note>(`/api/notes/${id}`).then((r) => r.data),
    enabled:  id > 0,                  // only fetch when we have a valid id
  });
}

// useMutation: handles POST/PATCH/DELETE with loading state and cache updates
export function useCreateNote() {
  const qc = useQueryClient();

  return useMutation({
    mutationFn: (data: Omit<Note, 'id' | 'updated_at'>) =>
      axios.post<Note>('/api/notes', data).then((r) => r.data),

    onSuccess: (newNote) => {
      // Optimistically add new note to the cache without a refetch
      qc.setQueryData<Note[]>(noteKeys.list(), (old = []) => [newNote, ...old]);
      // Pre-populate the detail cache — navigating to it will be instant
      qc.setQueryData(noteKeys.detail(newNote.id), newNote);
    },
  });
}

export function useDeleteNote() {
  const qc = useQueryClient();
  return useMutation({
    mutationFn: (id: number) => axios.delete(`/api/notes/${id}`),
    onSuccess: (_, id) => {
      // Invalidate all note list queries — triggers a background refetch
      qc.invalidateQueries({ queryKey: noteKeys.all() });
    },
  });
}

Zustand

Zustand is minimal global state — no boilerplate, no providers, no reducers. One function creates a store with state and actions. Any component subscribes with a selector; only that component re-renders when its slice changes.

Why Not Just Context?

Context re-renders all consumers when value changes. For high-frequency state (selected note, sidebar open/closed, editor cursor), that's expensive. Zustand's selector-based subscriptions mean components only re-render when their specific data changes.

Creating a Store

TS

  selectedNoteId: number | null;
  sidebarOpen:    boolean;
  editorMode:     'edit' | 'preview' | 'split';
  theme:          'dark' | 'light';

  // Actions — co-located with state for easy import
  selectNote:    (id: number | null) => void;
  toggleSidebar: () => void;
  setEditorMode: (mode: UIState['editorMode']) => void;
  toggleTheme:   () => void;

  devtools(       // Redux DevTools integration — time-travel debugging

React Hook Form + Zod

React Hook Form handles forms with minimal re-renders using uncontrolled inputs. Paired with Zod via zodResolver, you get schema-driven validation where a single Zod schema is the source of truth for types, validation rules, and error messages.

Why React Hook Form?

Controlled forms (value + onChange on every input) re-render on every keystroke. React Hook Form uses uncontrolled inputs with a ref — the DOM holds the value, React only gets involved on submit or validation. Benchmark: 1,000-field form renders once instead of 1,000 times.

import { useForm, useFieldArray, Controller } from 'react-hook-form';
import { zodResolver } from '@hookform/resolvers/zod';
import { NoteSchema, type NoteFormValues } from '../schemas/note';
import { useCreateNote } from '../hooks/useNotes';

interface Props {
  defaultValues?: Partial<NoteFormValues>;
  onSuccess: () => void;
}

export function NoteForm({ defaultValues, onSuccess }: Props) {
  const createNote = useCreateNote();

  const {
    register,         // connects inputs to RHF (uncontrolled)
    control,          // needed for Controller and useFieldArray
    handleSubmit,     // wraps your onSubmit, handles validation
    formState: { errors, isSubmitting, isDirty },
    reset,
    watch,
  } = useForm<NoteFormValues>({
    resolver:      zodResolver(NoteSchema), // Zod does all validation
    defaultValues: defaultValues ?? { tags: [], pinned: false, color: 'default' },
  });

  // useFieldArray: manages dynamic lists (tags) inside a form
  const { fields, append, remove } = useFieldArray({ control, name: 'tags' });

  const onSubmit = async (data: NoteFormValues) => {
    // data is validated and typed — tags are string[], not FieldArrayWithId
    await createNote.mutateAsync({ ...data, tags: data.tags.map(String) });
    reset();
    onSuccess();
  };

  const watchedColor = watch('color'); // real-time value without re-render overhead

  return (
    <form onSubmit={handleSubmit(onSubmit)}>
      {/* Title */}
      <div>
        <input
          {...register('title')}
          placeholder="Note title"
          className={errors.title ? 'input-error' : 'input'}
        />
        {errors.title && <p className="error">{errors.title.message}</p>}
      </div>

      {/* Body */}
      <textarea {...register('body')} rows={8} placeholder="Write your note..." />
      {errors.body && <p className="error">{errors.body.message}</p>}

      {/* Color picker — Controller wraps non-native inputs */}
      <Controller
        control={control}
        name="color"
        render={({ field }) => (
          <div className="color-picker">
            {(['default', 'red', 'yellow', 'green', 'blue'] as const).map((c) => (
              <button
                key={c} type="button"
                className={field.value === c ? 'active' : ''}
                onClick={() => field.onChange(c)}
                style={{ background: c === 'default' ? '#333' : c }}
              />
            ))}
          </div>
        )}
      />

      {/* Dynamic tag list */}
      <div>
        {fields.map((field, i) => (
          <div key={field.id}>
            <input {...register(`tags.${i}`)} placeholder="Tag name" />
            <button type="button" onClick={() => remove(i)}>✕</button>
          </div>
        ))}
        <button type="button" onClick={() => append('')}>+ Add Tag</button>
        {errors.tags && <p className="error">{errors.tags.message}</p>}
      </div>

      <label><input type="checkbox" {...register('pinned')} /> Pin this note</label>

      <button type="submit" disabled={isSubmitting || !isDirty}>
        {isSubmitting ? 'Saving...' : 'Save Note'}
      </button>
    </form>
  );
}
