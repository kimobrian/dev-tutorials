Introduction to System Design

System design is the discipline of deciding how all the pieces of a software system — servers, databases, caches, networks, and queues — fit together to serve real users reliably, quickly, and at scale. It is the bridge between writing code that works and building software that survives contact with the real world.

Why system design matters

When you write a Ruby script that reads a file and prints output, you do not need to think about system design. The script runs on one machine, handles one task, and either works or it does not. But the moment you build something that other people use over a network — a web app, an API, a data pipeline — you are building a distributed system, and the rules change completely.

Consider a simple scenario: you build a Ruby on Rails application and deploy it to a single server. Ten users sign up and everything is fast. Then the app gets shared widely, and suddenly ten thousand users hit it simultaneously. The server runs out of memory. The database cannot handle that many concurrent connections. Requests start queuing, then timing out. Users see errors. Your app, which worked perfectly at ten users, collapses at ten thousand.

This is not a bug in your code — it is an architectural failure. Fixing it requires thinking at a higher level than any individual function or class. That higher level is system design.

💡
The Core Insight

System design is fundamentally about tradeoffs. A choice that makes your system faster might make it harder to keep data consistent. A choice that improves reliability might increase operational complexity. Understanding these tradeoffs — and choosing the right ones for your specific context and constraints — is the essence of the discipline.

Essential vocabulary

Before going further, it is worth establishing the vocabulary precisely. These terms appear throughout every system design conversation, and using them correctly signals engineering maturity.

Traffic refers to the flow of requests into your system. Engineers talk about traffic in terms of volume (requests per second, or RPS), patterns (steady, bursty, seasonal, unpredictable), and composition (reads vs writes, authenticated vs anonymous). Managing traffic — spreading it across machines, throttling abusive sources, caching responses so the same work is not repeated — is central to almost every system design decision. A system that handles 100 RPS smoothly but falls over at 200 RPS has a traffic management problem, not a code quality problem.

Latency is the time it takes for one request to travel from the client to the server and receive a response, measured in milliseconds. A web page that loads in 150ms feels instant. One that takes 3 seconds feels broken, even if the content is identical. Every architectural layer you add — a load balancer, a cache lookup, a database query, a network hop across a datacenter — contributes latency. Good system design minimises unnecessary latency while adding exactly the layers needed for resilience and scale.

Throughput is the rate at which your system processes work — requests per second, bytes per second, jobs per hour. Latency measures one request; throughput measures the collective capacity. A system with excellent latency but poor throughput serves individual users quickly but cannot serve many of them simultaneously. Both matter, and they are often in tension: optimising for throughput (batching, buffering) can introduce latency, while optimising for latency (processing immediately, skipping queues) can reduce throughput.

Availability is the percentage of time a system is operational and correctly serving requests. It is expressed in "nines" — 99.9% available means about 8.7 hours of downtime per year; 99.999% means about 5 minutes. Achieving high availability requires redundancy at every layer: multiple servers, multiple database replicas, automatic failover, and no single points of failure anywhere in the request path.

Consistency means all nodes in a distributed system agree on the current state of data. If you update your profile photo, a consistent system ensures that every server, in every datacenter, immediately shows your new photo. Maintaining strict consistency across distributed systems is expensive — it requires coordination between nodes that takes time and can fail — which leads directly to the CAP theorem (Chapter 11).

Fault tolerance is a system's ability to continue operating correctly when individual components fail. Hardware dies. Networks drop packets. Processes crash. A fault-tolerant system treats these not as exceptional edge cases but as expected, routine events — and is architected to survive them without user-visible impact.

Your starting point — a real, runnable server

Every large system starts somewhere simple. Below is a minimal Ruby HTTP server you can run right now. It demonstrates the fundamental request-response cycle and, importantly, its most critical limitation: it is single-threaded, meaning it handles exactly one request at a time. All other incoming requests wait in a queue. This is the "Day 1" architecture — the baseline every system begins with and quickly outgrows.

2

3

Run it: ruby server.rb

4

Open your browser and visit http://localhost:3000/ and http://localhost:3000/time. Press Ctrl+C to stop.

Rubyserver.rb
✓ Fully runnable — no gems needed
require 'webrick'

# WEBrick is Ruby's built-in HTTP server — zero gem dependencies.
# It is synchronous and single-threaded by default:
# while processing request A, every other request waits.
# Under real traffic, even 20 concurrent users will feel lag.

server = WEBrick::HTTPServer.new(
  Port: 3000,
  Logger: WEBrick::Log.new($stdout),
  AccessLog: [[$stdout, WEBrick::AccessLog::COMBINED_LOG_FORMAT]]
)

# Route: GET / — the home page
server.mount_proc '/' do |req, res|
  res['Content-Type'] = 'text/html; charset=utf-8'
  res.body = <<~HTML
    <html><body style="font-family:sans-serif;padding:40px;background:#0f1117;color:#e2e8f0">
    <h1 style="color:#4f9cf9">System Design — Day 1 Server</h1>
    <p>Method: <code>#{req.request_method}</code></p>
    <p>Path: <code>#{req.path}</code></p>
    <p>Client IP: <code>#{req.peeraddr[3]}</code></p>
    <p><a href="/time" style="color:#4f9cf9">→ See current server time (JSON)</a></p>
    <p style="color:#8892a4;margin-top:32px">
      Problem: this server handles <strong style="color:#fbbf24">one request at a time</strong>.<br>
      Under real traffic, requests queue up and users see timeouts.
    </p>
    </body></html>
  HTML
end

# Route: GET /time — JSON response with server timestamp
server.mount_proc '/time' do |req, res|
  res['Content-Type'] = 'application/json'
  res.body = %Q({"server_time":"#{Time.now.iso8601}","pid":#{Process.pid}})
end

# Route: GET /slow — simulates an expensive operation (500ms DB query)
server.mount_proc '/slow' do |req, res|
  sleep 0.5   # simulates a slow database query
  res['Content-Type'] = 'application/json'
  res.body = '{"message":"Done. But everyone else waited 500ms for me."}'
end

trap('INT') { server.shutdown }
puts "✓ Server running at http://localhost:3000"
puts "  Try: /, /time, /slow"
puts "  Press Ctrl+C to stop.\n\n"
server.start

This server is the starting point. Every chapter from here adds a piece of the puzzle: how to handle more traffic, how to survive failures, how to keep data consistent across multiple machines. By the end, you will have the vocabulary and mental models to design systems that handle millions of users.

⚠️
Single Point of Failure

A single server is not just a performance bottleneck — it is a single point of failure. If the machine reboots, runs out of memory, or its disk fills up, your entire application goes offline for every user simultaneously. Real production systems are designed so that no single component failure brings everything down.

Scalability

Scalability is a system's ability to handle increased load without requiring a fundamental redesign. It is not the same as performance: a fast system can still be unscalable if performance degrades steeply as users grow. A scalable system maintains acceptable performance as load increases, by adding resources or distributing work more cleverly.

Vertical scaling — scaling up

The simplest approach to handling more traffic is to give your existing server more resources: a faster CPU, more RAM, faster NVMe storage. This is called vertical scaling or "scaling up." It requires zero changes to your application code — you simply upgrade the machine (or resize the cloud instance) and restart.

Vertical scaling works well up to a point and is often the correct first move. It is fast to implement, requires no architectural changes, and can immediately resolve a traffic problem. But it has hard physical limits. The largest available AWS instances today top out around 24 TB of RAM — impressive but finite. More critically, a single powerful machine is still a single point of failure. If it goes down, everything goes down simultaneously. And beyond a certain size, the cost-per-unit-of-capacity starts climbing steeply.

Horizontal scaling — scaling out

Horizontal scaling means adding more machines rather than making one machine bigger. Instead of one powerful server handling all traffic, you run a pool of smaller servers — each handling a portion of the load. A load balancer (Chapter 04) distributes incoming requests across the pool.

The advantages are significant: horizontal scaling is theoretically unlimited (keep adding machines), provides fault tolerance (one server failing does not take down the system), and is usually more cost-effective at large scale than vertical scaling. The requirement it introduces is fundamental: your application must be stateless.

The stateless requirement — the most important concept in this chapter

Stateless means each server can handle any request without needing to know what happened in previous requests from the same user. Consider what breaks without this: a user logs in and their session data is stored in Server A's memory. On their next request, the load balancer sends them to Server B. Server B has no knowledge of the session on Server A. The user appears logged out.

The solution is to move all shared state out of server memory and into an external shared store that every server can access. Redis is the standard choice for sessions. A database holds user data. An object store (S3, GCS) holds files. Now any server can handle any request, and adding more servers is a matter of spinning up a new instance — no code changes, no migration.

⚙ How to run this
1

No gems required. Save as sessions.rb.

2

Run: ruby sessions.rb

3

Observe how the stateful version fails when a different server handles the request, while the stateless version (using a shared temp file as a stand-in for Redis) works regardless of which server processes the request.

Rubysessions.rb
✓ Fully runnable — no gems needed
require 'json'
require 'tmpdir'
require 'securerandom'

# ──────────────────────────────────────────────────────────────────
# STATEFUL server: sessions live in this process's memory.
# Problem: if load balancer routes a user to a DIFFERENT server
# instance, that server has no record of the session. The user
# appears logged out. You cannot horizontally scale this.
# ──────────────────────────────────────────────────────────────────
class StatefulServer
  def initialize(name)
    @name = name
    @sessions = {}   # ← lives only in THIS server's memory
    puts "[#{@name}] Started (stateful — memory sessions)"
  end

  def login(username)
    token = SecureRandom.hex(8)
    @sessions[token] = { username: username, at: Time.now.to_s }
    puts "[#{@name}] LOGIN  #{username} → token:#{token[0,8]}…"
    token
  end

  def authenticate(token)
    session = @sessions[token]
    if session
      puts "[#{@name}] AUTH   ✓ #{session[:username]}"
      session[:username]
    else
      puts "[#{@name}] AUTH   ✗ NOT FOUND — session lives on another server!"
      nil
    end
  end
end

# ──────────────────────────────────────────────────────────────────
# STATELESS server: sessions stored in a shared file (simulating Redis).
# Any server instance can validate any token because they all read
# from the same external store. Adding servers requires zero changes.
# In production: replace File.read/write with redis.get/set calls.
# ──────────────────────────────────────────────────────────────────
class StatelessServer
  SESSION_FILE = File.join(Dir.tmpdir, 'sd_guide_sessions.json')

  def initialize(name)
    @name = name
    File.write(SESSION_FILE, '{}') unless File.exist?(SESSION_FILE)
    puts "[#{@name}] Started (stateless — shared store: #{SESSION_FILE})"
  end

  def login(username)
    token = SecureRandom.hex(8)
    sessions = JSON.parse(File.read(SESSION_FILE))
    sessions[token] = { 'username' => username, 'at' => Time.now.to_s }
    File.write(SESSION_FILE, JSON.generate(sessions))
    puts "[#{@name}] LOGIN  #{username} → token:#{token[0,8]}…"
    token
  end

  def authenticate(token)
    sessions = JSON.parse(File.read(SESSION_FILE))
    session = sessions[token]
    if session
      puts "[#{@name}] AUTH   ✓ #{session['username']}"
      session['username']
    else
      puts "[#{@name}] AUTH   ✗ NOT FOUND"
      nil
    end
  end
end

puts "\n══ STATEFUL DEMO — breaks when load balanced ══"
web1 = StatefulServer.new("web-1")
web2 = StatefulServer.new("web-2")
token = web1.login("amara")         # user hits web-1, session stored in web-1 memory
web1.authenticate(token)             # same server → works
web2.authenticate(token)             # different server → FAILS

puts "\n══ STATELESS DEMO — works with any number of servers ══"
File.delete(StatelessServer::SESSION_FILE) rescue nil
web3 = StatelessServer.new("web-1")
web4 = StatelessServer.new("web-2")
token2 = web3.login("wanjiru")     # logs in via web-1
web3.authenticate(token2)           # web-1 → works
web4.authenticate(token2)           # web-2 → ALSO works (reads shared store)

Measuring scale precisely

Vague claims like "the system is slow" or "we need to scale" are not actionable. Engineers think in measurable quantities. These are the numbers that matter:

MetricDefinitionGood target (web API)
RPSRequests per second — total system throughputVaries enormously by use case
p50 latencyMedian response time — the "typical" user experienceUnder 100ms
p95 latency95th percentile — 19 out of 20 users are fasterUnder 300ms
p99 latency99th percentile — 99 out of 100 users are fasterUnder 500ms
p999 latency99.9th percentile — the "tail" — 1 in 1000 requestsOften 10–100× the median
Error ratePercentage of requests returning 5xx errorsUnder 0.1%
📊
Why p99 matters more than average

An average latency of 40ms sounds excellent. But if your p99 is 5 seconds, 1% of your users — potentially thousands of people per day — experience a broken-feeling product. Optimising for average while ignoring tail latency is one of the most common and costly mistakes in system design. Always instrument and monitor your p95, p99, and p999 percentiles separately.

The Client-Server Model

Almost every system on the internet is built on one pattern: clients make requests, servers fulfil them. Understanding exactly what happens during this exchange — the DNS lookup, TCP handshake, TLS negotiation, HTTP request, server processing, and response — gives you the foundation to understand every optimisation and failure mode that follows.

The full lifecycle of one request

When a user types https://myapp.com/users/42 into a browser, the following sequence unfolds — all before a single pixel is rendered:

DNS resolution: The browser asks a DNS resolver to translate myapp.com into an IP address. DNS is a distributed global database, and this lookup may involve several recursive queries through a hierarchy of DNS servers. It is often cached in the browser, OS, or router — but on a cold first visit it can take 20–100ms. This is why minimising the number of unique domains your page loads resources from matters.

TCP connection: The browser opens a TCP connection to port 443 of the resolved IP address. TCP establishment requires a three-way handshake (SYN, SYN-ACK, ACK) — one round-trip of network latency. On a fast local connection this is imperceptible; between continents it is 100–300ms.

TLS handshake: For HTTPS, the client and server negotiate encryption parameters, exchange certificates, and establish a shared secret key. TLS 1.3 (the current standard) requires one additional round trip. TLS 1.2 required two. These are fixed costs paid once per connection — which is why HTTP/2 and HTTP/3 connection reuse is so valuable.

HTTP request: The browser sends an HTTP request: a method, path, headers (Accept, Authorization, User-Agent, etc.), and optionally a body (for POST/PUT requests).

Server processing: Your application receives the request, authenticates the user, queries the database or cache, applies business logic, and builds a response.

HTTP response: The server sends back a status code, response headers, and the body.

require 'webrick'
require 'net/http'
require 'json'

mode = ARGV.first || 'server'

# ─── SERVER ───────────────────────────────────────────────────────
if mode == 'server'
  USERS = {
    1  => { id: 1,  name: "Amara Osei",    email: "amara@example.com",   role: "admin"  },
    42 => { id: 42, name: "Wanjiru Kamau", email: "wanjiru@example.com", role: "member" },
  }

  server = WEBrick::HTTPServer.new(Port: 4567, AccessLog: [])

  server.mount_proc '/users' do |req, res|
    puts "\n[server] #{req.request_method} #{req.path}"
    puts "[server] Accept: #{req['Accept']}"
    puts "[server] Authorization: #{req['Authorization'] || '(none)'}"

    # Step 1: authenticate
    unless req['Authorization'] == 'Bearer secret'
      res.status = 401
      res['Content-Type'] = 'application/json'
      res['WWW-Authenticate'] = 'Bearer realm="api"'
      res.body = '{"error":"Unauthorized","hint":"Add: Authorization: Bearer secret"}'
      puts "[server] → 401 Unauthorized"
      next
    end

    # Step 2: parse the resource ID from path  /users/42 → 42
    id = req.path.split('/').last.to_i

    # Step 3: look up the resource
    user = USERS[id]
    if user
      res.status = 200
      res['Content-Type'] = 'application/json'
      res['X-Request-ID']  = "req_#{rand(9999)}"
      res.body = JSON.generate(user)
      puts "[server] → 200 OK (#{user[:name]})"
    else
      res.status = 404
      res['Content-Type'] = 'application/json'
      res.body = %Q({"error":"User #{id} not found"})
      puts "[server] → 404 Not Found"
    end
  end

  trap('INT') { server.shutdown }
  puts "Server at http://localhost:4567 — waiting for requests…"
  server.start

# ─── CLIENT ───────────────────────────────────────────────────────
else
  def make_request(label, path, headers = {})
    puts "\n── #{label} ──"
    uri = URI("http://localhost:4567#{path}")
    req = Net::HTTP::Get.new(uri)
    req['Accept'] = 'application/json'
    headers.each { |k, v| req[k] = v }

    Net::HTTP.start(uri.hostname, uri.port, read_timeout: 5) do |http|
      res = http.request(req)
      puts "Status:  #{res.code} #{res.message}"
      puts "Headers: Content-Type=#{res['Content-Type']}"
      body = JSON.parse(res.body) rescue { raw: res.body }
      puts "Body:    #{body.inspect}"
    end
  rescue Errno::ECONNREFUSED
    puts "ERROR: Server not running. Start it first: ruby http_demo.rb server"
  end

  make_request("No auth — should get 401", "/users/42")
  make_request("Valid request — user 42", "/users/42", "Authorization" => "Bearer secret")
  make_request("Valid request — user 1", "/users/1",  "Authorization" => "Bearer secret")
  make_request("Not found — user 999", "/users/999", "Authorization" => "Bearer secret")
end

HTTP methods and their semantics

HTTP methods carry precise semantic meaning that the entire web ecosystem relies on. Caches, load balancers, and browsers all treat different methods differently based on two key properties: safety (does calling this method change anything on the server?) and idempotency (does calling it multiple times have the same effect as calling it once?).

These properties matter for error handling. If a GET request times out, the client can safely retry it — it changes nothing. If a POST request times out, the client does not know whether the server received and processed it before the timeout. Retrying blindly might create a duplicate record. This is why POST is not idempotent and why idempotency keys (a unique client-generated ID sent with the request) are important for APIs that create resources.

GETRetrieve a resource✓ Yes✓ Yes✓ Yes
POSTCreate a new resource✗ No✗ No✗ No
PUTReplace a resource entirely✗ No✓ Yes✗ No
PATCHPartially update a resource✗ No✗ No*✗ No
DELETERemove a resource✗ No✓ Yes✗ No
HEADSame as GET but body omitted✓ Yes✓ Yes✓ Yes

Load Balancing

A load balancer is the traffic director of your system. It accepts all incoming requests at a single stable address and distributes them across a pool of application servers — ensuring no single server is overwhelmed, routing around unhealthy servers automatically, and making it possible to add or remove servers without user-visible interruption.

The problem it solves

The moment you run more than one application server — which you must do for both scalability and availability — you need something to decide which server handles each request. Without a load balancer, clients would need to know individual server addresses directly. Adding a server means updating every client. Removing a server means every client connected to it gets an error. A load balancer gives you a single stable entry point and abstracts the pool completely.

In production, load balancers also terminate TLS (handling the certificate and encryption so your app servers do not have to), strip or add headers, enforce rate limits, and provide a layer for DDoS mitigation. Popular choices include NGINX, HAProxy, and AWS Application Load Balancer.

Balancing algorithms

The algorithm determines which server receives each request. The choice matters: a poor algorithm leads to uneven distribution where some servers are overloaded while others sit mostly idle.

⚙ How to run this
1

No gems needed. Save as load_balancer.rb.

2

Run: ruby load_balancer.rb

3

The simulation distributes 15 requests across 3 servers (one of which is down) using each algorithm. Note how Least Connections prefers the server with fewer active connections.

Rubyload_balancer.rb
✓ Fully runnable — no gems needed
Server = Struct.new(:name, :active_connections, :healthy) do
  def to_s; "#{name}[#{healthy ? 'UP' : 'DOWN'}, conns=#{active_connections}]"; end
end

class LoadBalancer
  def initialize(servers)
    @servers = servers
    @rr_idx  = 0
  end

  def up; @servers.select(&:healthy); end

  # ── Round Robin ──────────────────────────────────────────────────
  # Cycles through healthy servers in order. Fair when all requests
  # take roughly the same time. Simple and very widely used.
  # Weakness: if some requests are much slower (heavy queries, file
  # uploads) one server accumulates slow connections while others
  # stay light — the rotation doesn't account for current load.
  def round_robin
    servers = up
    s = servers[@rr_idx % servers.length]
    @rr_idx += 1
    s
  end

  # ── Least Connections ────────────────────────────────────────────
  # Routes to the server with the fewest currently active connections.
  # Better for long-lived or variable-length requests. A server that
  # finishes requests quickly naturally receives more traffic over time
  # because its connection count drops faster.
  def least_connections
    up.min_by(&:active_connections)
  end

  # ── IP Hash ──────────────────────────────────────────────────────
  # Hashes the client's IP address to always route them to the same
  # server. Guarantees the same client hits the same server — useful
  # for stateful app features that haven't been extracted to shared
  # storage yet (e.g., multi-step file upload in progress).
  # Weakness: if that server goes down, all of that client's sessions
  # are disrupted. Also fails if IPs are behind a NAT (everyone looks
  # like the same IP).
  def ip_hash(client_ip)
    servers = up
    servers[client_ip.hash.abs % servers.length]
  end
end

# ── Setup ─────────────────────────────────────────────────────────
servers = [
  Server.new("web-1", 0,  true),   # up, idle
  Server.new("web-2", 8,  true),   # up, busy with 8 connections
  Server.new("web-3", 0,  false),  # DOWN — should be skipped
]

lb = LoadBalancer.new(servers)

puts "Servers: #{servers.map(&:to_s).join(', ')}"
puts

puts "── Round Robin (15 requests) ──"
15.times { |i| puts "  req #{(i+1).to_s.rjust(2)} → #{lb.round_robin.name}" }

puts "\n── Least Connections (15 requests) ──"
lb2 = LoadBalancer.new(servers.map { |s| Server.new(s.name, s.active_connections, s.healthy) })
15.times do |i|
  s = lb2.least_connections
  s.active_connections += 1
  puts "  req #{(i+1).to_s.rjust(2)} → #{s.name} (conns now #{s.active_connections})"
  s.active_connections -= 1 if rand > 0.6   # randomly simulate connections closing
end

puts "\n── IP Hash (same client always same server) ──"
clients = { "192.168.1.1" => 3, "10.0.0.5" => 2, "172.16.0.8" => 2 }
clients.each do |ip, count|
  count.times do |i|
    s = lb.ip_hash(ip)
    puts "  #{ip} req ##{i+1} → #{s.name} #{i > 0 ? '(same server ✓)' : ''}"
  end
end

Health checks

A load balancer is only as useful as its knowledge of which servers are actually alive. It discovers this through health checks: periodic probes sent to each server on a configurable interval (typically every 5–30 seconds). If a server fails to respond correctly within a timeout, it is marked unhealthy and removed from the rotation. When it recovers and passes health checks again, it is re-added automatically.

There are two types. A shallow health check simply opens a TCP connection to confirm the server process is running. A deep health check calls a dedicated HTTP endpoint (conventionally /health or /healthz) that your application implements. That endpoint verifies not just that the server is up, but that it can connect to the database, reach Redis, and perform its core functions. A server that is running but whose database connection pool is exhausted should fail its deep health check and be removed from rotation.

Caching

Caching is one of the highest-impact optimisations available to any system. The core idea: if you have already computed something expensive — a database query, an external API call, a complex calculation — save the result so you can return it instantly next time. Done well, caching can reduce database load by 90% and cut response times from hundreds of milliseconds to under one millisecond.

Where caches live in a system

There are multiple layers in the request lifecycle where caching can intercept a request. Each layer catches requests before they reach the next, more expensive layer. A CDN catching a request means it never reaches your load balancer. Your application cache returning data means it never reaches the database. Understanding all the layers helps you choose the right cache for each use case.

Cache-Aside — the most widely used pattern

In cache-aside (also called lazy loading), the application manages the cache explicitly. On a read: check the cache; if present, return it (cache hit); if absent (cache miss), fetch from the database, store in the cache with a TTL, and return the value. The cache is populated lazily — only with data that is actually requested — which means it naturally contains the hottest, most-frequently-accessed data.

    DB[id]&.dup
  end
end

# ── In-memory cache (simulates Redis) ────────────────────────────
class Cache
  def initialize
    @store  = {}
    @expiry = {}
    @hits   = 0
    @misses = 0
  end

  def get(key)
    if @expiry[key] && Time.now > @expiry[key]
      @store.delete(key); @expiry.delete(key)
      return nil
    end
    @store[key]
  end

  def set(key, value, ttl:)
    @store[key]  = value
    @expiry[key] = Time.now + ttl
    value
  end

  def del(key) = @store.delete(key) && @expiry.delete(key)
  def hit! = (@hits += 1)
  def miss! = (@misses += 1)
  def stats = { hits: @hits, misses: @misses, hit_rate: @hits.to_f / [@hits + @misses, 1].max }
end

# ── UserService — cache-aside pattern ────────────────────────────
class UserService
  USER_TTL = 300   # cache user records for 5 minutes

  def initialize
    @db    = Database.new
    @cache = Cache.new
  end

  def find(id)
    key    = "user:#{id}"
    cached = @cache.get(key)

    if cached
      @cache.hit!
      puts "  ⚡ CACHE HIT  user:#{id}"
      return cached
    end

    @cache.miss!
    puts "  🐢 CACHE MISS user:#{id} — fetching from DB…"
    user = @db.find_user(id)
    return nil unless user

    @cache.set(key, user, ttl: USER_TTL)
    user
  end

  def update(id, attrs)
    # Write-through: update DB then immediately update cache
    user = @db.find_user(id).merge(attrs)
    # In production: user = User.find(id).update!(attrs)
    @cache.set("user:#{id}", user, ttl: USER_TTL)
    puts "  ✎ Updated user:#{id} in DB and cache"
    user
  end

  def delete(id)
    # Must invalidate cache entry to prevent stale reads
    @cache.del("user:#{id}")
    puts "  ✗ Invalidated cache for user:#{id}"
  end

  def stats = @cache.stats
end

Cache eviction and TTL

Caches have finite memory. When a cache is full and a new entry must be stored, something must be evicted. The eviction policy determines what gets removed. The most common policy in Redis is LRU (Least Recently Used) — the entry that has not been accessed for the longest time is evicted first. LFU (Least Frequently Used) is better when access patterns are stable: things accessed many times should stay even if not accessed recently.

TTL (Time to Live) is a separate mechanism: it automatically expires entries after a fixed duration, regardless of eviction pressure. TTL is your protection against indefinitely stale data. The right TTL depends entirely on your tolerance for stale data. User profile data might be safely cached for 5 minutes. A product's stock level might only be safely cached for 10 seconds. Exchange rates for 1 second. Choose based on how much staleness your users and business can accept.

⚠️
Cache Invalidation — The Hard Part

"There are only two hard things in Computer Science: cache invalidation and naming things." — Phil Karlton. Every time data changes in your database, you must ask: is this data cached somewhere? If so, how do you invalidate or update that cache entry before a user reads stale data? Missing an invalidation leads to users seeing incorrect data. Over-invalidating defeats the purpose of caching. Getting this right is the core challenge of building a correct caching layer.

Databases & Storage

Your database is where truth lives. It is the most critical component in most systems — and the one with the most design leverage. Choosing the right database type, structuring your schema to match your query patterns, and adding the right indexes separates systems that scale gracefully from those that become bottlenecks under load.

SQL vs NoSQL — a tradeoff, not a preference war

SQL databases (PostgreSQL, MySQL, SQLite) give you ACID guarantees: Atomicity (a transaction fully succeeds or fully fails), Consistency (data always satisfies defined constraints), Isolation (concurrent transactions do not interfere), and Durability (committed data survives crashes). They give you a powerful query language, joins across tables, foreign key constraints, and a schema that enforces structure. These guarantees are invaluable for financial data, user records, and any domain where correctness is non-negotiable.

NoSQL databases trade some of those guarantees for flexibility and scalability. A document store like MongoDB lets you store records with arbitrary shapes — no schema migrations needed when you add a field. A wide-column store like Cassandra distributes writes across hundreds of nodes with no single point of write contention, achieving extraordinary write throughput. But you lose joins, often lose transactions, and must design your data layout around your specific query patterns rather than around your domain model.

The right choice is almost always SQL for new projects unless you have a specific, well-understood reason to choose otherwise. PostgreSQL in particular is extraordinarily capable — it supports JSON columns, full-text search, time-series data, and can handle most workloads up to billions of rows with proper indexing and connection pooling.

Why indexes matter so much

Without an index, finding a row requires scanning every row in the table sequentially. On a table with 10 million rows, that might read 10 million rows to find one. An index is a sorted data structure (typically a B-tree) that allows the database to jump directly to matching rows in O(log n) time rather than O(n). The difference between an indexed and unindexed query on a large table is often the difference between 1ms and 30 seconds.

Indexes have costs too: they take up space (often 10–30% of the table size each), and they must be updated on every INSERT, UPDATE, and DELETE — adding overhead to writes. The rule of thumb: add an index for every column used in WHERE, JOIN ON, and ORDER BY clauses. Composite indexes (covering multiple columns) can be even more powerful — a composite index on (status, user_id) can satisfy queries filtering on both columns with a single index lookup.

Replication & Sharding

When a single database can no longer handle your read traffic, replication provides the answer. When your dataset outgrows a single machine, sharding partitions it. These are two distinct tools for two distinct bottlenecks — and confusing which problem you have leads to using the wrong solution.

Replication — copies for reads and resilience

In database replication, one server (the primary) handles all writes. Changes are continuously streamed to one or more replica servers, which maintain exact copies of the data. Read queries can be directed to replicas, spreading the read load across multiple machines. Most web applications read far more than they write — a product detail page might be read ten thousand times for every price update — so this asymmetry maps well to the architecture.

Replication also provides redundancy: if the primary server fails, a replica can be promoted to become the new primary within seconds to minutes, depending on your setup. Without replication, a primary failure means downtime until the server is restored or replaced.

There is a catch: replication is asynchronous by default. There is typically a small replication lag — milliseconds to seconds — between when data is written to the primary and when it appears on replicas. For most reads this is fine. But for reads that must see the most recently written data (e.g., reading back what you just created), you must route to the primary. This is the classic "read-your-own-writes" consistency problem.

# Simulates a sharded "database" across 3 shards.
# Each shard is a Ruby Hash here; in production each would
# be a separate PostgreSQL instance on its own server.

class ShardedDatabase
  def initialize(num_shards)
    @num_shards = num_shards
    @shards     = Array.new(num_shards) { {} }   # 3 independent stores
    @shard_ops  = Array.new(num_shards, 0)
    puts "Initialised #{num_shards} shards\n\n"
  end

  # ── Shard key: user_id % num_shards ───────────────────────────
  # This distributes users evenly across shards IF user_ids
  # are assigned sequentially. The shard for user 1 is always
  # shard 1, shard for user 2 is always shard 2, etc.
  # Once chosen, the shard key is essentially permanent —
  # changing it would require migrating all data.
  def shard_for(user_id)
    user_id % @num_shards
  end

  def insert(user_id, data)
    shard = shard_for(user_id)
    @shards[shard][user_id] = data
    @shard_ops[shard] += 1
    puts "  INSERT user #{user_id.to_s.rjust(3)} → shard-#{shard}"
  end

  def lookup(user_id)
    shard = shard_for(user_id)
    data  = @shards[shard][user_id]
    puts "  LOOKUP user #{user_id.to_s.rjust(3)} ← shard-#{shard}: #{data ? data[:name] : 'NOT FOUND'}"
    data
  end

  # Cross-shard query: must query ALL shards and merge results.
  # This is the main weakness of sharding — operations that span
  # multiple shard keys require querying every shard.
  def find_by_email(email)
    puts "  CROSS-SHARD query for email=#{email} (scanning all #{@num_shards} shards)"
    @shards.each_with_index do |shard, i|
      shard.each_value do |record|
        if record[:email] == email
          puts "    → Found in shard-#{i}: #{record[:name]}"
          return record
        end
      end
    end
    puts "    → Not found"; nil
  end

  def distribution
    puts "\nShard distribution:"
    @shards.each_with_index do |shard, i|
      bar = "█" * shard.length
      puts "  shard-#{i}: #{bar} #{shard.length} records, #{@shard_ops[i]} ops"
    end
  end
end

db = ShardedDatabase.new(3)

puts "── Inserting 15 users ──"
15.times do |i|
  id = i + 1
  db.insert(id, { id: id, name: "User #{id}", email: "u#{id}@app.com", plan: 'free' })
end

🚨
Sharding is a last resort

Sharding adds enormous operational complexity. Cross-shard joins become very expensive. Schema migrations must run on every shard. The shard key is essentially immutable once chosen. Before sharding, exhaust every other option: better indexes, query optimisation, connection pooling (PgBouncer), read replicas, vertical scaling, and aggressive caching. Most applications never need to shard.

API Design

An API is a contract between your system and the world. Good API design makes the right things easy, the wrong things hard or impossible, and the contract stable enough that clients do not need to change every time your implementation evolves internally.

REST — the dominant style

REST structures an API around resources (users, orders, products) identified by URLs, with HTTP verbs expressing the action (GET to read, POST to create, PUT/PATCH to update, DELETE to remove). Its strengths are its alignment with HTTP semantics — caches understand GET; browsers handle it natively — and its simplicity. Every developer already knows what GET /users/42 means.

REST's weakness is over-fetching and under-fetching. A mobile screen showing a user's name and their 3 most recent orders might require two separate API calls: GET /users/42 and GET /users/42/orders?limit=3. That is two round trips, two sets of network latency. Alternatively, you might add a custom endpoint that returns both — and now your API is no longer truly RESTful.

    elsif m == 'POST'

      unless b['name'] && b['email']
        next json(res, { error: "name and email are required",

      json(res, { data: u }, status: 201)

      USERS[id] = u.merge(b.transform_keys(&:to_sym).slice(:name, :plan))
      json(res, { data: USERS[id] })

    elsif m == 'DELETE' && id
      USERS.delete(id) ? json(res, { message: "Deleted" }) :
        json(res, { error: "Not found" }, status: 404)
    end
  end

Availability & Fault Tolerance

Hardware dies. Networks drop packets. Third-party APIs go down. A fault-tolerant system treats these as normal, expected events and is designed to survive them without user-visible impact. The goal is not to prevent failures — that is impossible — but to make failures recoverable and isolated.

The Circuit Breaker pattern

When a downstream service starts failing — payment gateway, email provider, third-party API — blindly retrying every request makes things worse. You hammer a struggling service, exhaust your own thread pool waiting for timeouts, and degrade your entire application for all users. The circuit breaker pattern stops this cascade.

A circuit breaker wraps calls to downstream services and tracks failures. After a configurable threshold of consecutive failures, the circuit "opens" — subsequent calls are rejected immediately with an error, without even attempting the network call. After a timeout period, the circuit enters "half-open" state and allows one probe request through. If it succeeds, the circuit closes and normal operation resumes. If it fails, the circuit opens again.

class CircuitBreaker
  def initialize(name:, failure_threshold: 3, reset_timeout: 4)
    @name      = name
    @threshold = failure_threshold
    @timeout   = reset_timeout
    @failures  = 0
    @state     = :closed    # :closed (normal) | :open (blocking) | :half_open (testing)
    @opened_at = nil
  end

  def call(&block)
    case @state
    when :open
      elapsed = Time.now - @opened_at
      if elapsed >= @timeout
        @state = :half_open
        puts "  ◐ [#{@name}] Circuit HALF-OPEN — sending probe request"
      else
        remaining = (@timeout - elapsed).ceil
        puts "  ✗ [#{@name}] Circuit OPEN — fast-fail (#{remaining}s until retry)"
        raise "CircuitOpen: #{@name} unavailable"
      end
    when :closed
      puts "  ● [#{@name}] Circuit CLOSED — attempting call"
    when :half_open
      puts "  ◐ [#{@name}] Circuit HALF-OPEN — probe attempt"
    end

    begin
      result = block.call
      on_success
      result
    rescue => e
      on_failure(e)
      raise
    end
  end

  private

  def on_success
    puts "    → SUCCESS ✓ — circuit closed"
    @failures = 0; @state = :closed
  end

  def on_failure(err)
    @failures += 1
    puts "    → FAILURE #{@failures}/#{@threshold}: #{err.message}"
    if @failures >= @threshold
      @state     = :open
      @opened_at = Time.now
      puts "    ⚡ Circuit OPENED — no requests for #{@timeout}s"
    end
  end
end
