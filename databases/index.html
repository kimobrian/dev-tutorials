Introduction

What is SQL & PostgreSQL?

Understanding the language, the database, and the mental model you'll use throughout this course.

What is SQL?

SQL (Structured Query Language) is a declarative language for interacting with relational databases. You describe what you want — the database engine figures out how to get it. This is fundamentally different from procedural programming where you specify every step.

SQL has four main categories of commands:

  • DDL — Data Definition Language: CREATE, ALTER, DROP
  • DML — Data Manipulation Language: SELECT, INSERT, UPDATE, DELETE
  • DCL — Data Control Language: GRANT, REVOKE
  • TCL — Transaction Control Language: BEGIN, COMMIT, ROLLBACK

Why PostgreSQL?

PostgreSQL (often called "Postgres") is a powerful, open-source object-relational database system with over 35 years of active development. It is known for:

  • Full ACID compliance — guarantees data integrity even under system failure
  • Advanced data types — JSON, arrays, ranges, custom types, geometric types
  • Sophisticated query planner — one of the most intelligent cost-based optimizers
  • Extensibility — PostGIS (geospatial), TimescaleDB (time-series), pgvector (AI embeddings)
  • Standard compliance — strictly follows SQL:2011 standard

The Relational Model

In a relational database, data is stored in tables (also called relations). Each table has:

  • Columns (attributes) — define the structure and data type
  • Rows (tuples) — individual records
  • Primary Key — uniquely identifies each row
  • Foreign Key — references a primary key in another table to create relationships

PostgreSQL Data Types

Choosing the right data type is one of the most impactful performance and correctness decisions you'll make.

Numeric Types

Choosing the right numeric type is a balance between storage size, range, and precision. The most common mistake is defaulting to INTEGER for everything — but using BIGINT for a status flag wastes 4 bytes per row, and using SMALLINT for a user ID will silently overflow at 32,767 users. The key question: what's the maximum value this column will ever hold, and do you need exact or approximate arithmetic?

SERIAL and BIGSERIAL are shorthand for creating a sequence and setting it as the column default. In modern PostgreSQL (10+), the preferred approach is GENERATED ALWAYS AS IDENTITY, which is SQL-standard and harder to accidentally bypass.

⚠ Never use FLOAT for money
FLOAT and REAL are approximate types. 0.1 + 0.2 may not equal 0.3. Always use NUMERIC(12,2) for monetary values.

Text Types

Unlike most databases, PostgreSQL stores TEXT, VARCHAR(n), and CHAR(n) using the same underlying storage mechanism. There is no performance difference between them — the length limit on VARCHAR(n) is purely a constraint checked on write, not a storage optimisation. Reach for TEXT by default and only use VARCHAR(n) when you want the database to enforce a maximum length as a data-quality rule.

PostgreSQL Note
In Postgres, TEXT, VARCHAR, and CHAR are stored identically. There is no performance difference. Prefer TEXT unless you specifically need the constraint.

Date & Time Types

Date and time handling is one of the most bug-prone areas in database design. The key decision is whether to store a timezone. A TIMESTAMP without timezone is "naive" — it records the clock reading with no context, so the same value means different real moments depending on where the server is. TIMESTAMPTZ stores everything as UTC internally and converts to the session's timezone on output — this is almost always what you want for any column that represents a real point in time (created_at, logged_at, occurred_at). Use plain DATE only for genuine calendar dates like birthdays or deadlines where timezone doesn't apply.

Always use TIMESTAMPTZ (timestamp with time zone) for any timestamp that represents a real moment in time. It eliminates ambiguity across time zones.

Other Important Types

UUID is often used as a primary key instead of SERIAL in distributed systems — since UUIDs are globally unique, you can generate them client-side without a database round-trip, and they don't reveal record counts. The trade-off is that random UUIDs cause index fragmentation (B-trees prefer sequential inserts). Use gen_random_uuid() (built-in since PostgreSQL 13) or the uuid-ossp extension. For ordered UUIDs that don't fragment indexes, look into UUIDv7.

Creating Tables & DDL

Define your database schema with CREATE TABLE, constraints, and how to evolve it safely with ALTER.

CREATE TABLE

The fundamental DDL command. You define columns, their types, and constraints all at once.

sql
CREATE TABLE employees (
    employee_id  SERIAL       PRIMARY KEY,
    name         VARCHAR(100) NOT NULL,
    email        TEXT         UNIQUE NOT NULL,
    department   TEXT         NOT NULL,
    salary       NUMERIC(10,2) CHECK (salary > 0),
    hire_date    DATE          DEFAULT CURRENT_DATE,
    is_active    BOOLEAN       DEFAULT TRUE
);

    salary       NUMERIC(10,2)
);

ON DELETE / ON UPDATE Actions

When a referenced row in the parent table is deleted or updated, the database needs to know what to do with the child rows that point to it. This is controlled by the ON DELETE and ON UPDATE clauses. Getting this right prevents orphaned data (child rows pointing to non-existent parents) and accidental cascading deletions.

  • CASCADE — delete/update child rows automatically
  • SET NULL — set the FK column to NULL when parent is deleted
  • SET DEFAULT — set FK column to its default value
  • RESTRICT — prevent deletion of parent if children exist (default)
  • NO ACTION — like RESTRICT but deferred until end of transaction

ALTER TABLE — Evolving Your Schema

Schema changes in production need care. Most ALTER TABLE operations in PostgreSQL take an AccessExclusiveLock — which blocks all reads and writes on the table for the duration of the operation. On a large busy table, even a fast-looking change can cause a visible outage as queries queue up behind the lock.

Adding a column with a DEFAULT value used to require rewriting the entire table (PostgreSQL < 11). Since PostgreSQL 11, adding a non-volatile default is instant — the default is stored in the catalog and applied lazily. Changing a column's type usually does require a full table rewrite. Always test schema changes on a copy of production data first, and for large tables consider tools like pg_repack or online schema change approaches.

sql
-- Add a new column
ALTER TABLE employees
  ADD COLUMN phone VARCHAR(20);

-- Rename a column
ALTER TABLE employees
  RENAME COLUMN phone TO phone_number;

-- Change a column type
ALTER TABLE employees
  ALTER COLUMN salary TYPE NUMERIC(14,2);

-- Drop a column
ALTER TABLE employees
  DROP COLUMN phone_number;

-- Add a constraint after the fact
ALTER TABLE employees
  ADD CONSTRAINT chk_salary CHECK (salary >= 0);

DROP TABLE

sql
DROP TABLE employees;                -- fails if other tables reference it
DROP TABLE employees CASCADE;       -- drops dependent objects too
DROP TABLE IF EXISTS employees;     -- no error if table doesn't exist
Danger
DROP TABLE is irreversible. Always test in a transaction or on a non-production environment first. Wrap in BEGIN; ... ROLLBACK; to preview safely.

SELECT Fundamentals

The SELECT statement is the most powerful tool in SQL. Everything you need to retrieve and transform data.

Basic SELECT Syntax

sql — logical clause order
SELECT   columns           -- 5. pick columns / expressions
FROM     table             -- 1. which table(s)
WHERE    condition         -- 2. filter rows
GROUP BY columns           -- 3. group rows
HAVING   group_condition   -- 4. filter groups
ORDER BY columns           -- 6. sort result
LIMIT    n                 -- 7. how many rows
OFFSET   skip;             -- 8. skip first n rows
Execution Order vs Write Order
SQL is written in a specific order but executed differently: FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT. This is why you can't use a SELECT alias in a WHERE clause — it hasn't been evaluated yet.

Sample Data for this Chapter

Understanding this order matters a lot in practice. For example, you cannot use a SELECT alias in a WHERE clause — the alias is defined in step 5 (SELECT), but WHERE runs at step 2. Similarly, you can reference a SELECT alias in ORDER BY because ORDER BY runs after SELECT. Postgres is stricter than MySQL about this, which catches bugs early.

Another consequence: GROUP BY runs before SELECT, which is why you can group by a column that isn't in your SELECT list — the grouping happens independently of what you choose to display.

Selecting Columns

The column list in a SELECT is more than a filter — it's a transformation step. You can rename columns with AS, compute derived values with expressions (stock * price), call functions (UPPER(category)), and mix literal values in with real columns. The result set you get back is a new, virtual table constructed from these expressions, not a direct slice of the stored data.

Avoid SELECT * in application code. It couples your code to the table structure — adding a column to the table silently changes what your query returns, which can break downstream code that expects a fixed column order or count. It also fetches columns you don't need, wasting I/O and memory, and prevents index-only scans. Name your columns explicitly.

sql
-- All columns (avoid in production code)
SELECT * FROM products;

-- Specific columns
SELECT name, price, category FROM products;

-- With aliases (rename output columns)
SELECT
    name         AS product_name,
    price        AS unit_price,
    stock * price AS inventory_value
FROM products;

Expressions & Functions in SELECT

Any valid PostgreSQL expression can appear in a SELECT list: arithmetic, string operations, date arithmetic, conditional logic (CASE WHEN), type casts, and function calls. These are computed per row and don't require a subquery or join. When working with numeric expressions, be aware that integer division truncates: 7 / 2 = 3, not 3.5. Cast to numeric first: 7::numeric / 2 = 3.5.

    name,
    price,
    ROUND(price * 1.16, 2)    AS price_with_vat,
    UPPER(category)            AS category_upper,
    LENGTH(name)               AS name_length,
    NOW()                       AS query_time
FROM products
WHERE product_id = 1;

DISTINCT — Remove Duplicates

DISTINCT compares entire rows (or the specified columns) and removes duplicates from the result. It works by sorting or hashing the result, which adds cost — for large result sets this can be significant. If you find yourself writing DISTINCT frequently on a joined query, it usually indicates the join is producing unintended duplicates; fixing the join is better than masking it with DISTINCT.

PostgreSQL's DISTINCT ON (column) is a powerful extension not in standard SQL: it returns one row per unique value of that expression, choosing whichever row comes first according to the ORDER BY. This is the idiomatic way to get "the cheapest product per category" or "the latest order per customer" without a subquery.

sql
-- Find all unique categories
SELECT DISTINCT category FROM products;

-- DISTINCT ON (PostgreSQL-specific)
-- Get cheapest product per category
SELECT DISTINCT ON (category) category, name, price
FROM products
ORDER BY category, price ASC;

Filtering with WHERE

WHERE is your first line of defense against returning too much data. Master every operator.

Comparison Operators

The WHERE clause is evaluated once per row, before any aggregation or sorting. It's a boolean expression — every row where the expression evaluates to TRUE is kept; rows where it evaluates to FALSE or NULL are discarded. This last part is important: a NULL comparison never evaluates to TRUE, so rows with NULL in a filtered column are silently dropped even if you're not explicitly testing for NULL.

The standard comparison operators work as you'd expect on numbers, strings (alphabetical), and dates. When comparing strings, be aware that PostgreSQL's default text comparison is locale-aware and case-sensitive — 'Apple' = 'apple' is FALSE. For case-insensitive equality, use LOWER(name) = 'apple' or the ILIKE operator.

sql
SELECT * FROM products WHERE price = 29.99;
SELECT * FROM products WHERE price != 29.99;   -- or <>
SELECT * FROM products WHERE price > 100;
SELECT * FROM products WHERE price <= 50;

Logical Operators: AND, OR, NOT

Multiple conditions are combined with AND, OR, and NOT. Each condition still follows three-valued logic — TRUE, FALSE, or NULL — and the combination rules are: TRUE AND NULL = NULL, FALSE OR NULL = NULL, NOT NULL = NULL. This means a NULL can silently suppress rows even in complex conditions.

sql
-- AND: both conditions must be true
SELECT * FROM products
WHERE category = 'Electronics' AND price < 100;

-- OR: at least one condition is true
SELECT * FROM products
WHERE category = 'Books' OR category = 'Furniture';

-- NOT: invert a condition
SELECT * FROM products
WHERE NOT category = 'Electronics';
Operator Precedence: AND before OR
AND binds tighter than OR. The expression WHERE category = 'Books' OR category = 'Furniture' AND price < 100 is parsed as WHERE category = 'Books' OR (category = 'Furniture' AND price < 100) — probably not what you intended. Always use parentheses to make complex conditions explicit: WHERE (category = 'Books' OR category = 'Furniture') AND price < 100.

BETWEEN, IN, LIKE, ILIKE

These operators are syntactic sugar for common patterns. BETWEEN a AND b is exactly equivalent to >= a AND <= b — inclusive on both ends. IN (list) is cleaner than chaining OR conditions and lets the planner use an index more efficiently. For very large lists (hundreds of values), consider = ANY(ARRAY[...]) or a JOIN to a temporary values table instead.

With LIKE, % matches any sequence of characters (including none) and _ matches exactly one character. A leading wildcard (LIKE '%word') cannot use a B-tree index — it forces a full sequential scan. For efficient substring or fuzzy search, use the pg_trgm extension with a GIN trigram index, or PostgreSQL's built-in full-text search covered in Chapter 20.

sql
-- BETWEEN (inclusive on both ends)
SELECT name, price FROM products
WHERE price BETWEEN 40 AND 100;

-- IN (membership test — much cleaner than multiple ORs)
SELECT name, category FROM products
WHERE category IN ('Books', 'Furniture');

-- LIKE (case-sensitive pattern matching)
-- % matches any sequence, _ matches one character
SELECT name FROM products WHERE name LIKE '%Pro%';
SELECT name FROM products WHERE name LIKE 'W____ess%';

-- ILIKE (case-insensitive, PostgreSQL-specific)
SELECT name FROM products WHERE name ILIKE '%laptop%';

NULL Handling

NULL is one of the most misunderstood concepts in SQL. It does not mean zero, empty string, or false — it means "unknown" or "not applicable". Because NULL is unknown, any comparison with NULL produces NULL (not TRUE or FALSE). This three-valued logic (TRUE / FALSE / NULL) is the source of many subtle bugs.

NULL represents the absence of a value. It is not equal to anything — not even itself. Use IS NULL / IS NOT NULL.

sql
-- WRONG: this never matches anything!
SELECT * FROM employees WHERE manager_id = NULL;

-- CORRECT
SELECT * FROM employees WHERE manager_id IS NULL;
SELECT * FROM employees WHERE manager_id IS NOT NULL;

-- COALESCE: return first non-null value
SELECT name, COALESCE(phone, 'No phone') AS contact
FROM employees;

-- NULLIF: return NULL if two values are equal
SELECT NULLIF(salary, 0) AS salary  -- NULL instead of 0
FROM employees;
NULL Propagation
Any arithmetic or comparison with NULL produces NULL. NULL + 5 = NULL, NULL = NULL → NULL (not TRUE). This catches many developers off guard.

Sorting & Limiting

Control the order and volume of your result sets with ORDER BY, LIMIT, and OFFSET — and understand keyset pagination.

ORDER BY

Without an ORDER BY clause, the order of rows returned by a SELECT is undefined — the database is free to return them in any order it finds convenient, and that order can change between executions of the same query as data is added, pages are reorganised, or the query plan changes. Never rely on implicit ordering. If order matters, always specify it explicitly.

When sorting on multiple columns, PostgreSQL sorts by the first column, then breaks ties using the second column, and so on. The sort direction (ASC / DESC) and NULL handling (NULLS FIRST / NULLS LAST) can be specified independently for each column in the list. By default, NULLs sort as if they are larger than any non-NULL value — so they appear last in ASC order and first in DESC order.

sql
-- Ascending (default) and descending
SELECT name, price FROM products ORDER BY price;
SELECT name, price FROM products ORDER BY price DESC;

-- Multi-column sort
SELECT name, category, price
FROM products
ORDER BY category ASC, price DESC;

-- NULL handling in sort
SELECT name, salary FROM employees
ORDER BY salary DESC NULLS LAST;  -- NULLs at the bottom

LIMIT & OFFSET

LIMIT caps the number of rows returned. OFFSET skips a given number of rows before starting to return results. Together they're used for pagination — but there's a subtle correctness issue: if the underlying data changes between page requests (rows inserted or deleted), OFFSET-based pagination can skip rows or show the same row twice. Keyset pagination (shown below) avoids this by using the last seen value as a cursor.

sql
-- Get top 3 most expensive products
SELECT name, price FROM products
ORDER BY price DESC
LIMIT 3;

-- Pagination: page 2, 2 items per page
SELECT name, price FROM products
ORDER BY product_id
LIMIT 2 OFFSET 2;  -- skip first 2, return next 2
Performance Warning
OFFSET gets expensive on large tables — the database must scan and skip all preceding rows. For high-traffic pagination, use keyset pagination instead.

Keyset Pagination (Cursor-Based)

sql — efficient pagination for large tables
-- First page
SELECT product_id, name, price
FROM products
ORDER BY product_id
LIMIT 10;

-- Next page: pass last seen product_id (e.g. 10)
SELECT product_id, name, price
FROM products
WHERE product_id > 10  -- the cursor
ORDER BY product_id
LIMIT 10;
-- This is O(1) regardless of how deep into the result set you are!

One of the most common surprises: all aggregate functions except COUNT(*) silently ignore NULL values. This means AVG(salary) on a table where some employees have no salary recorded will compute the average of only the non-NULL rows — it won't count those employees in the denominator. This can give you a misleadingly high average. If you want NULLs to count as zero, use AVG(COALESCE(salary, 0)).

The difference between COUNT(*) and COUNT(column) is important: COUNT(*) counts every row including those with NULLs; COUNT(salary) only counts rows where salary is not NULL. Use COUNT(*) - COUNT(salary) to find how many rows have a NULL salary.

sql — aggregating the products table
SELECT
    COUNT(*)                   AS total_products,
    COUNT(DISTINCT category)  AS categories,
    SUM(stock * price)        AS total_inventory_value,
    AVG(price)                 AS avg_price,
    MIN(price)                 AS cheapest,
    MAX(price)                 AS most_expensive
FROM products;

Statistical Aggregates

PostgreSQL ships with a full suite of statistical aggregate functions. PERCENTILE_CONT computes a continuous percentile — interpolating between values — while PERCENTILE_DISC returns an actual value from the dataset (the nearest discrete value). For the median, both give similar results on large datasets. For the 95th or 99th percentile of response times in a monitoring context, the distinction matters for exact threshold comparisons.

These functions use the WITHIN GROUP (ORDER BY column) syntax, which looks unusual but is part of the SQL standard for "ordered-set aggregate functions". The ordering determines how the aggregation proceeds — for percentile functions, you must order by the column you're computing the percentile of.

sql — PostgreSQL extended aggregates
SELECT
    STDDEV(price)       AS price_stddev,
    VARIANCE(price)     AS price_variance,
    PERCENTILE_CONT(0.5) WITHIN GROUP (ORDER BY price) AS median,
    PERCENTILE_CONT(0.9) WITHIN GROUP (ORDER BY price) AS p90
FROM products;

STRING_AGG & ARRAY_AGG

These two functions let you collect all the values in a group into a single output value — either a delimited string or a PostgreSQL array. Both accept an optional ORDER BY clause inside the aggregate to control the order of items in the result, and both ignore NULL values by default.

STRING_AGG is the PostgreSQL equivalent of MySQL's GROUP_CONCAT. It's useful for generating comma-separated lists, building JSON manually, or creating readable summary rows. ARRAY_AGG is more powerful — the resulting array can be passed to other array functions, used with = ANY() comparisons, or unnested with UNNEST() back into rows.

sql
-- Concatenate names into a comma-separated string
SELECT
    category,
    STRING_AGG(name, ', ' ORDER BY name) AS products_list
FROM products
GROUP BY category;

-- Collect into a Postgres array
SELECT
    category,
    ARRAY_AGG(name ORDER BY price) AS products_by_price
FROM products
GROUP BY category;

GROUP BY & HAVING

Slice your data into groups, aggregate each group, then filter the groups themselves.

GROUP BY

GROUP BY divides rows into groups based on one or more columns. The key rule: every column in your SELECT that is not inside an aggregate function must appear in GROUP BY. This is because once rows are collapsed into groups, Postgres has no way to know which individual row's value to pick for a non-grouped column — it could be different for every row in the group.

A helpful mental model: think of GROUP BY as creating "buckets". All rows with the same category go in the same bucket. You can then apply aggregate functions (COUNT, SUM, etc.) to compute one value per bucket. The columns you GROUP BY are the bucket labels — those are the only columns that are unambiguous to select directly.

GROUP BY divides rows into groups based on one or more columns. All columns in SELECT that are not aggregates must appear in GROUP BY.

sql
SELECT
    category,
    COUNT(*)      AS product_count,
    AVG(price)    AS avg_price,
    SUM(stock)    AS total_stock
FROM products
GROUP BY category
ORDER BY avg_price DESC;

HAVING — Filter Groups

WHERE filters rows before grouping. HAVING filters groups after aggregation.

sql
-- Only categories with more than 1 product AND avg price > 100
SELECT
    category,
    COUNT(*)   AS cnt,
    AVG(price) AS avg_price
FROM products
GROUP BY category
HAVING COUNT(*) > 1
   AND AVG(price) > 100;

The type of JOIN you choose determines what happens when there's no match. INNER JOIN discards unmatched rows from both sides. LEFT JOIN keeps all left rows even without a match, filling right-side columns with NULL. This is why LEFT JOIN is far more common than RIGHT JOIN — you can always rewrite a RIGHT JOIN as a LEFT JOIN by swapping the table order, and LEFT JOIN reads more naturally ("give me all employees, and their department if they have one").

RIGHT JOIN & FULL OUTER JOIN

sql
-- RIGHT JOIN: all from departments + matching employees
SELECT e.name, d.dept_name
FROM employees e
RIGHT JOIN departments d ON e.dept_id = d.dept_id;
-- Returns: Alice/Engineering, Bob/Marketing, Carol/Engineering, NULL/HR

-- FULL OUTER JOIN: all rows from both sides
SELECT e.name, d.dept_name
FROM employees e
FULL OUTER JOIN departments d ON e.dept_id = d.dept_id;
-- Returns all 5 rows, NULLs where no match

CROSS JOIN & Self-JOIN

A CROSS JOIN produces the Cartesian product — every combination of every row from the left table with every row from the right. If table A has 100 rows and table B has 200 rows, the result is 20,000 rows. This sounds dangerous, but it's genuinely useful for generating all combinations: pairing every product with every colour option, creating a calendar grid, or seeding test data. Always add a WHERE clause to filter down to meaningful combinations.

A self-join joins a table to itself using two different aliases. This is the standard way to express hierarchical or comparative relationships within a single table — finding every employee and their manager (where both are rows in the same employees table), or finding all pairs of products in the same category.

sql
-- CROSS JOIN: every combination (Cartesian product)
SELECT e1.name, e2.name
FROM employees e1
CROSS JOIN employees e2
WHERE e1.emp_id < e2.emp_id;  -- all pairs, no duplicates

-- Self-JOIN: manager hierarchy
SELECT
    e.name       AS employee,
    m.name       AS manager
FROM employees e
LEFT JOIN employees m ON e.manager_id = m.emp_id;

JOIN with Multiple Conditions

The ON clause can contain any boolean expression — not just a single equality. You can join on multiple columns, add range conditions, or filter out certain matches. Note the difference between putting a condition in ON vs in WHERE: in a LEFT JOIN, a condition in ON filters which right-side rows are matched (non-matching right rows still appear as NULLs), while a condition in WHERE filters the final result and can accidentally turn a LEFT JOIN into an INNER JOIN.

sql
SELECT o.order_id, p.name, op.quantity, op.unit_price
FROM orders o
JOIN order_items op ON o.order_id = op.order_id
JOIN products p    ON op.product_id = p.product_id
                   AND op.unit_price = p.price  -- extra condition
WHERE o.status = 'completed';
Performance
Always join on indexed columns. Foreign keys create indexes automatically in most workflows. JOINs on non-indexed columns cause sequential scans on both tables — a major performance killer.

Subqueries & CTEs

Subqueries in WHERE

SELECT name
FROM departments d
WHERE EXISTS (
    SELECT 1 FROM employees e
    WHERE e.dept_id = d.dept_id

SELECT name FROM products
WHERE product_id NOT IN (
    SELECT product_id FROM order_items

sql
-- Aggregate of an aggregation
SELECT
    AVG(category_avg)  AS overall_avg_of_avgs,

FROM (
    SELECT
        category,
        AVG(price) AS category_avg
    FROM products
    GROUP BY category

Common Table Expressions (WITH)

CTEs (introduced with the WITH keyword) let you name an intermediate result and reference it like a table in the main query. They are purely a readability and organisational tool — in most cases the query planner treats them identically to subqueries. The real benefit is breaking a complex query into named, logical steps that can be read top-to-bottom like paragraphs.

When to use a CTE vs a subquery: use a CTE when you need to reference the same intermediate result more than once, when the logic is complex enough to deserve a name, or when you want to build up a query step-by-step for debugging (you can comment out CTEs to isolate issues). Use a subquery when the logic is simple and only used once — it keeps the query compact.

CTEs make complex queries readable by naming intermediate result sets. They're evaluated once and referenced like a temporary table.

sql
WITH high_value_products AS (
    SELECT product_id, name, price
    FROM products
    WHERE price > 100
),
category_totals AS (
    SELECT
        category,
        SUM(price) AS total_value,
        COUNT(*)  AS cnt
    FROM high_value_products hvp
    JOIN products p USING(product_id)
    GROUP BY category
)
SELECT * FROM category_totals
ORDER BY total_value DESC;

Recursive CTEs

Recursive CTEs are ideal for hierarchical data like org charts, directory trees, or bill-of-materials.

sql — traverse org hierarchy
WITH RECURSIVE org_tree AS (
    -- Base case: top-level employees (no manager)
    SELECT emp_id, name, manager_id, 0 AS level
    FROM employees
    WHERE manager_id IS NULL

    UNION ALL

    -- Recursive case: find direct reports
    SELECT e.emp_id, e.name, e.manager_id, ot.level + 1
    FROM employees e
    INNER JOIN org_tree ot ON e.manager_id = ot.emp_id
)
SELECT
    REPEAT('  ', level) || name AS hierarchy,
    level
FROM org_tree
ORDER BY level, name;

Set Operations

Set Operations

Combine result sets from multiple SELECT statements with UNION, INTERSECT, and EXCEPT.

Set operations let you combine the result sets of two or more SELECT statements as if they were rows from the same query. They are conceptually different from JOINs: a JOIN combines columns side-by-side (horizontal expansion), while set operations stack rows on top of each other (vertical combination). The column count and compatible types must match, but the column names come from the first query — aliases in the second query are ignored.

UNION — Combine Results

sql
-- UNION removes duplicates; UNION ALL keeps them (faster)
SELECT name, 'Electronics' AS source FROM products
WHERE category = 'Electronics'

UNION ALL

SELECT name, 'Furniture' AS source FROM products
WHERE category = 'Furniture';

INTERSECT — Rows in Both

INTERSECT returns only rows that appear in both result sets — the mathematical intersection. Like UNION, it removes duplicates by default. Use INTERSECT ALL to preserve them. A common alternative is a JOIN or an EXISTS subquery — they're equivalent, but INTERSECT is cleaner when you only care about matching key values rather than the full rows.

sql
-- Customers who placed orders in both 2023 AND 2024
SELECT customer_id FROM orders WHERE EXTRACT(YEAR FROM order_date) = 2023
INTERSECT
SELECT customer_id FROM orders WHERE EXTRACT(YEAR FROM order_date) = 2024;

EXCEPT — Rows in First but Not Second

EXCEPT returns rows from the first query that do not appear in the second — the mathematical set difference. It's a concise way to find "what's missing" or "what changed". The equivalent using a JOIN would be a LEFT JOIN with WHERE right_side.key IS NULL. EXCEPT is often more readable. As with UNION and INTERSECT, EXCEPT ALL treats duplicates as separate instances.

sql
-- Customers who ordered in 2023 but NOT in 2024 (churned?)
SELECT customer_id FROM orders WHERE EXTRACT(YEAR FROM order_date) = 2023
EXCEPT
SELECT customer_id FROM orders WHERE EXTRACT(YEAR FROM order_date) = 2024;
Rules for Set Operations
Both queries must return the same number of columns, and corresponding columns must have compatible data types. Column names are taken from the first query.

INSERT, UPDATE, DELETE

Modify your data safely with DML commands — and master PostgreSQL-specific power features like UPSERT and RETURNING.

INSERT

The INSERT statement adds one or more rows to a table. Always specify the column list explicitly — if you omit it and rely on column position order, your insert will silently break the day someone adds or reorders a column in the table definition. Listing columns is a small discipline that prevents very hard-to-debug data corruption.

Inserting multiple rows in a single VALUES clause is far more efficient than running separate INSERT statements in a loop — it reduces round-trips and allows PostgreSQL to batch the writes internally. For thousands of rows, prefer COPY FROM which is even faster, or INSERT ... SELECT to populate from an existing table.

sql
-- Single row
INSERT INTO products (name, category, price, stock)
VALUES ('Mechanical Keyboard', 'Electronics', 149.99, 75);

-- Multiple rows
INSERT INTO products (name, category, price, stock) VALUES
    ('Monitor 27"',    'Electronics', 399.00, 20),
    ('Desk Chair',     'Furniture',   299.00, 15),
    ('SQL Internals',  'Books',        54.99,  50);

-- Insert from SELECT
INSERT INTO products_archive
SELECT * FROM products
WHERE created_at < '2023-01-01';

-- RETURNING: get the inserted data back
INSERT INTO products (name, category, price, stock)
VALUES ('Webcam HD', 'Electronics', 79.99, 60)
RETURNING product_id, name, created_at;
Why RETURNING is powerful
The RETURNING clause (PostgreSQL-specific) lets you get data back from an INSERT, UPDATE, or DELETE in the same round-trip. Without it, you'd need a separate SELECT query after the write — two round-trips, plus a race condition risk if another process modifies the row in between. RETURNING * is especially useful in application code where you need the auto-generated id or created_at value right after an insert.

UPSERT — INSERT … ON CONFLICT

Postgres's ON CONFLICT lets you atomically insert or update — preventing race conditions and separate SELECT + INSERT logic.

sql
-- If product_id exists, update price; else insert
INSERT INTO products (product_id, name, price, stock)
VALUES (1, 'Laptop Pro 15', 1199.99, 50)
ON CONFLICT (product_id) DO UPDATE
    SET price  = EXCLUDED.price,
        stock  = products.stock + EXCLUDED.stock;

-- Silently ignore duplicates
INSERT INTO tags (name)
VALUES ('postgresql')
ON CONFLICT (name) DO NOTHING;

UPDATE

The most dangerous thing about UPDATE is forgetting the WHERE clause — which updates every row in the table. The professional habit is to always run a SELECT with the same WHERE clause first to confirm the affected rows, then run the UPDATE. Even better: wrap in a transaction, check the row count, and only commit if it's what you expected.

PostgreSQL's UPDATE ... FROM syntax lets you join to another table in an update — useful when the new values come from a different table. This is PostgreSQL-specific syntax; the SQL standard uses a subquery in the SET clause instead.

sql
-- Simple update
UPDATE products
SET price = price * 0.9  -- 10% discount
WHERE category = 'Electronics';

-- UPDATE with JOIN (UPDATE … FROM)
UPDATE employees e
SET salary = e.salary * 1.1
FROM departments d
WHERE e.dept_id = d.dept_id
  AND d.dept_name = 'Engineering'
RETURNING e.name, e.salary;

DELETE

Like UPDATE, a DELETE without a WHERE clause removes every row — it won't ask for confirmation. The same discipline applies: SELECT first, then DELETE. The RETURNING clause is particularly useful with DELETE — it lets you capture the deleted rows for logging or further processing without a separate SELECT before the deletion.

TRUNCATE is a DDL command (not DML) that removes all rows by deallocating the table's data pages — it's orders of magnitude faster than DELETE FROM table for large tables. However, it can't be filtered with a WHERE clause, it fires statement-level triggers (not row-level), and it requires a more permissive lock. TRUNCATE ... CASCADE also truncates referencing tables, which can be surprising.

sql
-- Delete specific rows
DELETE FROM products
WHERE stock = 0
RETURNING product_id, name;

-- Delete with subquery
DELETE FROM order_items
WHERE order_id IN (
    SELECT order_id FROM orders
    WHERE status = 'cancelled'
);

-- TRUNCATE: remove all rows, very fast
TRUNCATE TABLE session_logs;
TRUNCATE TABLE orders CASCADE; -- also truncates related tables
Always test DML with a transaction
Before running any UPDATE or DELETE, wrap it in BEGIN; first, check the rows affected, then COMMIT; or ROLLBACK;. One missing WHERE clause can corrupt an entire table.

Transactions & ACID

Ensure data integrity even when things go wrong — transactions are the backbone of reliable databases.

What is a Transaction?

A transaction is a sequence of SQL operations treated as a single unit. Either all of them succeed, or none of them do. There is no partial state.

ACID Properties

Basic Transaction Syntax

sql
BEGIN;  -- start transaction (also: START TRANSACTION)

-- Debit account A
UPDATE accounts SET balance = balance - 500
WHERE account_id = 1;

-- Credit account B
UPDATE accounts SET balance = balance + 500
WHERE account_id = 2;

COMMIT;   -- make it permanent
-- or: ROLLBACK; -- undo everything

SAVEPOINT — Partial Rollback

Savepoints let you mark a point within a transaction that you can roll back to without abandoning the entire transaction. This is useful in complex operations where one step might fail but prior work should be preserved — for example, processing a batch of items where some may be invalid. You roll back to the savepoint, skip the bad item, and continue.

Savepoints have a cost: PostgreSQL must track the state needed to restore to each one. In tight loops, creating a savepoint per iteration can degrade performance. A common pattern is to use a savepoint per "logical unit" within the transaction rather than per row.

sql
BEGIN;
INSERT INTO orders (...) VALUES (...);

SAVEPOINT after_order;

INSERT INTO order_items (...) VALUES (...);
-- oops, something wrong with the item
ROLLBACK TO SAVEPOINT after_order;

-- try again with corrected data
INSERT INTO order_items (...) VALUES (...);
COMMIT;

Isolation Levels

Isolation levels control what a transaction can see when other transactions are running concurrently. There are three classic anomalies they protect against:

  • Dirty read — reading uncommitted data from another transaction. If that transaction rolls back, you've acted on data that never existed.
  • Non-repeatable read — reading the same row twice in one transaction and getting different values because another transaction committed an update in between.
  • Phantom read — running the same query twice and getting different sets of rows because another transaction inserted or deleted rows in between.

PostgreSQL's default, READ COMMITTED, is appropriate for most OLTP workloads — each statement sees a fresh snapshot of committed data. Use REPEATABLE READ for reports or export jobs that need a consistent view across multiple queries. SERIALIZABLE gives you the gold standard but uses predicate locking and may cause transactions to be aborted and retried when the planner detects a serialization conflict.

Window Functions

Perform calculations across rows related to the current row — without collapsing them into groups. One of the most powerful features in SQL.

The Concept

Unlike GROUP BY which collapses rows into one summary per group, window functions compute a value for each row based on a "window" of related rows — and every original row is still visible in the output.

The key insight: window functions run after WHERE, GROUP BY, and HAVING — but before ORDER BY and LIMIT. This means you can use window functions on the already-filtered, already-grouped result set, but you can't filter on window function results in a WHERE clause (use a CTE or subquery wrapper for that).

The PARTITION BY clause divides the rows into independent groups (like a GROUP BY that doesn't collapse rows). The ORDER BY inside OVER() controls the order within each partition for running totals, rankings, and lag/lead — it's completely independent of the query's outer ORDER BY.

Indexes & Performance

Indexes are the single biggest lever for query performance. Learn all the types, when to create them, and when not to.

What is an Index?

An index is a separate on-disk data structure that maintains a sorted copy of one or more columns and a pointer back to the full row (called the heap). Without an index, Postgres must read every single row in the table to find matches — called a sequential scan — which is O(n). With a B-tree index, it can find matching rows in O(log n) by traversing a balanced tree of sorted values.

The trade-off: indexes speed up reads but slow down writes. Every INSERT, UPDATE, or DELETE must also update all relevant indexes. For a table with 5 indexes, each write touches 6 data structures (1 table + 5 indexes). This is why you should index selectively — not every column — and drop unused indexes rather than keeping them "just in case".

B-Tree Index (Default)

Handles equality (=), range (<, >, BETWEEN), and sort operations. Suitable for 95% of use cases.

sql
-- Basic index
CREATE INDEX idx_products_category ON products(category);

-- Composite index (column order matters!)
-- Good for: WHERE category = ? AND price < ?
CREATE INDEX idx_cat_price ON products(category, price);

-- Unique index (also enforces constraint)
CREATE UNIQUE INDEX idx_products_sku ON products(sku);

-- Partial index: index only rows matching a condition
-- Much smaller, much faster for targeted queries
CREATE INDEX idx_active_products
    ON products(category, price)
    WHERE is_active = TRUE;

-- Concurrent index (no table lock — safe for production)
CREATE INDEX CONCURRENTLY idx_orders_date ON orders(order_date);

Specialized Index Types

PostgreSQL ships with several index access methods beyond B-tree, each optimised for a different kind of data or query pattern. Picking the wrong index type means the planner won't use it — or will use it but more slowly than a sequential scan.

Expression Indexes

An expression index stores the result of a function or expression rather than the raw column value. This lets the planner use the index for queries that filter or sort on that expression — but only if the query uses exactly the same expression. Even a semantically equivalent expression (like chaining -> instead of using #>> for JSON) will not match the index.

Expression indexes are particularly powerful for case-insensitive searches (index LOWER(email)), computed columns (index price * 1.16 for VAT-inclusive price), and JSONB field access (index a specific nested path).

sql
-- Case-insensitive search on email
CREATE INDEX idx_email_lower ON users(LOWER(email));

-- Query must match the expression exactly to use the index:
SELECT * FROM users WHERE LOWER(email) = 'alice@example.com';

-- Index on JSONB field
CREATE INDEX idx_user_role ON users((metadata ->> 'role'));
SELECT * FROM users WHERE metadata ->> 'role' = 'admin';

When Indexes Are NOT Used

Index Killers
These patterns prevent index use — they force a sequential scan:
  • WHERE LOWER(name) = 'alice' — function on indexed column (use expression index instead)
  • WHERE salary + 1000 > 80000 — arithmetic on indexed column
  • WHERE name LIKE '%alice%' — leading wildcard
  • WHERE id != 5 — negative conditions on low-selectivity columns
  • Low-cardinality columns (boolean, status) — planner may choose seq scan anyway

Maintaining Indexes

Indexes need maintenance. Over time, as rows are updated and deleted, B-tree index pages accumulate dead entries (bloat) which waste space and slow scans. PostgreSQL's autovacuum process reclaims space within pages but doesn't always return it to the OS or compact the index structure. A REINDEX rebuilds from scratch, which can reclaim significant space on write-heavy tables — but locks the index for the duration. Use REINDEX ... CONCURRENTLY (PG 12+) to rebuild without blocking reads.

Unused indexes are pure overhead — they consume disk space and slow down every INSERT, UPDATE, and DELETE. The pg_stat_user_indexes view tracks how many times each index has been used since the last stats reset. Any index with idx_scans = 0 after a representative period of traffic is a candidate for removal.

sql
-- List all indexes on a table
SELECT indexname, indexdef FROM pg_indexes
WHERE tablename = 'products';

-- Check for unused indexes (costly to maintain)
SELECT schemaname, tablename, indexname, idx_scans
FROM pg_stat_user_indexes
WHERE idx_scans = 0
ORDER BY pg_relation_size(indexrelid) DESC;

-- Rebuild a bloated index
REINDEX INDEX CONCURRENTLY idx_products_category;

-- Drop an index
DROP INDEX CONCURRENTLY idx_products_category;

Before diving into plan output, it helps to understand what Postgres is actually doing when you run EXPLAIN: it asks the query planner to choose among several possible execution strategies (which indexes to use, which join algorithm to apply, what order to join tables) by estimating the cost of each. It then shows you the winning plan.

EXPLAIN alone doesn't execute the query — it's entirely safe to run on any query, including slow ones. EXPLAIN ANALYZE does execute it, giving you actual timing. Be careful with EXPLAIN ANALYZE on INSERT/UPDATE/DELETE — it will actually modify your data.

Reading the Plan: Cost Notation

The cost numbers (e.g. cost=0.00..12.40) are in abstract planner units — not milliseconds. They represent an estimated total work, calibrated so that reading one 8KB page from disk costs 1.0. Sequential reads cost less than random reads (seq_page_cost=1.0 vs random_page_cost=4.0 by default). What matters is the relative cost between nodes, not the absolute value. A node with cost 10,000 isn't "slow" — it's 1000× more expensive than a node with cost 10. The startup cost (before ..) is the time before the first row is returned; the total cost is for all rows.

Views & Materialized Views

Encapsulate complex queries behind a simple name — and optionally persist the results for instant access.

Views

A view is a named SQL query stored in the database. When you SELECT from a view, PostgreSQL substitutes the view definition into the query and optimises the whole thing together — the view is not materialised as an intermediate step. This means views have zero storage overhead and always reflect the latest data, but they also mean the full query cost is paid on every access.

Views serve several important purposes beyond convenience: they provide a stable interface so application code doesn't break when the underlying table structure changes; they implement column-level access control by exposing only safe columns; and they encapsulate complex joins and calculations behind a simple name that domain experts can understand without knowing SQL internals.

It behaves like a table but is computed fresh on every access. No data is stored.

sql
-- Create a view
CREATE VIEW electronics_summary AS
    SELECT
        name,
        price,
        stock,
        price * stock AS inventory_value
    FROM products
    WHERE category = 'Electronics';

-- Use it just like a table
SELECT * FROM electronics_summary WHERE price < 100;

-- Replace a view without dropping it
CREATE OR REPLACE VIEW electronics_summary AS
    SELECT name, price, stock FROM products WHERE category = 'Electronics';
Views as a Security Layer
One of the most practical uses of views is column-level access control. PostgreSQL doesn't natively restrict which columns a role can SELECT — but you can grant SELECT on a view that only exposes safe columns. For example, grant your reporting role SELECT on a employees_public view that includes name and department but excludes salary and personal details. The underlying table remains inaccessible to that role.

Updatable Views

Simple views (single table, no aggregates, no DISTINCT) can be updated like tables.

sql
-- This view is updatable
CREATE VIEW active_products AS
    SELECT product_id, name, price FROM products
    WHERE is_active = TRUE
    WITH CHECK OPTION;  -- prevents inserting rows that would vanish

UPDATE active_products SET price = 999 WHERE product_id = 1;

Materialized Views

A materialized view stores the query result on disk. This is a fundamental trade-off: you pay once on refresh and get instant reads thereafter — ideal for expensive aggregation queries that power dashboards or reports. The data is stale between refreshes, so you need to decide how stale is acceptable and schedule refreshes accordingly.

Unlike a regular view, you can create indexes on a materialized view. This makes them even faster for filtered queries. The combination of a pre-computed aggregation plus an index is often the right answer for reporting queries that regularly scan millions of rows but only need summary data.

A materialized view stores the query result on disk. Reads are instant but the data may be stale — you must refresh it manually or on schedule.

sql
-- Create (runs the query once and stores the result)
CREATE MATERIALIZED VIEW monthly_sales_summary AS
    SELECT
        DATE_TRUNC('month', order_date) AS month,
        COUNT(*)                         AS orders,
        SUM(total_amount)                 AS revenue
    FROM orders
    GROUP BY 1
    ORDER BY 1;

-- You can index a materialized view!
CREATE INDEX ON monthly_sales_summary(month);

-- Refresh when you need fresh data
REFRESH MATERIALIZED VIEW monthly_sales_summary;

-- Refresh without locking reads (requires unique index)
REFRESH MATERIALIZED VIEW CONCURRENTLY monthly_sales_summary;
When to Use Each
  • View: Reusable query abstraction, always fresh, no extra storage. Use for security (hide columns), simplification, or business logic.
  • Materialized View: Expensive aggregate queries used by dashboards, reports. Refresh periodically (e.g. with pg_cron) or after ETL loads.

Stored Procedures & Functions

Encapsulate business logic in the database with PL/pgSQL — PostgreSQL's powerful procedural language.

Functions vs Procedures

PostgreSQL gives you two ways to package reusable logic: functions and procedures. The distinction matters in practice — functions are designed to be called as part of a query (in a SELECT, WHERE, or JOIN), while procedures are standalone units called with CALL, primarily for multi-step workflows that need to manage their own transactions.

Function (CREATE FUNCTION)Procedure (CREATE PROCEDURE)

Can call in SELECTYesNo (use CALL)

Function Volatility Labels

PostgreSQL uses three volatility labels that affect how the planner caches and optimises function calls:

  • IMMUTABLE — same inputs always produce the same output, regardless of database state. The planner can evaluate the function once at plan time and inline the result. Examples: mathematical operations, string transformations.
  • STABLE — returns the same result within a single query, but may differ across queries (e.g. reads a config table). The planner can cache results within a single scan but won't inline them at plan time.
  • VOLATILE (default) — may return different results every call. The planner never caches. Required for functions that modify data or call NOW(), RANDOM(), or sequence functions.

Choosing the correct label is not just a hint — it affects correctness. Marking a function IMMUTABLE when it reads the database can cause the planner to use a stale cached value from an earlier point in the query.

Creating a Function

PL/pgSQL is PostgreSQL's procedural language. It looks like Pascal-style pseudocode wrapped in SQL. The function body is a string delimited by dollar-quoting ($$) — you can use any matching pair like $body$ or $func$ if your function body itself contains single quotes.

The DECLARE block defines local variables. The BEGIN ... END block is the function body. You assign variables with := (not =). You raise errors with RAISE EXCEPTION, which automatically rolls back the current transaction.

sql — PL/pgSQL function with explanation
CREATE OR REPLACE FUNCTION calculate_discount(
    price         NUMERIC,   -- input parameter (passed by value)
    discount_pct  NUMERIC    -- input parameter
)
RETURNS NUMERIC              -- the type this function gives back
LANGUAGE plpgsql              -- tells PG which language to use
IMMUTABLE                     -- no DB access, same input = same output
AS $$                         -- start of function body string
DECLARE
    discounted_price NUMERIC; -- local variable
BEGIN
    -- Guard clause: validate input before doing any work
    IF discount_pct < 0 OR discount_pct > 100 THEN
        RAISE EXCEPTION 'Discount must be between 0 and 100, got %', discount_pct;
        -- % is a format placeholder, like printf. This rolls back the transaction.
    END IF;

    discounted_price := price * (1 - discount_pct / 100.0);
    RETURN discounted_price; -- must RETURN a value matching the declared type
END;
$$;

-- Functions can be called anywhere an expression is valid
SELECT name, price, calculate_discount(price, 15) AS sale_price
FROM products;

-- In a WHERE clause
SELECT name FROM products
WHERE calculate_discount(price, 20) < 50;

-- Standalone
SELECT calculate_discount(199.99, 10); -- → 179.991

Table-Returning Functions

A function declared with RETURNS TABLE(...) is sometimes called a "parameterised view". Unlike a regular view, it accepts arguments — so you can filter at definition time rather than wrapping the view in an outer query. The planner can often push down additional WHERE conditions from the calling query into the function body (this is called "inlining", and only works for LANGUAGE sql functions marked STABLE or IMMUTABLE).

An alternative is RETURNS SETOF record with OUT parameters, or RETURNS SETOF existing_type where the return type is an existing table or composite type. The RETURNS TABLE syntax is the most readable and explicit.

A function declared with RETURNS TABLE(...) returns a result set just like a regular query. You can use it in a FROM clause exactly like a table or view. This is useful for parameterised queries that are too complex for a view (views can't take parameters), or when you want to encapsulate a query with business logic that should be reused across the application.

sql — returns a set of rows
CREATE OR REPLACE FUNCTION get_products_by_category(
    p_category  TEXT,
    p_max_price NUMERIC DEFAULT 9999999  -- DEFAULT makes the param optional
)
RETURNS TABLE(             -- column names and types for the result set
    product_id INT,
    name       TEXT,
    price      NUMERIC
)
LANGUAGE sql   -- plain SQL language (simpler than plpgsql when no control flow)
STABLE         -- reads the DB, same results within one query
AS $$
    SELECT product_id, name, price
    FROM products
    WHERE category = p_category
      AND price <= p_max_price
    ORDER BY price;
$$;

-- Called like a table — can be JOINed, filtered, aggregated
SELECT * FROM get_products_by_category('Electronics', 100);

-- Use in a JOIN
SELECT p.name, p.price, o.order_id
FROM get_products_by_category('Electronics') p
JOIN order_items o ON o.product_id = p.product_id;

-- With optional parameter (uses the DEFAULT 9999999)
SELECT * FROM get_products_by_category('Books');

Triggers

A trigger is an instruction that tells PostgreSQL to automatically call a function when a specific event happens on a table — an INSERT, UPDATE, DELETE, or TRUNCATE. Triggers are how you enforce business rules, maintain derived data, or build audit trails without relying on application code to remember to do it.

Every trigger has two parts: the trigger function (the logic, written in PL/pgSQL returning TRIGGER) and the trigger definition (which table, which event, which timing). One trigger function can be reused by many trigger definitions across multiple tables.

Trigger Anatomy

OptionChoicesMeaning
TimingBEFORE / AFTER / INSTEAD OFWhen relative to the operation the trigger fires. BEFORE can modify the row or cancel the operation. AFTER runs after the row is committed to the table (can't modify the row).
EventINSERT / UPDATE / DELETE / TRUNCATEWhich DML operation fires the trigger. You can combine: INSERT OR UPDATE.
GranularityFOR EACH ROW / FOR EACH STATEMENTROW triggers fire once per affected row. STATEMENT triggers fire once per SQL statement regardless of how many rows are affected.

NEW and OLD: The Row Variables

Inside a row-level trigger function, PostgreSQL gives you two special record variables:

  • NEW — the row as it will be after the operation (available in INSERT and UPDATE triggers). In a BEFORE trigger, you can modify NEW fields to change what gets written to the table.
  • OLD — the row as it was before the operation (available in UPDATE and DELETE triggers). You can read it but not modify it.

A BEFORE row trigger must return either NEW (to proceed with the write, potentially modified), OLD (for DELETE, to proceed), or NULL (to silently cancel the operation for this row). An AFTER trigger's return value is ignored — the write already happened.

Example 1 — Auto-update Timestamp

The most common trigger in the wild: automatically set an updated_at column on every UPDATE so application code never has to remember to pass it. The trigger fires BEFORE the UPDATE, modifies NEW.updated_at, and returns the modified NEW — so the timestamp is baked into the row before it hits disk.

sql
-- Step 1: Create the trigger function
-- Returns TRIGGER (not a regular type) — this is always required for trigger functions
CREATE OR REPLACE FUNCTION set_updated_at()
RETURNS TRIGGER
LANGUAGE plpgsql
AS $$
BEGIN
    NEW.updated_at := NOW();  -- overwrite whatever the app passed in
    RETURN NEW;               -- MUST return NEW in a BEFORE INSERT/UPDATE trigger
END;
$$;

-- Step 2: Attach the trigger to a table
-- BEFORE UPDATE means it fires before the row is written — so we can still modify NEW
CREATE TRIGGER trg_products_updated
    BEFORE UPDATE ON products
    FOR EACH ROW
    EXECUTE FUNCTION set_updated_at();

-- Attach the same function to another table — trigger functions are reusable
CREATE TRIGGER trg_orders_updated
    BEFORE UPDATE ON orders
    FOR EACH ROW
    EXECUTE FUNCTION set_updated_at();

Example 2 — Audit Log Trigger

A common production pattern: record every change to a sensitive table into a separate audit log, capturing who changed what and when. This fires AFTER the update so the main write succeeds first, and uses OLD to capture the before-state.

sql
-- The audit log table that records all changes
CREATE TABLE employee_audit (
    audit_id    SERIAL PRIMARY KEY,
    employee_id INT,
    changed_at  TIMESTAMPTZ  DEFAULT NOW(),
    changed_by  TEXT         DEFAULT current_user,
    old_salary  NUMERIC,
    new_salary  NUMERIC,
    old_dept    TEXT,
    new_dept    TEXT
);

-- Trigger function: fires AFTER UPDATE, reads both OLD and NEW
CREATE OR REPLACE FUNCTION log_employee_changes()
RETURNS TRIGGER
LANGUAGE plpgsql
AS $$
BEGIN
    -- Only log if salary or department actually changed
    -- IS DISTINCT FROM handles NULLs correctly (unlike !=)
    IF NEW.salary IS DISTINCT FROM OLD.salary
    OR NEW.department IS DISTINCT FROM OLD.department THEN

        INSERT INTO employee_audit
            (employee_id, old_salary, new_salary, old_dept, new_dept)
        VALUES
            (OLD.employee_id, OLD.salary, NEW.salary, OLD.department, NEW.department);
    END IF;

    RETURN NEW; -- return value ignored in AFTER triggers, but good practice
END;
$$;

-- Attach: fires AFTER UPDATE, only when salary OR department changed
CREATE TRIGGER trg_employee_audit
    AFTER UPDATE OF salary, department ON employees
    FOR EACH ROW
    WHEN (OLD.* IS DISTINCT FROM NEW.*)  -- skip no-op updates
    EXECUTE FUNCTION log_employee_changes();

Example 3 — Prevent Deletes (Soft Delete Enforcement)

An INSTEAD OF trigger on a view, or a BEFORE DELETE trigger returning NULL, can enforce that certain rows are never physically deleted — they're "soft deleted" instead by setting an is_deleted flag.

sql
CREATE OR REPLACE FUNCTION soft_delete_employee()
RETURNS TRIGGER
LANGUAGE plpgsql
AS $$
BEGIN
    -- Instead of deleting, mark the row as inactive
    UPDATE employees
    SET
        is_active   = FALSE,
        deleted_at  = NOW(),
        deleted_by  = current_user
    WHERE employee_id = OLD.employee_id;

    RETURN NULL; -- returning NULL from a BEFORE trigger cancels the DELETE
END;
$$;

CREATE TRIGGER trg_no_hard_delete
    BEFORE DELETE ON employees
    FOR EACH ROW
    EXECUTE FUNCTION soft_delete_employee();

-- Now this DELETE will soft-delete instead of removing the row:
DELETE FROM employees WHERE employee_id = 5;
-- Row still exists: is_active = false, deleted_at = now()

Managing Triggers

sql
-- List all triggers on a table
SELECT trigger_name, event_manipulation, action_timing, action_orientation
FROM information_schema.triggers
WHERE event_object_table = 'employees';

-- Temporarily disable a trigger (e.g. for bulk data loading)
ALTER TABLE employees DISABLE TRIGGER trg_employee_audit;
-- ... run bulk inserts ...
ALTER TABLE employees ENABLE TRIGGER trg_employee_audit;

-- Disable ALL triggers on a table (requires superuser)
ALTER TABLE employees DISABLE TRIGGER ALL;

-- Drop a trigger
DROP TRIGGER trg_employee_audit ON employees;
Trigger Pitfalls
  • Hidden performance cost — triggers are invisible to application developers reading the code. A slow trigger on a high-volume table is very hard to diagnose. Always check pg_stat_user_functions if a table's writes are unexpectedly slow.
  • Cascading triggers — a trigger that modifies another table can fire triggers on that table, which modify another, and so on. This is called trigger chaining and can cause infinite loops. PostgreSQL has no built-in depth limit — guard against this with a session variable check.
  • No trigger on bulk COPY — COPY FROM does not fire row-level triggers by default. If you use COPY for data loading, audit triggers will miss those rows.

JSON & JSONB

Store, query, and index semi-structured data natively in PostgreSQL — without losing relational power.

JSON vs JSONB

PostgreSQL supports two JSON column types. The rule is simple: almost always use JSONB. JSON stores the raw text verbatim — which means it preserves duplicate keys and whitespace, but has to re-parse the text on every read. JSONB parses it once on write into a binary format, deduplicates keys (last value wins), and reads much faster. The only reason to use JSON is when you specifically need to preserve the original text formatting, which is rare.

Filtering with Nested Paths

The most efficient way to filter on a JSONB field depends on what you're checking. For exact-match checks on nested fields, the containment operator @> works on any depth and is supported by a GIN index. For comparisons (greater than, less than), use the ->> or #>> operators and cast to the appropriate type.

sql — filtering patterns
-- Equality on a top-level field (use ->> for text comparison)
SELECT name FROM users WHERE metadata ->> 'role' = 'admin';

-- Equality on nested field using path operator
SELECT name FROM users
WHERE metadata #>> '{address,city}' = 'Nairobi';

-- Numeric comparison — cast the text result to a number
SELECT name FROM users
WHERE (metadata ->> 'score')::NUMERIC > 80;

-- Nested numeric comparison
SELECT name FROM users
WHERE (metadata #>> '{address,coords,lat}')::FLOAT < 0;  -- southern hemisphere

-- Containment: check if JSON contains a nested structure (index-supported)
SELECT name FROM users
WHERE metadata @> '{"address": {"country": "Kenya"}}';

-- Check notifications email setting at any depth
SELECT name FROM users
WHERE metadata @> '{"preferences": {"notifications": {"email": true}}}';

-- Array contains a specific element
SELECT name FROM users
WHERE metadata @> '{"tags": ["vip"]}';

-- Key exists at top level
SELECT name FROM users WHERE metadata ? 'score';

-- Check existence of a nested key (must use #>> or containment)
SELECT name FROM users
WHERE (metadata #> '{address,coords}') IS NOT NULL;  -- has coords sub-object

Indexing JSONB

A GIN index on the whole JSONB column supports the containment (@>) and existence (?, ?|, ?&) operators for any field at any depth. It's powerful but large — it indexes every key and value in the document. A targeted expression index on a specific path is smaller and faster for queries you know in advance.

sql
-- GIN index on the whole column: supports @>, ?, ?|, ?&
-- Good when you query many different fields unpredictably
CREATE INDEX idx_users_metadata ON users USING GIN(metadata);

-- Expression index on a specific top-level field
-- Only useful for queries that use exactly this expression
CREATE INDEX idx_users_role ON users ((metadata ->> 'role'));

-- Expression index on a NESTED field
CREATE INDEX idx_users_city ON users ((metadata #>> '{address,city}'));

-- The query MUST use the same expression to hit the index:
SELECT * FROM users WHERE metadata #>> '{address,city}' = 'Nairobi'; -- ✓ uses index
SELECT * FROM users WHERE metadata -> 'address' ->> 'city' = 'Nairobi'; -- ✗ different expr

-- Cast in expression index (for numeric comparisons without full cast each time)
CREATE INDEX idx_users_score ON users (((metadata ->> 'score')::NUMERIC));
SELECT * FROM users WHERE (metadata ->> 'score')::NUMERIC > 80; -- ✓ uses index

-- jsonpath matching with @@ operator (PostgreSQL 12+)
-- More expressive than containment — supports conditions, wildcards
SELECT * FROM users WHERE metadata @@ '$.score > 80';
SELECT * FROM users WHERE metadata @@ '$.address.city == "Nairobi"';
SELECT * FROM users WHERE metadata @@ '$.tags[*] == "vip"'; -- any tag = vip

Modifying JSONB

JSONB columns are immutable in place — you can't update a single field without replacing the whole column value. PostgreSQL provides functions and operators to do this immutably: they return a new JSONB value with the change applied, which you then SET back onto the column.

sql
-- jsonb_set(target, path, new_value, create_missing)
-- Updates a nested field at any depth, creates it if it doesn't exist
UPDATE users
SET metadata = jsonb_set(metadata, '{score}', '100')
WHERE name = 'Alice';

-- Update a nested field (address.city) without touching other fields
UPDATE users
SET metadata = jsonb_set(metadata, '{address,city}', '"Kisumu"', true)
WHERE name = 'Bob';

-- Create deeply nested field (create_missing = true)
UPDATE users
SET metadata = jsonb_set(
    metadata,
    '{address,coords}',
    '{"lat": -4.043, "lng": 39.668}',
    true   -- create the key if it doesn't exist
)
WHERE name = 'Bob';

-- || (merge): merges at the top level, adding/overwriting keys
-- Does NOT deep-merge — nested objects are replaced entirely
UPDATE users
SET metadata = metadata || '{"verified": true, "score": 99}';

-- - (delete key): remove a top-level key
UPDATE users
SET metadata = metadata - 'score';

-- #- (delete by path): remove a nested key
UPDATE users
SET metadata = metadata #- '{address,coords}';  -- remove coords from address

-- Append to a JSONB array
UPDATE users
SET metadata = jsonb_set(
    metadata,
    '{tags}',
    (metadata -> 'tags') || '"premium"'  -- concat a new element
)
WHERE name = 'Alice';

Full-Text Search

Search through text documents the smart way — with stemming, ranking, and highlighting — without a separate search engine.

The Basics: tsvector & tsquery

PostgreSQL's full-text search works by converting text into a canonical form before indexing it, so searches work naturally across grammatical variations. "Running", "ran", and "runs" all reduce to the lexeme "run". This process — stripping stop words, lowercasing, and applying stemming rules — is controlled by a text search configuration (e.g. 'english', 'french', 'simple'). The 'simple' configuration only lowercases and removes stop words without stemming, which is useful for exact-token matching like product codes or identifiers.

tsvector is a preprocessed, sorted list of lexemes (stemmed, normalized tokens). tsquery is a search query. The @@ operator tests if a query matches a document.

sql
-- Convert text to tsvector (language-aware stemming)
SELECT to_tsvector('english', 'The quick brown fox jumps over the lazy dog');
-- Result: 'brown':3 'dog':9 'fox':4 'jump':5 'lazi':8 'quick':2

-- Convert a search phrase to tsquery
SELECT to_tsquery('english', 'jumping & dogs');
-- Result: 'jump' & 'dog'  (stemmed!)

-- Match test
SELECT to_tsvector('english', 'the quick brown fox')
    @@ to_tsquery('english', 'fox');  -- → true

Full Table FTS

For real applications, you pre-compute the tsvector and store it in a dedicated column with a GIN index. This is much faster than calling to_tsvector() at query time on every row. A trigger keeps the stored vector up to date automatically whenever the source columns change — the example below uses PostgreSQL's built-in tsvector_update_trigger() function which handles this without custom PL/pgSQL code.

The ts_rank() function scores each matching document by how frequently and prominently the query terms appear. Higher rank = more relevant. ts_headline() returns a snippet of the original text with query terms highlighted — similar to the bold excerpts shown in web search results.

sql
CREATE TABLE articles (
    id      SERIAL PRIMARY KEY,
    title   TEXT,
    body    TEXT,
    search_vector TSVECTOR  -- pre-computed, kept updated by trigger
);

-- Index the vector column
CREATE INDEX idx_articles_fts ON articles USING GIN(search_vector);

-- Trigger to auto-update the vector
CREATE TRIGGER trg_articles_search
    BEFORE INSERT OR UPDATE ON articles
    FOR EACH ROW EXECUTE FUNCTION
    tsvector_update_trigger(search_vector, 'pg_catalog.english', title, body);

-- Search with ranking
SELECT
    id,
    title,
    ts_rank(search_vector, query)       AS rank,
    ts_headline('english', body, query,
        'MaxWords=30, MinWords=15')        AS snippet
FROM
    articles,
    to_tsquery('english', 'PostgreSQL & performance') AS query
WHERE  search_vector @@ query
ORDER BY rank DESC
LIMIT 10;

Query Functions Compared

PostgreSQL provides four functions for constructing a tsquery, each with different input syntax — choose based on where the query comes from:

  • to_tsquery — expects explicit Boolean operators (&, |, !). Good for programmatic use where you construct the query string yourself.
  • plainto_tsquery — treats all words as AND. Simplest for basic user input: 'query optimization' becomes 'queri' & 'optim'.
  • phraseto_tsquery — treats words as a phrase (must appear adjacent in order): 'query optimization' becomes 'queri' <-> 'optim'.
  • websearch_to_tsquery (PG 11+) — Google-style syntax: quoted phrases, minus for exclusion, AND/OR keywords. Best for search boxes exposed to end users.
sql
-- phraseto: for when word order matters
SELECT phraseto_tsquery('english', 'query optimization');
-- 'queri' <-> 'optim'  (adjacent)

-- websearch_to_tsquery: Google-style syntax (PG 11+)
SELECT websearch_to_tsquery('english', '"index scan" -hash');
-- 'index' <-> 'scan' & !'hash'

Table Partitioning

Split huge tables into smaller, manageable chunks — and let the query planner skip irrelevant chunks entirely.

Why Partition?

  • Query performance: Partition pruning skips partitions that can't match the WHERE clause
  • Data management: Drop an entire partition to delete a year of logs instantly (DROP TABLE vs bulk DELETE)
  • Maintenance: VACUUM and ANALYZE run on smaller pieces
  • Parallel processing: Different partitions can be scanned in parallel

Range Partitioning (by date)

Range partitioning divides rows by a continuous range of values — most commonly a date or timestamp. Each partition holds rows where the partition key falls within a specific range (non-overlapping, contiguous). This is the most common partition strategy for time-series data like orders, events, and logs.

The most powerful benefit is partition pruning: when your WHERE clause filters on the partition key, the planner reads only the relevant partition(s) and completely skips the rest — even if the parent table has billions of rows. This can turn an hours-long scan into a millisecond lookup. You can also drop old partitions instantly with DROP TABLE orders_2022 (a metadata operation, no row scanning) rather than a slow DELETE.

sql
-- 1. Create the parent (partitioned) table
CREATE TABLE orders (
    order_id    BIGINT       NOT NULL,
    order_date  DATE         NOT NULL,
    customer_id INT          NOT NULL,
    total       NUMERIC(12,2)
) PARTITION BY RANGE (order_date);

-- 2. Create child partitions
CREATE TABLE orders_2023 PARTITION OF orders
    FOR VALUES FROM ('2023-01-01') TO ('2024-01-01');

CREATE TABLE orders_2024 PARTITION OF orders
    FOR VALUES FROM ('2024-01-01') TO ('2025-01-01');

CREATE TABLE orders_2025 PARTITION OF orders
    FOR VALUES FROM ('2025-01-01') TO ('2026-01-01');

-- 3. Indexes on child partitions (PG 11+: create on parent)
CREATE INDEX ON orders(order_date);
-- Automatically creates index on all partitions and future ones

-- 4. Query — Postgres prunes to only relevant partition
SELECT * FROM orders
WHERE order_date BETWEEN '2024-03-01' AND '2024-03-31';
-- EXPLAIN will show: Seq Scan on orders_2024 (only!)

List Partitioning (by category)

List partitioning assigns specific discrete values to each partition. Use it when your partition key has a known, finite set of values — country codes, regions, status values, tenant IDs. Unlike range partitioning, there's no inherent ordering, so list partitioning doesn't help with range queries — it only prunes when the query filters on exact values in the partition key.

The DEFAULT partition catches any rows whose values don't match any defined partition. This is good defensive programming — without it, inserts with unexpected values fail with an error. The default partition can't be split later without detaching and re-inserting, so plan your value space carefully.

sql
CREATE TABLE products_by_region (
    product_id INT,
    region     TEXT,
    price      NUMERIC
) PARTITION BY LIST (region);

CREATE TABLE products_east_africa PARTITION OF products_by_region
    FOR VALUES IN ('kenya', 'tanzania', 'uganda');

CREATE TABLE products_west_africa PARTITION OF products_by_region
    FOR VALUES IN ('nigeria', 'ghana', 'senegal');

CREATE TABLE products_other PARTITION OF products_by_region
    DEFAULT;  -- catch-all partition

Hash Partitioning (even distribution)

Hash partitioning distributes rows evenly across partitions by hashing the partition key. Unlike range and list partitioning, there's no pruning based on value ranges — instead, a single lookup value hashes to exactly one partition, which can speed up point lookups. The main use case is distributing write load across multiple partitions (and potentially tablespaces on different disks) when data arrives in no particular order.

Choosing the number of partitions is a commitment — adding more later requires rebuilding the entire table. A power of 2 is conventional, though not required. Typically 4–16 partitions is sufficient for most hash partitioning use cases.

sql
-- Split evenly across N partitions (great for sharding by user_id)
CREATE TABLE events (
    event_id   BIGINT,
    user_id    INT,
    event_type TEXT
) PARTITION BY HASH (user_id);

CREATE TABLE events_p0 PARTITION OF events
    FOR VALUES WITH (MODULUS 4, REMAINDER 0);
CREATE TABLE events_p1 PARTITION OF events
    FOR VALUES WITH (MODULUS 4, REMAINDER 1);
-- ... p2, p3

Security & Roles

Lock down your database with PostgreSQL's robust role-based access control and row-level security.

Roles & Users

In PostgreSQL, users and groups are both "roles". The difference is just whether the role can log in (LOGIN attribute). This unified model is more flexible than the traditional user/group distinction: a role can be a member of another role, inheriting its permissions; and a single person can have multiple roles with different privilege levels, switching between them as needed with SET ROLE.

The principle of least privilege is the foundation of good database security: every role should have exactly the permissions needed for its function — no more. In practice, this means your application should connect as a role that can only SELECT/INSERT/UPDATE the tables it needs, with no CREATE, DROP, or TRUNCATE rights. The superuser postgres account should only be used for administration.

The difference is just whether the role can log in.

sql
-- Create a role (group)
CREATE ROLE readonly;
CREATE ROLE app_user;

-- Create a login user
CREATE USER alice WITH PASSWORD 'strongpassword';

-- Grant role membership
GRANT readonly TO alice;

Privileges (GRANT / REVOKE)

Privileges in PostgreSQL are object-level: you grant or revoke specific operations on specific objects (tables, sequences, functions, schemas) to specific roles. The most commonly needed table privileges are SELECT, INSERT, UPDATE, and DELETE. The TRUNCATE, REFERENCES, and TRIGGER privileges are granted separately and rarely needed by application roles.

A critical detail: granting privileges on existing tables doesn't affect tables created in the future. The ALTER DEFAULT PRIVILEGES command sets what privileges are automatically granted on objects created later — always set this when creating a new schema so new tables aren't accidentally inaccessible.

sql
-- Table privileges
GRANT SELECT                       ON products       TO readonly;
GRANT SELECT, INSERT, UPDATE       ON products       TO app_user;
GRANT ALL PRIVILEGES               ON ALL TABLES
    IN SCHEMA public                               TO app_user;

-- Future tables too (default privileges)
ALTER DEFAULT PRIVILEGES IN SCHEMA public
    GRANT SELECT ON TABLES TO readonly;

-- Revoke
REVOKE DELETE ON products FROM app_user;

Row-Level Security (RLS)

Row-Level Security lets you define policies that restrict which rows each role can see or modify — the database enforces this automatically on every query, regardless of how the query is written. This is the foundation of multi-tenant applications built on a shared schema: each tenant's role can only see rows where a tenant_id matches their identity, without any application code changes needed.

RLS policies are transparent to the application. A query like SELECT * FROM orders will silently return only the rows the current role is allowed to see — no joins or WHERE clauses needed in the application. This makes it much harder to accidentally leak data through a new code path or API endpoint. The downside is that RLS policies add complexity to the database layer and can be hard to debug when behaviour seems inconsistent.

RLS lets you restrict which rows a user can see — based on the current user's identity or role. Perfect for multi-tenant applications.

sql
-- Enable RLS on a table
ALTER TABLE orders ENABLE ROW LEVEL SECURITY;

-- Policy: users can only see their own orders
CREATE POLICY orders_user_isolation ON orders
    USING (customer_id = (SELECT id FROM users
                            WHERE username = current_user));

-- Separate INSERT policy
CREATE POLICY orders_insert ON orders
    FOR INSERT
    WITH CHECK (customer_id = (SELECT id FROM users
                                 WHERE username = current_user));

-- Bypass RLS for admin role
ALTER TABLE orders FORCE ROW LEVEL SECURITY;
GRANT BYPASSRLS TO admin_role;

Schemas for Isolation

A PostgreSQL schema is a namespace within a database — like a folder that contains tables, views, functions, and other objects. Every database starts with a public schema, but you can create as many schemas as you need. Schemas are a lighter-weight isolation mechanism than separate databases: multiple schemas in one database can still join data across schema boundaries, share connections, and be managed together.

A common multi-tenancy pattern is to give each tenant their own schema with identical table structures. The application sets search_path to the tenant's schema on each connection, so all queries run against that tenant's tables without schema-qualifying every table name. This provides strong isolation without the overhead of separate database clusters.

sql
-- Create tenant schemas
CREATE SCHEMA tenant_acme;
CREATE SCHEMA tenant_beta;

-- Grant schema access
GRANT USAGE ON SCHEMA tenant_acme TO acme_user;
GRANT ALL ON ALL TABLES IN SCHEMA tenant_acme TO acme_user;

-- Set search path so you don't need schema prefix
SET search_path = tenant_acme, public;
Security Best Practices
  • Never use the postgres superuser for application connections
  • Grant only the minimum privileges needed (principle of least privilege)
  • Use SCRAM-SHA-256 password hashing in pg_hba.conf (not md5)
  • Enable SSL/TLS for all connections, especially over networks
  • Use connection pooling (PgBouncer) to limit direct DB connections

What is MongoDB?

When to Choose MongoDB

  • Flexible / evolving schema — product catalogs, user profiles, CMS content
  • Hierarchical / nested data — documents where embedding avoids joins
  • High write throughput — event logs, IoT sensor data, activity feeds
  • Horizontal scaling — built-in sharding across multiple servers
  • Developer speed — schema-less iteration in early product development
MongoDB vs PostgreSQL
MongoDB and PostgreSQL are not competitors — they solve different problems well. MongoDB shines for hierarchical, schema-flexible, high-throughput scenarios. PostgreSQL wins when you need complex JOINs, strong consistency, rich SQL, or financial accuracy. See Chapter M12 for a full comparison.

Defining a Schema

js — models/Product.js
const { Schema, model } = require('mongoose');

const reviewSchema = new Schema({
  user:    { type: String,  required: true },
  rating:  { type: Number,  min: 1, max: 5, required: true },
  comment: { type: String,  maxlength: 500 },
  date:    { type: Date,    default: Date.now }
}, { _id: false });

const productSchema = new Schema({
  name: {
    type:     String,
    required: [true, 'Product name is required'],
    trim:     true,
    maxlength: 200
  },
  category: {
    type: String,
    enum: ['Electronics', 'Furniture', 'Books', 'Other'],
    required: true
  },
  price: {
    type:    Number,
    required: true,
    min:     [0, 'Price cannot be negative']
  },
  stock:    { type: Number, default: 0, min: 0 },
  tags:     [String],               // array of strings
  specs:    { type: Map, of: Schema.Types.Mixed },
  reviews:  [reviewSchema],           // array of sub-documents
  isActive: { type: Boolean, default: true }
}, {
  timestamps: true,   // auto adds createdAt, updatedAt
  collection: 'products'
});

// ── Virtuals ──────────────────────────────────────────────────────
// Virtual: not stored in DB, computed on access
productSchema.virtual('inventoryValue').get(function() {
  return this.price * this.stock;
});
productSchema.virtual('averageRating').get(function() {
  if (!this.reviews.length) return null;
  return this.reviews.reduce((s,r) => s + r.rating, 0) / this.reviews.length;
});

// ── Middleware hooks ───────────────────────────────────────────────
productSchema.pre('save', async function(next) {
  // 'this' refers to the document being saved
  if (this.isModified('price')) {
    console.log(`Price changed to ${this.price}`);
  }
  next();
});
productSchema.post('save', function(doc) {
  console.log(`Product saved: ${doc._id}`);
});

// ── Instance method ───────────────────────────────────────────────
productSchema.methods.applyDiscount = function(pct) {
  return this.price * (1 - pct / 100);
};

// ── Static method ─────────────────────────────────────────────────
productSchema.statics.findByCategory = function(cat) {
  return this.find({ category: cat, isActive: true });
};

// Export the model
const Product = model('Product', productSchema);
module.exports = Product;

Understanding Pre/Post Middleware Hooks

Mongoose middleware (hooks) are functions that run automatically at specific points in a document's lifecycle. Pre hooks run before the operation — useful for validation, transformation, or setting derived fields. Post hooks run after — useful for logging, cache invalidation, or triggering side effects.

The this context inside a pre('save') hook refers to the document being saved. The method this.isModified('fieldName') returns true only if that specific field changed since the document was last loaded — very useful for expensive operations like password hashing that you only want to run when the password actually changes, not on every save.

Important: hooks defined with pre('save') only fire for doc.save() and Model.create(). They do not fire for Model.updateOne() or Model.findOneAndUpdate(). For those, use pre('findOneAndUpdate') or restructure to load-modify-save.

Query Operators

js
// Comparison: $eq $ne $gt $gte $lt $lte $in $nin
await Product.find({ price: { $gt: 100 } });
await Product.find({ price: { $gte: 50, $lte: 200 } });  // BETWEEN
await Product.find({ category: { $in: ['Books', 'Furniture'] } });
await Product.find({ category: { $nin: ['Electronics'] } });

// Logical: $and $or $not $nor
await Product.find({ $and: [{ category: 'Electronics' }, { price: { $lt: 100 } }] });
await Product.find({ $or: [{ stock: 0 }, { isActive: false }] });

// Element: $exists $type
await Product.find({ specs: { $exists: true } });
await Product.find({ price: { $type: 'number' } });

// Array operators: $all $elemMatch $size
await Product.find({ tags: { $all: ['laptop', 'premium'] } });
await Product.find({ reviews: { $elemMatch: { rating: { $gte: 5 } } } });

// Regex: case-insensitive search
await Product.find({ name: { $regex: /laptop/i } });
await Product.find({ name: /pro/i });    // shorthand

// Dot notation for nested fields
await Product.find({ 'specs.ram_gb': { $gte: 16 } });

How Mongoose Queries Work Internally

When you call Product.find(), Mongoose doesn't immediately hit the database. It builds a Query object — a description of what you want. The query only executes when you call .then(), await it, or call .exec(). This lazy evaluation lets you chain methods (.sort().limit().select()) before the query runs.

The result is an array of Mongoose Documents — full objects with prototype methods, change-tracking, virtual getters, and validation built in. This is powerful but has overhead: Mongoose wraps every returned object and tracks its state. For API endpoints that just read and serialize data, this overhead is unnecessary.

// With lean(): returns plain JS objects — much faster for read-only queries

  .find({ category: 'Electronics' })
  .lean();           // ~3-5x faster, lower memory

// lean() + virtuals (Mongoose 6+)

  .find({})
  .lean({ virtuals: true });  // includes computed virtuals

Performance Rule of Thumb
Use .lean() for any GET/read endpoint that just formats and returns data. Reserve full Mongoose Documents for operations that need to call .save() or use instance methods.

Aggregation Pipeline

Aggregation Pipeline

The aggregation pipeline transforms documents through a series of stages — the MongoDB equivalent of SQL's GROUP BY, JOIN, and computed columns all in one.

Pipeline Concept

An aggregation pipeline is an array of stages. Documents flow through each stage in order, each stage transforming the stream. Think of it as a Unix pipe: collection | $match | $group | $sort | $limit.

The most important performance rule for aggregation pipelines: put $match and $limit as early as possible. Every stage after $match only processes the documents that survived the filter — so filtering early dramatically reduces the work done by all subsequent stages. Similarly, if you only need the top 10 results, add $limit: 10 right after the sort before any expensive $lookup stages.

The pipeline is processed stage-by-stage in memory. If a stage produces a result set larger than 100MB, MongoDB will throw an error unless you set allowDiskUse: true in the aggregation options. For production pipelines on large collections, always test with realistic data volumes.

Relationships & Population

Model relationships with embedding or referencing — and use Mongoose's populate() to resolve references.

Making the Embedding Decision

The most important data modelling question in MongoDB is: should this related data be embedded or referenced? The answer hinges on your access patterns — how you read the data matters more than the logical relationship.

Embed when: the child data is always loaded with the parent (a user's address, a product's images), the child data isn't shared across multiple parent documents, and the child array won't grow unboundedly. A document in MongoDB has a 16MB limit — embedding an array that could grow to thousands of items (like all orders for a customer) will eventually hit that limit and cause write performance to degrade as the document gets larger.

Reference when: the child data is accessed independently of the parent, the relationship is many-to-many (an order references a product, but a product can be in many orders), or the child set is unbounded (all events by a user, all comments on a post).

Transactions & Sessions

MongoDB supports multi-document ACID transactions (replica set or sharded cluster required).

When You Need Transactions

MongoDB single-document operations are always atomic. Multi-document transactions are needed when you must update multiple documents or collections atomically — like transferring credits between accounts.

Replica Set Required
Transactions require a replica set or sharded cluster. A single standalone mongod does not support transactions. In development, use a replica set: docker run mongo:7 --replSet rs0.

withTransaction Pattern (Recommended)

js
const mongoose = require('mongoose');

async function transferBalance(fromId, toId, amount) {
  const session = await mongoose.startSession();

  try {
    await session.withTransaction(async () => {
      // All ops use { session } to participate in transaction
      const from = await Account.findById(fromId).session(session);
      if (!from || from.balance < amount) {
        throw new Error('Insufficient balance');
      }

      await Account.updateOne(
        { _id: fromId },
        { $inc: { balance: -amount } },
        { session }
      );
      await Account.updateOne(
        { _id: toId },
        { $inc: { balance: amount } },
        { session }
      );

      await TransactionLog.create([{
        from: fromId, to: toId, amount,
        timestamp: new Date()
      }], { session });
    });
    // withTransaction auto-commits on success, auto-retries on transient errors
    console.log('Transfer complete');
  } finally {
    session.endSession();
  }
}

js

MongoDB vs PostgreSQL

Feature Comparison

Choose PostgreSQL When

  • Your data is highly relational — orders, customers, products, inventory with many FK relationships
  • You need complex JOINs across many tables in a single query
  • You're handling financial data — NUMERIC precision, strict constraints, audit trails
  • You need full SQL expressiveness — window functions, CTEs, complex aggregations
  • Your team knows SQL well
  • You need strong referential integrity enforced at the database level

Choose MongoDB When

  • Your data is naturally hierarchical — e.g. a blog post with embedded comments and tags
  • Your schema evolves rapidly — early-stage product, A/B testing different document shapes
  • You have variable structure — product catalog with different specs per category
  • You need horizontal write scaling from day one — IoT, real-time events, logs
  • Your access pattern is document-centric — you always load the whole object
  • Your team uses Node.js and prefers working with JSON end-to-end

Use Both (Polyglot Persistence)

Many production systems use both databases for what each does best:

js — example: e-commerce with both DBs
// PostgreSQL: orders, payments, inventory, users (relational core)
// MongoDB: product catalog (flexible specs), reviews, activity feed, sessions

// PostgreSQL via pg or Prisma
const { Pool } = require('pg');
const pgPool = new Pool({ connectionString: process.env.PG_URI });

// MongoDB via Mongoose
await mongoose.connect(process.env.MONGO_URI);

// Create an order: write to Postgres for ACID integrity
async function createOrder(customerId, items) {
  const pgClient = await pgPool.connect();
  try {
    await pgClient.query('BEGIN');
    const { rows } = await pgClient.query(
      'INSERT INTO orders (customer_id, total) VALUES ($1, $2) RETURNING id',
      [customerId, items.reduce((s,i) => s + i.price * i.qty, 0)]
    );
    await pgClient.query('COMMIT');
    // Log to MongoDB activity feed (best-effort, no transaction needed)
    await ActivityFeed.create({ type: 'order_placed', orderId: rows[0].id });
    return rows[0];
  } catch (e) { await pgClient.query('ROLLBACK'); throw e; }
  finally  { pgClient.release(); }
}
The Real Answer
The best database is the one your team knows well and that fits your access patterns. Start with one, measure, then add a second store only when you have a clear, concrete reason — not because it sounds architecturally cool.
